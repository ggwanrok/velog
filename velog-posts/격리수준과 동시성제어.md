<p>데이터베이스에는 여러 사용자가 동시에 접근한다.</p>
<p>예를 들어 은행 시스템에서는 한 사용자가 계좌이체를 수행하는 동안 다른 사용자가 같은 계좌의 잔액을 조회하거나 결제할 수 있다. 쇼핑몰에서는 여러 사용자가 동시에 마지막 재고 한 개를 주문할 수 있고, 예약 시스템에서는 같은 좌석을 동시에 선택할 수 있다.</p>
<p>이러한 요청을 무조건 하나씩 순서대로 처리하면 데이터 정합성을 유지하기는 쉽다. 하지만 여러 사용자가 앞선 작업이 끝날 때까지 기다려야 하므로 시스템의 처리량이 크게 떨어진다.</p>
<p>반대로 모든 작업을 아무런 제어 없이 동시에 실행하면 성능은 높아질 수 있지만 다음 문제가 발생할 수 있다.</p>
<pre><code class="language-text">아직 확정되지 않은 값을 읽음
다른 트랜잭션의 변경을 덮어씀
한 트랜잭션 안에서 같은 값을 다르게 읽음
서로 연관된 데이터가 일관되지 않은 시점으로 조회됨
업무 규칙을 위반하는 상태로 두 트랜잭션이 함께 커밋됨</code></pre>
<p>데이터베이스의 동시성 제어는 다음 두 목표를 동시에 달성하려는 기술이다.</p>
<pre><code class="language-text">정확성
→ 동시 실행 결과가 데이터 정합성을 해치지 않아야 함

동시성
→ 가능한 많은 트랜잭션을 서로 기다리지 않고 실행해야 함</code></pre>
<p>즉, 동시성 제어의 핵심은 모든 작업을 막는 것이 아니라 다음 질문에 답하는 것이다.</p>
<blockquote>
<p>어떤 작업은 동시에 허용하고, 어떤 작업은 기다리게 하며, 어떤 작업은 실패시켜야 하는가?</p>
</blockquote>
<hr />
<h1 id="1-트랜잭션이란">1. 트랜잭션이란?</h1>
<p>트랜잭션(Transaction)은 데이터베이스에서 하나의 논리적인 작업 단위를 구성하는 연산들의 집합이다.</p>
<p>예를 들어 A 계좌에서 B 계좌로 10만 원을 이체한다고 하자.</p>
<pre><code class="language-sql">BEGIN;

UPDATE accounts
SET balance = balance - 100000
WHERE account_id = 'A';

UPDATE accounts
SET balance = balance + 100000
WHERE account_id = 'B';

COMMIT;</code></pre>
<p>이 작업은 두 개의 <code>UPDATE</code>로 구성되지만 업무적으로는 하나의 계좌이체다.</p>
<p>따라서 다음과 같이 처리되어야 한다.</p>
<pre><code class="language-text">A 계좌 차감 성공 + B 계좌 입금 성공
→ 전체 성공

A 계좌 차감 성공 + B 계좌 입금 실패
→ A 계좌 차감도 취소

A 계좌 차감 실패
→ B 계좌 입금도 수행하지 않음</code></pre>
<p>트랜잭션은 여러 SQL을 단순히 묶는 문법이 아니다.</p>
<pre><code class="language-text">여러 데이터 변경을
하나의 논리적 상태 전이로 만드는 단위</code></pre>
<p>라고 이해해야 한다.</p>
<hr />
<h1 id="2-트랜잭션의-상태">2. 트랜잭션의 상태</h1>
<p>트랜잭션은 일반적으로 다음 상태를 거친다.</p>
<pre><code class="language-text">Active
→ Partially Committed
→ Committed</code></pre>
<p>오류가 발생하면 다음 흐름으로 이동할 수 있다.</p>
<pre><code class="language-text">Active
→ Failed
→ Aborted</code></pre>
<hr />
<h2 id="21-active">2.1 Active</h2>
<p>트랜잭션이 SQL을 실행하고 있는 상태다.</p>
<pre><code class="language-text">데이터 조회
데이터 변경
조건 검사
잠금 획득</code></pre>
<p>등의 작업을 수행한다.</p>
<hr />
<h2 id="22-partially-committed">2.2 Partially Committed</h2>
<p>마지막 명령은 수행했지만, 커밋 결과가 아직 안정적으로 보존되었다고 확정되지 않은 상태다.</p>
<p>트랜잭션의 논리적인 연산이 끝났더라도 로그와 변경 내용이 안정적인 저장장치에 반영되는 과정이 남아 있을 수 있다.</p>
<hr />
<h2 id="23-committed">2.3 Committed</h2>
<p>트랜잭션이 성공적으로 완료된 상태다.</p>
<p>커밋된 변경은 이후 다른 트랜잭션이 볼 수 있으며, 시스템 장애가 발생하더라도 복구할 수 있어야 한다.</p>
<hr />
<h2 id="24-failed">2.4 Failed</h2>
<p>트랜잭션을 정상적으로 계속 실행할 수 없는 상태다.</p>
<p>다음과 같은 원인으로 실패할 수 있다.</p>
<pre><code class="language-text">제약조건 위반
명령 실행 오류
애플리케이션의 명시적 취소
데드락 희생자 선택
직렬화 실패
시스템 장애</code></pre>
<hr />
<h2 id="25-aborted">2.5 Aborted</h2>
<p>트랜잭션의 변경을 취소하여 트랜잭션 시작 전 상태로 되돌린 상태다.</p>
<p>이후 트랜잭션은 다음 중 하나로 처리될 수 있다.</p>
<pre><code class="language-text">완전히 종료
다시 실행
사용자에게 오류 반환</code></pre>
<hr />
<h1 id="3-commit-rollback-savepoint">3. COMMIT, ROLLBACK, SAVEPOINT</h1>
<h2 id="31-commit">3.1 COMMIT</h2>
<p><code>COMMIT</code>은 트랜잭션의 변경을 최종 확정한다.</p>
<pre><code class="language-sql">COMMIT;</code></pre>
<p>커밋된 이후에는 해당 변경을 단순한 <code>ROLLBACK</code>으로 되돌릴 수 없다.</p>
<p>되돌리려면 반대 의미의 새로운 트랜잭션을 수행해야 한다.</p>
<hr />
<h2 id="32-rollback">3.2 ROLLBACK</h2>
<p><code>ROLLBACK</code>은 현재 트랜잭션에서 수행한 변경을 취소한다.</p>
<pre><code class="language-sql">ROLLBACK;</code></pre>
<p>트랜잭션 내부에서 여러 SQL이 실행되었더라도 전체 트랜잭션이 취소된다.</p>
<hr />
<h2 id="33-savepoint">3.3 SAVEPOINT</h2>
<p><code>SAVEPOINT</code>는 트랜잭션 내부의 중간 지점을 표시한다.</p>
<pre><code class="language-sql">BEGIN;

UPDATE orders
SET status = 'PAID'
WHERE order_id = 100;

SAVEPOINT payment_completed;

INSERT INTO delivery_requests(order_id)
VALUES (100);

ROLLBACK TO SAVEPOINT payment_completed;

COMMIT;</code></pre>
<p>전체 트랜잭션을 취소하지 않고 특정 지점 이후의 작업만 되돌릴 수 있다.</p>
<p>다만 Savepoint는 별도의 독립된 트랜잭션이 아니다.</p>
<p>최종적으로 바깥쪽 트랜잭션이 롤백되면 Savepoint 이전 작업도 모두 취소된다.</p>
<hr />
<h1 id="4-acid">4. ACID</h1>
<p>트랜잭션의 대표적인 성질은 ACID로 설명한다.</p>
<pre><code class="language-text">Atomicity
Consistency
Isolation
Durability</code></pre>
<hr />
<h2 id="41-atomicity">4.1 Atomicity</h2>
<p>Atomicity는 트랜잭션의 연산이 전부 수행되거나 전부 수행되지 않아야 한다는 성질이다.</p>
<pre><code class="language-text">All or Nothing</code></pre>
<p>계좌이체에서 출금만 성공하고 입금이 실패한 상태가 남으면 안 된다.</p>
<pre><code class="language-text">출금 + 입금
→ 모두 성공

또는

출금 + 입금
→ 모두 취소</code></pre>
<p>Atomicity는 일반적으로 Undo 정보, 로그, 버전 관리 등의 복구 메커니즘으로 구현된다.</p>
<hr />
<h2 id="42-consistency">4.2 Consistency</h2>
<p>Consistency는 트랜잭션 전후에 데이터베이스가 정의된 무결성 규칙을 만족해야 한다는 성질이다.</p>
<p>예를 들어 다음과 같은 규칙이 있다고 하자.</p>
<pre><code class="language-text">계좌 잔액은 음수가 될 수 없다.
주문의 결제 금액은 0보다 커야 한다.
외래 키는 존재하는 부모 데이터를 참조해야 한다.
동일한 좌석에는 하나의 예약만 존재해야 한다.</code></pre>
<p>정상적인 상태에서 시작한 트랜잭션은 정상적으로 완료된 뒤에도 이러한 규칙을 만족해야 한다.</p>
<p>다만 Consistency는 DBMS가 자동으로 모든 업무 규칙을 이해하고 보장한다는 뜻은 아니다.</p>
<p>다음 요소가 함께 정확해야 한다.</p>
<pre><code class="language-text">애플리케이션 로직
트랜잭션 범위
제약조건
격리수준
동시성 제어
데이터베이스 설계</code></pre>
<p>잘못 작성된 트랜잭션은 원자적으로 커밋되더라도 업무 규칙을 위반할 수 있다.</p>
<hr />
<h2 id="43-isolation">4.3 Isolation</h2>
<p>Isolation은 동시에 실행되는 트랜잭션들이 서로에게 미치는 영향을 제어하는 성질이다.</p>
<p>이상적인 목표는 다음과 같다.</p>
<blockquote>
<p>여러 트랜잭션을 동시에 실행하더라도 그 결과가 어떤 순서로 하나씩 실행한 결과와 같아야 한다.</p>
</blockquote>
<p>하지만 이러한 완전한 격리를 항상 강제하면 동시성이 낮아질 수 있다.</p>
<p>따라서 데이터베이스는 여러 격리수준을 제공하며, 시스템은 정확성과 성능 사이의 균형을 선택한다.</p>
<hr />
<h2 id="44-durability">4.4 Durability</h2>
<p>Durability는 커밋된 트랜잭션의 결과가 시스템 장애 이후에도 보존되어야 한다는 성질이다.</p>
<pre><code class="language-text">COMMIT 성공 응답
→ 이후 서버 프로세스가 종료됨
→ 전원이 차단됨
→ 시스템이 다시 시작됨
→ 커밋된 변경은 복구되어야 함</code></pre>
<p>Durability는 일반적으로 로그 선행 기록, 복구 로그, 체크포인트, 복제 등의 기술로 보장한다.</p>
<hr />
<h1 id="5-왜-트랜잭션을-동시에-실행하는가">5. 왜 트랜잭션을 동시에 실행하는가?</h1>
<p>모든 트랜잭션을 하나씩 순서대로 실행하면 동시성 문제는 대부분 사라진다.</p>
<p>하지만 다음 문제가 발생한다.</p>
<pre><code class="language-text">CPU가 디스크 I/O를 기다리는 동안 다른 작업도 대기
한 사용자의 긴 작업 때문에 모든 사용자가 대기
서버 자원을 충분히 활용하지 못함
처리량 감소
응답시간 증가</code></pre>
<p>트랜잭션은 다음 작업을 번갈아 수행한다.</p>
<pre><code class="language-text">CPU 연산
메모리 접근
디스크 또는 네트워크 I/O 대기
잠금 대기</code></pre>
<p>한 트랜잭션이 I/O를 기다리는 동안 다른 트랜잭션을 실행하면 시스템 자원을 더 효율적으로 활용할 수 있다.</p>
<p>동시 실행의 장점은 다음과 같다.</p>
<pre><code class="language-text">처리량 증가
평균 응답시간 감소
CPU와 I/O 장치 활용률 증가
다수 사용자 서비스 가능</code></pre>
<p>따라서 동시성 제어의 목표는 동시 실행을 없애는 것이 아니라 <strong>정확성을 해치지 않는 범위에서 최대한 허용하는 것</strong>이다.</p>
<hr />
<h1 id="6-트랜잭션-연산의-표기">6. 트랜잭션 연산의 표기</h1>
<p>트랜잭션 이론에서는 데이터 항목 <code>X</code>를 읽고 쓰는 연산을 다음처럼 표현한다.</p>
<pre><code class="language-text">r₁(X)
→ 트랜잭션 T₁이 X를 읽음

w₁(X)
→ 트랜잭션 T₁이 X를 기록함

c₁
→ 트랜잭션 T₁이 커밋함

a₁
→ 트랜잭션 T₁이 중단 또는 롤백됨</code></pre>
<p>예를 들어 다음 트랜잭션이 있다고 하자.</p>
<pre><code class="language-text">T₁:
r₁(X)
X = X - 100
w₁(X)</code></pre>
<p>이는 <code>T₁</code>이 X를 읽고 값을 변경한 뒤 다시 기록한다는 뜻이다.</p>
<hr />
<h1 id="7-스케줄">7. 스케줄</h1>
<p>스케줄(Schedule)은 여러 트랜잭션의 연산이 실제로 실행되는 순서를 나타낸다.</p>
<p>각 트랜잭션 내부의 연산 순서는 유지되어야 하지만, 서로 다른 트랜잭션의 연산은 섞일 수 있다.</p>
<p>예를 들어 다음 두 트랜잭션이 있다고 하자.</p>
<pre><code class="language-text">T₁:
r₁(X)
w₁(X)

T₂:
r₂(Y)
w₂(Y)</code></pre>
<p>가능한 스케줄 중 하나는 다음과 같다.</p>
<pre><code class="language-text">r₁(X)
w₁(X)
r₂(Y)
w₂(Y)</code></pre>
<p>다른 스케줄은 다음과 같다.</p>
<pre><code class="language-text">r₁(X)
r₂(Y)
w₁(X)
w₂(Y)</code></pre>
<p>두 트랜잭션의 내부 순서는 유지되지만 서로의 연산이 교차되어 있다.</p>
<hr />
<h1 id="8-직렬-스케줄과-비직렬-스케줄">8. 직렬 스케줄과 비직렬 스케줄</h1>
<h2 id="81-직렬-스케줄">8.1 직렬 스케줄</h2>
<p>직렬 스케줄(Serial Schedule)은 하나의 트랜잭션이 모두 끝난 후 다음 트랜잭션을 실행하는 방식이다.</p>
<pre><code class="language-text">T₁ 전체 실행
→ T₂ 전체 실행</code></pre>
<p>예:</p>
<pre><code class="language-text">r₁(X)
w₁(X)
c₁
r₂(X)
w₂(X)
c₂</code></pre>
<p>또는 반대 순서도 가능하다.</p>
<pre><code class="language-text">r₂(X)
w₂(X)
c₂
r₁(X)
w₁(X)
c₁</code></pre>
<p>트랜잭션이 각각 정확하게 작성되었다면 직렬 실행은 일반적으로 데이터 정합성을 유지한다.</p>
<p>그러나 동시성이 낮다.</p>
<hr />
<h2 id="82-비직렬-스케줄">8.2 비직렬 스케줄</h2>
<p>비직렬 스케줄(Non-serial Schedule)은 여러 트랜잭션의 연산이 서로 섞여 실행되는 방식이다.</p>
<pre><code class="language-text">r₁(X)
r₂(X)
w₁(X)
w₂(X)</code></pre>
<p>동시성을 높일 수 있지만, 잘못된 순서로 실행되면 데이터 이상이 발생할 수 있다.</p>
<p>중요한 것은 비직렬 스케줄 자체가 잘못된 것이 아니라는 점이다.</p>
<pre><code class="language-text">비직렬 스케줄
→ 결과가 직렬 실행과 동등함
→ 안전할 수 있음

비직렬 스케줄
→ 어떤 직렬 실행 결과와도 동등하지 않음
→ 데이터 이상 가능</code></pre>
<p>따라서 동시성 제어의 핵심 기준은 단순히 연산이 섞였는지가 아니라 <strong>직렬 가능성</strong>이다.</p>
<hr />
<h1 id="9-직렬-가능성">9. 직렬 가능성</h1>
<p>직렬 가능성(Serializability)은 비직렬 스케줄의 결과가 어떤 직렬 스케줄의 결과와 동등한 성질이다.</p>
<p>예를 들어 비직렬로 실행했지만 결과가 다음 직렬 순서와 같다면 안전하다고 볼 수 있다.</p>
<pre><code class="language-text">T₁ → T₂</code></pre>
<p>또는:</p>
<pre><code class="language-text">T₂ → T₁</code></pre>
<p>직렬 가능성은 동시성 제어 이론에서 가장 중요한 정확성 기준이다.</p>
<pre><code class="language-text">실제로는 동시에 실행
+
결과는 순차적으로 실행한 것과 동일</code></pre>
<p>을 목표로 한다.</p>
<hr />
<h1 id="10-충돌-연산">10. 충돌 연산</h1>
<p>서로 다른 두 트랜잭션의 연산이 다음 조건을 만족하면 충돌한다고 한다.</p>
<pre><code class="language-text">같은 데이터 항목에 접근
+
둘 중 하나 이상이 쓰기 연산</code></pre>
<p>다음 연산들을 비교해보자.</p>
<hr />
<h2 id="101-read-read">10.1 Read-Read</h2>
<pre><code class="language-text">r₁(X)
r₂(X)</code></pre>
<p>두 트랜잭션 모두 X를 읽기만 한다.</p>
<p>실행 순서를 바꾸어도 결과가 달라지지 않는다.</p>
<pre><code class="language-text">충돌하지 않음</code></pre>
<hr />
<h2 id="102-read-write">10.2 Read-Write</h2>
<pre><code class="language-text">r₁(X)
w₂(X)</code></pre>
<p>T₁이 X를 읽은 뒤 T₂가 X를 변경한다.</p>
<p>순서를 바꾸면 T₁이 읽는 값이 달라질 수 있다.</p>
<pre><code class="language-text">충돌함</code></pre>
<hr />
<h2 id="103-write-read">10.3 Write-Read</h2>
<pre><code class="language-text">w₁(X)
r₂(X)</code></pre>
<p>T₁이 X를 변경한 뒤 T₂가 읽는다.</p>
<p>순서를 바꾸면 T₂가 읽는 값이 달라질 수 있다.</p>
<pre><code class="language-text">충돌함</code></pre>
<hr />
<h2 id="104-write-write">10.4 Write-Write</h2>
<pre><code class="language-text">w₁(X)
w₂(X)</code></pre>
<p>두 트랜잭션이 모두 X를 변경한다.</p>
<p>순서를 바꾸면 최종 값이 달라질 수 있다.</p>
<pre><code class="language-text">충돌함</code></pre>
<hr />
<h1 id="11-충돌-직렬-가능성">11. 충돌 직렬 가능성</h1>
<p>스케줄에서 서로 충돌하지 않는 연산들의 순서를 교환하여 어떤 직렬 스케줄로 만들 수 있다면, 해당 스케줄은 충돌 직렬 가능하다고 한다.</p>
<p>예를 들어 다음 스케줄을 보자.</p>
<pre><code class="language-text">r₁(X)
w₁(X)
r₂(Y)
w₂(Y)</code></pre>
<p>T₁은 X에만 접근하고 T₂는 Y에만 접근하므로 연산들이 충돌하지 않는다.</p>
<p>따라서 순서를 바꾸어 다음 직렬 스케줄과 동등하게 만들 수 있다.</p>
<pre><code class="language-text">T₁ → T₂</code></pre>
<p>반면 서로 같은 데이터를 읽고 쓰면 순서 제약이 생긴다.</p>
<hr />
<h1 id="12-선행-그래프">12. 선행 그래프</h1>
<p>충돌 직렬 가능성은 선행 그래프(Precedence Graph), 또는 직렬화 그래프로 판단할 수 있다.</p>
<p>그래프는 다음과 같이 만든다.</p>
<pre><code class="language-text">각 트랜잭션
→ 하나의 정점

Tᵢ의 연산이 Tⱼ의 충돌 연산보다 먼저 실행됨
→ Tᵢ에서 Tⱼ로 간선 생성</code></pre>
<p>예를 들어 다음 순서가 있다고 하자.</p>
<pre><code class="language-text">w₁(X)
r₂(X)</code></pre>
<p>T₁의 쓰기 이후 T₂가 같은 X를 읽으므로 다음 간선이 생긴다.</p>
<pre><code class="language-text">T₁ → T₂</code></pre>
<p>다른 데이터에서 반대 순서의 충돌이 있다면:</p>
<pre><code class="language-text">w₂(Y)
r₁(Y)</code></pre>
<p>다음 간선도 생긴다.</p>
<pre><code class="language-text">T₂ → T₁</code></pre>
<p>전체 그래프는 다음과 같다.</p>
<pre><code class="language-text">T₁ → T₂
↑     ↓
└─────┘</code></pre>
<p>사이클이 존재한다.</p>
<p>충돌 직렬 가능성의 판정 기준은 다음과 같다.</p>
<pre><code class="language-text">선행 그래프에 사이클이 없음
→ 충돌 직렬 가능

선행 그래프에 사이클이 있음
→ 충돌 직렬 가능하지 않음</code></pre>
<p>사이클이 없는 경우 위상 정렬 결과가 해당 스케줄과 동등한 직렬 실행 순서를 나타낸다.</p>
<hr />
<h1 id="13-뷰-직렬-가능성">13. 뷰 직렬 가능성</h1>
<p>뷰 직렬 가능성(View Serializability)은 충돌 직렬 가능성보다 더 일반적인 개념이다.</p>
<p>두 스케줄이 다음 관계를 동일하게 유지하면 뷰 동등하다고 볼 수 있다.</p>
<pre><code class="language-text">각 읽기 연산이 어떤 트랜잭션의 값을 읽는가?
어떤 트랜잭션이 각 데이터의 최종 값을 기록하는가?
초기값을 읽는 관계가 같은가?</code></pre>
<p>충돌 직렬 가능한 스케줄은 모두 뷰 직렬 가능하다.</p>
<pre><code class="language-text">충돌 직렬 가능
⊂
뷰 직렬 가능</code></pre>
<p>하지만 뷰 직렬 가능성을 판정하는 것은 훨씬 어렵다.</p>
<p>실제 동시성 제어 이론과 구현에서는 충돌 직렬 가능성을 중심으로 설명하는 경우가 많다.</p>
<hr />
<h1 id="14-복구-가능성">14. 복구 가능성</h1>
<p>직렬 가능성은 트랜잭션 간 실행 결과의 논리적 정확성을 다룬다.</p>
<p>하지만 트랜잭션이 실패했을 때 안전하게 복구할 수 있는지도 별도로 고려해야 한다.</p>
<hr />
<h2 id="141-recoverable-schedule">14.1 Recoverable Schedule</h2>
<p>T₂가 T₁이 기록한 값을 읽었다고 하자.</p>
<pre><code class="language-text">w₁(X)
r₂(X)</code></pre>
<p>이 경우 T₂는 T₁의 결과에 의존한다.</p>
<p>복구 가능한 스케줄에서는 T₂가 T₁보다 먼저 커밋해서는 안 된다.</p>
<pre><code class="language-text">T₂가 T₁의 값을 읽음
→ T₁이 먼저 커밋
→ 그 후 T₂ 커밋 가능</code></pre>
<p>즉:</p>
<pre><code class="language-text">T₂가 T₁의 값을 읽었다면
commit(T₁) &lt; commit(T₂)</code></pre>
<p>여야 한다.</p>
<p>만약 T₂가 먼저 커밋한 뒤 T₁이 롤백된다면, 이미 확정된 T₂는 존재하지 않아야 할 값에 의존한 셈이 된다.</p>
<hr />
<h2 id="142-cascading-rollback">14.2 Cascading Rollback</h2>
<p>다음과 같은 의존 관계가 있다고 하자.</p>
<pre><code class="language-text">T₁의 미커밋 값
→ T₂가 읽음

T₂의 미커밋 값
→ T₃가 읽음</code></pre>
<p>이후 T₁이 롤백되면:</p>
<pre><code class="language-text">T₁ 롤백
→ T₂도 롤백
→ T₃도 롤백</code></pre>
<p>해야 할 수 있다.</p>
<p>이를 연쇄 롤백(Cascading Rollback)이라고 한다.</p>
<hr />
<h2 id="143-cascadeless-schedule">14.3 Cascadeless Schedule</h2>
<p>연쇄 롤백을 방지하려면 다른 트랜잭션이 커밋한 값만 읽도록 해야 한다.</p>
<pre><code class="language-text">T₂가 T₁의 값을 읽으려면
→ T₁이 먼저 커밋되어 있어야 함</code></pre>
<p>이러한 스케줄을 Cascadeless Schedule이라고 한다.</p>
<hr />
<h2 id="144-strict-schedule">14.4 Strict Schedule</h2>
<p>Strict Schedule에서는 트랜잭션이 기록한 데이터 항목을 해당 트랜잭션이 종료할 때까지 다른 트랜잭션이 읽거나 기록하지 못한다.</p>
<pre><code class="language-text">T₁이 X 기록
→ T₁이 COMMIT 또는 ROLLBACK하기 전까지
→ 다른 트랜잭션은 X를 읽거나 쓸 수 없음</code></pre>
<p>Strict Schedule은 다음 문제를 방지한다.</p>
<pre><code class="language-text">Dirty Read
Dirty Write
Cascading Rollback</code></pre>
<p>일반적으로 다음 포함 관계가 성립한다.</p>
<pre><code class="language-text">Strict
→ Cascadeless
→ Recoverable</code></pre>
<p>Strict한 실행은 복구를 단순하게 만들기 때문에 실제 시스템에서 중요한 성질이다.</p>
<hr />
<h1 id="15-동시-실행에서-발생하는-이상-현상">15. 동시 실행에서 발생하는 이상 현상</h1>
<p>트랜잭션이 적절히 격리되지 않으면 여러 형태의 데이터 이상이 발생할 수 있다.</p>
<p>SQL 표준의 대표 현상 외에도 실제 애플리케이션에서는 Lost Update, Read Skew, Write Skew 등을 함께 이해해야 한다.</p>
<hr />
<h1 id="16-dirty-write">16. Dirty Write</h1>
<p>Dirty Write는 한 트랜잭션이 아직 커밋하지 않은 값을 다른 트랜잭션이 덮어쓰는 현상이다.</p>
<p>초기값:</p>
<pre><code class="language-text">X = 100</code></pre>
<p>실행:</p>
<pre><code class="language-text">T₁: X = 200으로 변경
T₂: T₁이 끝나기 전에 X = 300으로 변경
T₁: ROLLBACK</code></pre>
<p>이제 복구 과정에서 X를 어떤 값으로 되돌려야 하는지 문제가 생긴다.</p>
<pre><code class="language-text">T₁ 이전 값인 100?
T₂가 기록한 300?</code></pre>
<p>Dirty Write는 복구와 정합성을 심각하게 훼손하므로 대부분의 트랜잭션 시스템이 가장 기본적으로 방지한다.</p>
<hr />
<h1 id="17-dirty-read">17. Dirty Read</h1>
<p>Dirty Read는 다른 트랜잭션이 아직 커밋하지 않은 값을 읽는 현상이다.</p>
<p>초기 상태:</p>
<pre><code class="language-text">X = 100</code></pre>
<p>실행:</p>
<pre><code class="language-text">T₁: X를 200으로 변경
T₂: X를 읽음 → 200
T₁: ROLLBACK</code></pre>
<p>T₂는 최종적으로 존재하지 않게 된 값을 읽었다.</p>
<pre><code class="language-text">T₂가 읽은 값: 200
실제 확정된 값: 100</code></pre>
<p>이후 T₂가 읽은 값을 기준으로 다른 작업까지 수행했다면 연쇄적인 오류가 발생할 수 있다.</p>
<hr />
<h1 id="18-non-repeatable-read">18. Non-Repeatable Read</h1>
<p>Non-Repeatable Read는 한 트랜잭션이 동일한 행을 두 번 읽었는데 값이 달라지는 현상이다.</p>
<p>초기 상태:</p>
<pre><code class="language-text">employee_id = 1
salary = 5000</code></pre>
<p>실행:</p>
<pre><code class="language-text">T₁: salary 조회 → 5000

T₂: salary를 6000으로 변경
T₂: COMMIT

T₁: salary 다시 조회 → 6000</code></pre>
<p>T₁ 내부에서 동일한 행의 값이 달라졌다.</p>
<pre><code class="language-text">첫 번째 읽기: 5000
두 번째 읽기: 6000</code></pre>
<p>이를 Fuzzy Read라고 부르기도 한다.</p>
<hr />
<h1 id="19-phantom-read">19. Phantom Read</h1>
<p>Phantom Read는 같은 조건으로 범위 조회를 반복했을 때 조건에 포함되는 행의 집합이 달라지는 현상이다.</p>
<pre><code class="language-text">T₁:
salary &gt;= 5000인 직원 조회
→ 10명</code></pre>
<p>그 사이 다른 트랜잭션이 새로운 행을 추가한다.</p>
<pre><code class="language-text">T₂:
salary = 7000인 직원 INSERT
COMMIT</code></pre>
<p>T₁이 동일한 조건을 다시 실행한다.</p>
<pre><code class="language-text">T₁:
salary &gt;= 5000인 직원 조회
→ 11명</code></pre>
<p>Non-Repeatable Read가 기존 행의 값 변경에 초점을 둔다면 Phantom Read는 <strong>조건을 만족하는 행 집합의 변화</strong>에 초점을 둔다.</p>
<pre><code class="language-text">Non-Repeatable Read
→ 같은 행의 값이 변함

Phantom Read
→ 같은 조건의 결과 집합이 변함</code></pre>
<p>Phantom을 막으려면 현재 존재하는 행만 잠그는 것으로 충분하지 않을 수 있다.</p>
<p>아직 존재하지 않는 행이 조건 범위에 삽입되는 것도 막아야 하므로 Predicate Lock이나 Key-Range Lock과 같은 범위 보호가 필요할 수 있다.</p>
<hr />
<h1 id="20-lost-update">20. Lost Update</h1>
<p>Lost Update는 두 트랜잭션이 같은 값을 읽고 각각 수정한 뒤, 한쪽 변경이 다른 변경을 덮어쓰는 현상이다.</p>
<p>초기값:</p>
<pre><code class="language-text">X = 100</code></pre>
<p>실행:</p>
<pre><code class="language-text">T₁: X를 읽음 → 100
T₂: X를 읽음 → 100

T₁: X에 10을 더함 → 110
T₂: X에 20을 더함 → 120

T₁: X = 110 기록
T₂: X = 120 기록</code></pre>
<p>최종값:</p>
<pre><code class="language-text">X = 120</code></pre>
<p>정상적으로 두 변경이 모두 반영되었다면 다음 값이 되어야 한다.</p>
<pre><code class="language-text">X = 130</code></pre>
<p>하지만 T₁의 <code>+10</code> 변경이 사라졌다.</p>
<hr />
<h2 id="201-read-modify-write-패턴">20.1 Read-Modify-Write 패턴</h2>
<p>Lost Update는 다음 패턴에서 자주 발생한다.</p>
<pre><code class="language-text">1. 현재 값 읽기
2. 애플리케이션에서 계산
3. 계산 결과를 다시 저장</code></pre>
<pre><code class="language-sql">SELECT quantity
FROM products
WHERE product_id = 1;

-- 애플리케이션에서 quantity - 1 계산

UPDATE products
SET quantity = 계산된_값
WHERE product_id = 1;</code></pre>
<p>동시에 여러 트랜잭션이 같은 값을 읽으면 갱신이 유실될 수 있다.</p>
<hr />
<h2 id="202-원자적-갱신">20.2 원자적 갱신</h2>
<p>가능하면 계산을 데이터베이스 내부의 하나의 연산으로 표현하는 것이 안전하다.</p>
<pre><code class="language-sql">UPDATE products
SET quantity = quantity - 1
WHERE product_id = 1;</code></pre>
<p>이 경우 읽기와 쓰기를 분리하지 않고 하나의 갱신 연산으로 처리할 수 있다.</p>
<p>다만 업무 조건까지 함께 검사해야 한다면 다음과 같이 작성할 수 있다.</p>
<pre><code class="language-sql">UPDATE products
SET quantity = quantity - 1
WHERE product_id = 1
  AND quantity &gt; 0;</code></pre>
<p>영향받은 행 수를 확인하여 재고 부족 여부를 판단한다.</p>
<hr />
<h1 id="21-dirty-read와-lost-update의-차이">21. Dirty Read와 Lost Update의 차이</h1>
<p>두 현상은 서로 다르다.</p>
<pre><code class="language-text">Dirty Read
→ 커밋되지 않은 값을 읽음

Lost Update
→ 두 변경 중 하나가 덮어써져 사라짐</code></pre>
<p>Lost Update는 Dirty Read 없이도 발생할 수 있다.</p>
<p>두 트랜잭션이 모두 정상적으로 커밋된 값 100을 읽고 각각 결과를 저장해도 한쪽 변경이 유실될 수 있기 때문이다.</p>
<hr />
<h1 id="22-read-skew">22. Read Skew</h1>
<p>Read Skew는 하나의 트랜잭션이 서로 관련된 여러 데이터를 서로 다른 시점의 상태로 읽는 현상이다.</p>
<p>다음 불변식이 있다고 하자.</p>
<pre><code class="language-text">A 계좌 잔액 + B 계좌 잔액 = 100만 원</code></pre>
<p>초기 상태:</p>
<pre><code class="language-text">A = 500,000
B = 500,000</code></pre>
<p>T₂가 A에서 B로 100,000원을 이체한다.</p>
<pre><code class="language-text">A: 500,000 → 400,000
B: 500,000 → 600,000</code></pre>
<p>T₁의 조회가 다음처럼 실행될 수 있다.</p>
<pre><code class="language-text">T₁: A 조회 → 500,000

T₂: 이체 수행 후 COMMIT

T₁: B 조회 → 600,000</code></pre>
<p>T₁이 계산한 합계:</p>
<pre><code class="language-text">500,000 + 600,000 = 1,100,000</code></pre>
<p>실제로 어느 시점에도 총액이 1,100,000원이었던 적은 없다.</p>
<p>T₁은 서로 다른 시점의 데이터를 조합해 일관되지 않은 상태를 관찰했다.</p>
<p>이를 Inconsistent Analysis라고도 한다.</p>
<hr />
<h1 id="23-write-skew">23. Write Skew</h1>
<p>Write Skew는 서로 다른 행을 수정하는 두 트랜잭션이 같은 조건을 읽고 각각의 변경을 커밋하여 전체 업무 규칙을 위반하는 현상이다.</p>
<p>Lost Update와 달리 두 트랜잭션이 같은 행을 덮어쓰지 않을 수도 있다.</p>
<hr />
<h2 id="231-당직-의사-예시">23.1 당직 의사 예시</h2>
<p>다음 규칙이 있다고 하자.</p>
<pre><code class="language-text">항상 최소 한 명의 의사가 당직 상태여야 한다.</code></pre>
<p>초기 상태:</p>
<pre><code class="language-text">의사 A: 당직
의사 B: 당직</code></pre>
<p>각 의사는 자신이 퇴근해도 다른 의사가 남아 있다면 당직을 해제할 수 있다.</p>
<p>T₁과 T₂가 동시에 실행된다.</p>
<pre><code class="language-text">T₁:
현재 당직 의사 수 조회 → 2명
의사 A를 당직 해제

T₂:
현재 당직 의사 수 조회 → 2명
의사 B를 당직 해제</code></pre>
<p>각 트랜잭션은 자신이 읽은 시점에서는 규칙을 만족한다고 판단한다.</p>
<pre><code class="language-text">T₁ 관점: B가 남아 있음
T₂ 관점: A가 남아 있음</code></pre>
<p>두 트랜잭션이 모두 커밋하면:</p>
<pre><code class="language-text">의사 A: 당직 아님
의사 B: 당직 아님</code></pre>
<p>업무 규칙이 깨진다.</p>
<p>두 트랜잭션은 서로 다른 행을 변경했으므로 단순한 동일 행 Write-Write 충돌 검사만으로는 막히지 않을 수 있다.</p>
<hr />
<h2 id="232-lost-update와-write-skew-비교">23.2 Lost Update와 Write Skew 비교</h2>
<pre><code class="language-text">Lost Update
→ 같은 데이터 항목을 갱신
→ 한쪽 변경이 덮어써짐

Write Skew
→ 서로 다른 데이터 항목을 갱신할 수 있음
→ 읽은 조건 사이의 논리적 제약이 깨짐</code></pre>
<p>Write Skew는 Snapshot Isolation과 Serializable의 차이를 설명할 때 매우 중요한 현상이다.</p>
<hr />
<h1 id="24-serialization-anomaly">24. Serialization Anomaly</h1>
<p>Serialization Anomaly는 동시 실행 결과를 어떤 직렬 실행 순서로도 설명할 수 없는 현상을 포괄한다.</p>
<p>Dirty Read나 Non-Repeatable Read 같은 개별 현상이 나타나지 않더라도 여러 트랜잭션의 읽기·쓰기 의존 관계가 순환하면 직렬 가능하지 않을 수 있다.</p>
<pre><code class="language-text">T₁은 T₂보다 먼저 실행된 것처럼 보이고
T₂는 T₃보다 먼저 실행된 것처럼 보이며
T₃는 다시 T₁보다 먼저 실행된 것처럼 보임</code></pre>
<p>의존 관계:</p>
<pre><code class="language-text">T₁ → T₂ → T₃ → T₁</code></pre>
<p>이러한 순환은 어떤 단일한 직렬 순서로도 표현할 수 없다.</p>
<hr />
<h1 id="25-sql-격리수준">25. SQL 격리수준</h1>
<p>SQL 표준은 대표적으로 다음 네 가지 격리수준을 정의한다.</p>
<pre><code class="language-text">READ UNCOMMITTED
READ COMMITTED
REPEATABLE READ
SERIALIZABLE</code></pre>
<p>격리수준은 트랜잭션이 동시에 실행될 때 어떤 현상을 허용할지를 나타낸다.</p>
<p>다만 중요한 주의점이 있다.</p>
<blockquote>
<p>격리수준의 이름이 같더라도 실제 구현과 보장 범위는 DBMS마다 다를 수 있다.</p>
</blockquote>
<p>SQL 표준의 현상 기반 정의와 실제 DBMS의 Lock, MVCC, Snapshot 구현은 반드시 구분해서 이해해야 한다.</p>
<hr />

<p>따라서 격리수준을 단순 암기표로만 이해하면 안 된다.</p>
<hr />
<h1 id="27-read-uncommitted">27. Read Uncommitted</h1>
<p>Read Uncommitted는 다른 트랜잭션이 아직 커밋하지 않은 변경을 읽을 수 있는 가장 낮은 격리수준이다.</p>
<pre><code class="language-text">T₁: X를 100 → 200으로 변경
T₂: X를 읽음 → 200
T₁: ROLLBACK</code></pre>
<p>T₂는 존재하지 않게 된 값을 읽는다.</p>
<p>허용될 수 있는 현상:</p>
<pre><code class="language-text">Dirty Read
Non-Repeatable Read
Phantom Read
Read Skew
Lost Update
기타 직렬화 이상</code></pre>
<p>Dirty Read는 잘못된 값을 기반으로 후속 작업을 수행하게 할 수 있고 연쇄 롤백 문제를 발생시킬 수 있다.</p>
<p>따라서 일반적인 업무 트랜잭션에서는 거의 사용하지 않는다.</p>
<p>일부 DBMS는 이 격리수준을 지원하지 않거나 내부적으로 더 높은 수준처럼 처리하기도 한다.</p>
<hr />
<h1 id="28-read-committed">28. Read Committed</h1>
<p>Read Committed는 커밋된 데이터만 읽을 수 있도록 보장한다.</p>
<pre><code class="language-text">다른 트랜잭션의 미커밋 변경
→ 읽지 않음</code></pre>
<p>따라서 Dirty Read는 방지한다.</p>
<p>하지만 하나의 트랜잭션 안에서도 각 명령이 서로 다른 커밋 상태를 볼 수 있다.</p>
<pre><code class="language-text">T₁ 첫 번째 SELECT
→ 해당 시점까지 커밋된 데이터

다른 트랜잭션 COMMIT

T₁ 두 번째 SELECT
→ 새로 커밋된 데이터까지 포함 가능</code></pre>
<p>따라서 다음 현상이 발생할 수 있다.</p>
<pre><code class="language-text">Non-Repeatable Read
Phantom Read
Read Skew
Lost Update 가능성
기타 직렬화 이상</code></pre>
<p>Read Committed는 비교적 높은 동시성을 제공하기 때문에 많은 시스템의 기본 격리수준으로 사용된다.</p>
<p>하지만 여러 SQL이 동일한 데이터 상태를 전제로 해야 하는 업무에서는 추가적인 동시성 제어가 필요하다.</p>
<hr />
<h1 id="29-repeatable-read">29. Repeatable Read</h1>
<p>Repeatable Read는 하나의 트랜잭션 안에서 이미 읽은 행을 다시 읽었을 때 같은 값을 유지하는 것을 목표로 한다.</p>
<pre><code class="language-text">첫 번째 읽기: X = 100
다른 트랜잭션이 X = 200으로 변경 후 커밋
두 번째 읽기: 여전히 X = 100</code></pre>
<p>따라서 다음 현상을 방지한다.</p>
<pre><code class="language-text">Dirty Read
Non-Repeatable Read</code></pre>
<p>전통적인 SQL 표준 정의에서는 Phantom Read는 발생할 수 있다.</p>
<pre><code class="language-text">기존 행의 값은 반복 가능
하지만
검색 조건에 새로 포함되는 행은 나타날 수 있음</code></pre>
<p>다만 실제 DBMS가 Repeatable Read를 Snapshot Isolation 형태로 구현한다면 Phantom도 보이지 않을 수 있다.</p>
<p>그러나 Phantom이 보이지 않는다고 해서 반드시 Serializable인 것은 아니다.</p>
<pre><code class="language-text">같은 스냅샷 유지
≠
직렬 가능성 완전 보장</code></pre>
<p>Snapshot 기반 Repeatable Read에서는 Write Skew가 발생할 수 있다.</p>
<hr />
<h1 id="30-serializable">30. Serializable</h1>
<p>Serializable은 동시에 실행된 트랜잭션의 결과가 어떤 직렬 실행 결과와 동일하도록 보장하는 가장 강한 격리수준이다.</p>
<pre><code class="language-text">실제로는 동시 실행
하지만
결과는 T₁ → T₂ 또는 T₂ → T₁과 같은 직렬 순서로 설명 가능</code></pre>
<p>Serializable은 다음을 목표로 한다.</p>
<pre><code class="language-text">Dirty Read 방지
Non-Repeatable Read 방지
Phantom Read 방지
Lost Update 방지
Write Skew 방지
Serialization Anomaly 방지</code></pre>
<p>하지만 Serializable이 모든 트랜잭션을 실제로 하나씩 실행한다는 뜻은 아니다.</p>
<p>DBMS는 다음 방법 중 하나를 사용할 수 있다.</p>
<pre><code class="language-text">Strict Two-Phase Locking
Predicate 또는 Key-Range Locking
Serializable Snapshot Isolation
기타 직렬 가능성 보장 알고리즘</code></pre>
<p>충돌하는 트랜잭션을 기다리게 할 수도 있고, 직렬 가능성이 깨질 위험이 있으면 트랜잭션 하나를 실패시킬 수도 있다.</p>
<p>따라서 Serializable에서는 다음 상황을 애플리케이션이 고려해야 한다.</p>
<pre><code class="language-text">잠금 대기 증가
데드락 가능성
직렬화 실패
트랜잭션 재시도
동시성 감소</code></pre>
<hr />
<h1 id="31-격리수준은-강할수록-항상-좋은가">31. 격리수준은 강할수록 항상 좋은가?</h1>
<p>격리수준을 높이면 데이터 이상 가능성은 줄어들지만 비용이 발생할 수 있다.</p>
<pre><code class="language-text">잠금 범위 증가
잠금 유지시간 증가
대기 증가
충돌 증가
트랜잭션 실패 증가
처리량 감소 가능</code></pre>
<p>반대로 낮은 격리수준은 동시성을 높일 수 있지만 애플리케이션이 직접 처리해야 하는 문제가 늘어난다.</p>
<pre><code class="language-text">재검증
버전 검사
명시적 잠금
원자적 UPDATE
제약조건
재시도</code></pre>
<p>따라서 격리수준은 다음 기준으로 선택해야 한다.</p>
<pre><code class="language-text">업무 규칙의 중요도
동일 데이터에 대한 동시 접근 빈도
트랜잭션 길이
읽기 중심인지 쓰기 중심인지
충돌 발생 확률
재시도 가능 여부
허용 가능한 응답시간</code></pre>
<hr />
<h1 id="32-동시성-제어-방식의-큰-분류">32. 동시성 제어 방식의 큰 분류</h1>
<p>데이터베이스의 동시성 제어 방식은 크게 다음처럼 나눌 수 있다.</p>
<pre><code class="language-text">Lock-Based Concurrency Control
→ 잠금을 이용해 충돌을 사전에 제어

Timestamp-Based Concurrency Control
→ 트랜잭션 순서를 타임스탬프로 결정

Optimistic Concurrency Control
→ 일단 실행한 뒤 커밋 전에 충돌 검증

Multi-Version Concurrency Control
→ 여러 버전을 유지하여 읽기와 쓰기 충돌 감소</code></pre>
<p>이 방식들은 완전히 배타적인 것이 아니다.</p>
<p>실제 DBMS는 여러 방법을 조합할 수 있다.</p>
<pre><code class="language-text">MVCC + 행 잠금
MVCC + Timestamp
Snapshot + Serializable 검증
낙관적 검증 + 버전 컬럼</code></pre>
<hr />
<h1 id="33-lock-based-concurrency-control">33. Lock-Based Concurrency Control</h1>
<p>잠금 기반 동시성 제어는 트랜잭션이 데이터에 접근하기 전에 필요한 잠금을 획득하도록 한다.</p>
<pre><code class="language-text">읽으려면 읽기 잠금
쓰려면 쓰기 잠금</code></pre>
<p>충돌하는 잠금을 다른 트랜잭션이 이미 가지고 있다면 다음 중 하나가 발생한다.</p>
<pre><code class="language-text">대기
즉시 실패
다른 트랜잭션 중단
타임아웃</code></pre>
<hr />
<h1 id="34-shared-lock과-exclusive-lock">34. Shared Lock과 Exclusive Lock</h1>
<p>가장 기본적인 잠금 모드는 Shared Lock과 Exclusive Lock이다.</p>
<hr />
<h2 id="341-shared-lock">34.1 Shared Lock</h2>
<p>Shared Lock은 데이터를 읽기 위해 획득하는 잠금이다.</p>
<pre><code class="language-text">S Lock
Read Lock
공유 잠금</code></pre>
<p>여러 트랜잭션이 같은 데이터에 동시에 Shared Lock을 획득할 수 있다.</p>
<pre><code class="language-text">T₁: S(X)
T₂: S(X)
→ 가능</code></pre>
<p>읽기끼리는 데이터를 변경하지 않으므로 서로 충돌하지 않는다.</p>
<hr />
<h2 id="342-exclusive-lock">34.2 Exclusive Lock</h2>
<p>Exclusive Lock은 데이터를 변경하기 위해 획득하는 잠금이다.</p>
<pre><code class="language-text">X Lock
Write Lock
배타 잠금</code></pre>
<p>하나의 트랜잭션이 X Lock을 보유하면 다른 트랜잭션은 동일한 데이터에 S Lock이나 X Lock을 획득할 수 없다.</p>
<pre><code class="language-text">T₁: X(X)
T₂: S(X) → 대기
T₃: X(X) → 대기</code></pre>
<hr />

<h1 id="35-잠금의-단위">35. 잠금의 단위</h1>
<p>잠금은 여러 수준에 적용할 수 있다.</p>
<pre><code class="language-text">데이터베이스
테이블
페이지
행
키 범위
논리적 조건</code></pre>
<hr />
<h2 id="351-큰-단위-잠금">35.1 큰 단위 잠금</h2>
<p>예를 들어 테이블 전체를 잠그면 관리가 단순하다.</p>
<pre><code class="language-text">잠금 개수 적음
잠금 관리 비용 낮음</code></pre>
<p>하지만 서로 다른 행에 접근하는 트랜잭션도 기다려야 한다.</p>
<pre><code class="language-text">동시성 낮음
불필요한 충돌 증가</code></pre>
<hr />
<h2 id="352-작은-단위-잠금">35.2 작은 단위 잠금</h2>
<p>행 단위 잠금은 서로 다른 행을 처리하는 트랜잭션이 동시에 실행될 수 있다.</p>
<pre><code class="language-text">동시성 높음</code></pre>
<p>하지만 다음 비용이 증가한다.</p>
<pre><code class="language-text">잠금 개수 증가
잠금 테이블 메모리 사용 증가
잠금 관리 비용 증가
데드락 관계 복잡</code></pre>
<p>잠금 단위는 다음 트레이드오프를 가진다.</p>
<pre><code class="language-text">큰 잠금
→ 관리 비용 낮음
→ 동시성 낮음

작은 잠금
→ 관리 비용 높음
→ 동시성 높음</code></pre>
<hr />
<h1 id="36-다중-단위-잠금과-의도-잠금">36. 다중 단위 잠금과 의도 잠금</h1>
<p>데이터베이스는 테이블과 행처럼 여러 계층의 잠금을 함께 관리할 수 있다.</p>
<pre><code class="language-text">Database
└── Table
    └── Page
        └── Row</code></pre>
<p>한 트랜잭션이 특정 행에 X Lock을 가지고 있는데 다른 트랜잭션이 테이블 전체에 S Lock을 요청한다면 충돌 여부를 빠르게 판단해야 한다.</p>
<p>모든 행의 잠금을 하나씩 확인하면 비효율적이다.</p>
<p>이를 위해 의도 잠금(Intention Lock)을 사용한다.</p>
<p>대표적인 잠금은 다음과 같다.</p>
<pre><code class="language-text">IS
→ Intention Shared
→ 하위 단위에 S Lock을 획득할 의도

IX
→ Intention Exclusive
→ 하위 단위에 X Lock을 획득할 의도

SIX
→ 현재 단위에는 S Lock
→ 하위 단위에는 X Lock을 획득할 의도</code></pre>
<p>예를 들어 특정 행을 수정하려면 다음과 같은 계층이 될 수 있다.</p>
<pre><code class="language-text">테이블에 IX
→ 특정 행에 X</code></pre>
<p>의도 잠금은 실제 데이터를 직접 읽거나 쓰는 잠금이 아니라 상위 계층에 하위 잠금의 존재를 알리는 메타 잠금이다.</p>
<hr />
<h1 id="37-잠금-변환">37. 잠금 변환</h1>
<p>트랜잭션이 처음에는 데이터를 읽기만 하다가 이후 수정할 수 있다.</p>
<p>이 경우 다음 잠금 변환이 필요하다.</p>
<pre><code class="language-text">S Lock
→ X Lock</code></pre>
<p>이를 Lock Upgrade라고 한다.</p>
<p>반대로 X Lock을 S Lock으로 낮추는 것을 Lock Downgrade라고 한다.</p>
<p>두 트랜잭션이 동시에 S Lock을 획득한 뒤 모두 X Lock으로 승격하려고 하면 서로를 기다릴 수 있다.</p>
<pre><code class="language-text">T₁: S(X)
T₂: S(X)

T₁: X(X)로 승격 요청 → T₂의 S 때문에 대기
T₂: X(X)로 승격 요청 → T₁의 S 때문에 대기</code></pre>
<p>데드락이 발생할 수 있다.</p>
<p>이러한 문제를 줄이기 위해 일부 시스템은 갱신 의도를 나타내는 별도 잠금 모드를 사용하기도 한다.</p>
<hr />
<h1 id="38-two-phase-locking">38. Two-Phase Locking</h1>
<p>Two-Phase Locking, 2PL은 충돌 직렬 가능성을 보장하기 위한 대표적인 잠금 규약이다.</p>
<p>트랜잭션의 잠금 과정을 두 단계로 나눈다.</p>
<pre><code class="language-text">Growing Phase
→ 잠금을 획득할 수 있음
→ 잠금을 해제할 수 없음

Shrinking Phase
→ 잠금을 해제할 수 있음
→ 새로운 잠금을 획득할 수 없음</code></pre>
<p>즉, 트랜잭션이 한 번이라도 잠금을 해제하기 시작하면 이후 새로운 잠금을 얻을 수 없다.</p>
<pre><code class="language-text">잠금 획득
잠금 획득
잠금 획득
→ 첫 잠금 해제
잠금 해제
잠금 해제</code></pre>
<p>다음과 같은 형태는 허용되지 않는다.</p>
<pre><code class="language-text">잠금 획득
잠금 해제
새로운 잠금 획득</code></pre>
<p>2PL을 따르는 스케줄은 충돌 직렬 가능성을 보장할 수 있다.</p>
<p>하지만 기본 2PL만으로는 다음 문제를 모두 해결하지 못한다.</p>
<pre><code class="language-text">데드락
연쇄 롤백
미커밋 값 접근</code></pre>
<p>이를 보완한 여러 변형이 존재한다.</p>
<hr />
<h1 id="39-basic-2pl">39. Basic 2PL</h1>
<p>Basic 2PL은 Growing Phase와 Shrinking Phase만 지키는 기본 규약이다.</p>
<pre><code class="language-text">성장 단계
→ 필요한 잠금 획득

축소 단계
→ 잠금 해제</code></pre>
<p>충돌 직렬 가능성을 보장하지만 X Lock을 커밋 전에 해제할 수 있으므로 다른 트랜잭션이 미커밋 데이터를 읽을 가능성이 남을 수 있다.</p>
<p>따라서 Cascading Rollback이 발생할 수 있다.</p>
<hr />
<h1 id="40-conservative-2pl">40. Conservative 2PL</h1>
<p>Conservative 2PL은 트랜잭션 실행 전에 필요한 모든 잠금을 한꺼번에 획득한다.</p>
<pre><code class="language-text">필요한 모든 잠금 획득 성공
→ 트랜잭션 시작

하나라도 획득 실패
→ 아무 잠금도 잡지 않고 대기</code></pre>
<p>장점:</p>
<pre><code class="language-text">잠금 대기 순환 방지
데드락 방지</code></pre>
<p>단점:</p>
<pre><code class="language-text">미리 필요한 모든 데이터를 알아야 함
실제로 나중에 사용할 데이터까지 일찍 잠금
잠금 보유시간 증가
동시성 감소</code></pre>
<p>동적인 쿼리에서는 필요한 모든 잠금을 사전에 알기 어려울 수 있다.</p>
<hr />
<h1 id="41-strict-2pl">41. Strict 2PL</h1>
<p>Strict 2PL은 모든 X Lock을 트랜잭션이 커밋하거나 롤백할 때까지 유지한다.</p>
<pre><code class="language-text">X Lock
→ COMMIT 또는 ROLLBACK까지 유지</code></pre>
<p>S Lock은 그보다 일찍 해제할 수 있다.</p>
<p>Strict 2PL은 다음을 방지한다.</p>
<pre><code class="language-text">Dirty Write
Dirty Read
Cascading Rollback</code></pre>
<p>또한 복구 처리를 단순하게 한다.</p>
<p>많은 데이터베이스 시스템에서 동시성 제어를 설명할 때 핵심적으로 등장하는 방식이다.</p>
<hr />
<h1 id="42-rigorous-2pl">42. Rigorous 2PL</h1>
<p>Rigorous 2PL은 S Lock과 X Lock을 모두 트랜잭션 종료 시점까지 유지한다.</p>
<pre><code class="language-text">S Lock
X Lock
→ 모두 COMMIT 또는 ROLLBACK까지 유지</code></pre>
<p>Strict 2PL보다 더 강한 방식이다.</p>
<pre><code class="language-text">Strict 2PL
→ X Lock만 종료까지 유지

Rigorous 2PL
→ S Lock과 X Lock 모두 종료까지 유지</code></pre>
<p>직렬화 순서와 커밋 순서를 일치시키기 쉬운 장점이 있지만 읽기 잠금도 오래 유지하므로 동시성이 더 낮아질 수 있다.</p>
<hr />
<h1 id="43-2pl의-한계">43. 2PL의 한계</h1>
<p>2PL은 직렬 가능성을 보장하는 강력한 방법이지만 다음 한계가 있다.</p>
<pre><code class="language-text">데드락 발생 가능
잠금 대기 증가
긴 트랜잭션이 많은 데이터를 장시간 차단
잠금 관리 비용
Phantom 방지를 위한 범위 잠금 필요</code></pre>
<p>특히 현재 존재하는 행만 잠그면 새로운 행 삽입으로 발생하는 Phantom을 막을 수 없다.</p>
<hr />
<h1 id="44-predicate-lock과-key-range-lock">44. Predicate Lock과 Key-Range Lock</h1>
<p>다음 조건으로 조회했다고 하자.</p>
<pre><code class="language-sql">SELECT *
FROM employees
WHERE salary &gt;= 5000;</code></pre>
<p>현재 조건을 만족하는 행만 잠그더라도 다른 트랜잭션이 <code>salary = 7000</code>인 새 행을 삽입할 수 있다.</p>
<pre><code class="language-text">기존 행 잠금
≠
아직 존재하지 않는 행의 삽입 방지</code></pre>
<p>Phantom을 막으려면 논리적 조건 또는 검색 키 범위를 보호해야 한다.</p>
<hr />
<h2 id="441-predicate-lock">44.1 Predicate Lock</h2>
<p>Predicate Lock은 다음과 같은 논리적 조건 자체를 잠그는 개념이다.</p>
<pre><code class="language-text">salary &gt;= 5000</code></pre>
<p>다른 트랜잭션이 이 조건을 만족하는 행을 삽입하거나 변경하지 못하게 한다.</p>
<p>이론적으로 명확하지만 조건 간 충돌을 판정하는 비용이 클 수 있다.</p>
<hr />
<h2 id="442-key-range-lock">44.2 Key-Range Lock</h2>
<p>Key-Range Lock은 인덱스 키의 범위와 키 사이의 간격을 잠근다.</p>
<pre><code class="language-text">[5000, +∞)</code></pre>
<p>현재 존재하는 키뿐 아니라 그 범위에 새 키가 삽입되는 것도 제어한다.</p>
<p>일부 시스템에서는 다음과 유사한 잠금을 사용한다.</p>
<pre><code class="language-text">Record Lock
Gap Lock
Next-Key Lock</code></pre>
<p>구체적인 구현과 용어는 DBMS마다 다르지만 목적은 같다.</p>
<pre><code class="language-text">기존 행 변경 방지
+
조건 범위에 새로운 행이 들어오는 것 방지</code></pre>
<hr />
<h1 id="45-deadlock">45. Deadlock</h1>
<p>데드락은 둘 이상의 트랜잭션이 서로 상대방이 가진 자원을 기다리며 영원히 진행하지 못하는 상태다.</p>
<p>예:</p>
<pre><code class="language-text">T₁:
X 잠금 획득
Y 잠금 요청 → T₂ 때문에 대기

T₂:
Y 잠금 획득
X 잠금 요청 → T₁ 때문에 대기</code></pre>
<p>대기 관계:</p>
<pre><code class="language-text">T₁ → T₂
T₂ → T₁</code></pre>
<p>순환이 형성된다.</p>
<hr />
<h1 id="46-데드락의-네-가지-필요조건">46. 데드락의 네 가지 필요조건</h1>
<p>데드락이 발생하려면 일반적으로 다음 네 조건이 동시에 성립해야 한다.</p>
<hr />
<h2 id="461-mutual-exclusion">46.1 Mutual Exclusion</h2>
<p>하나의 자원을 동시에 여러 트랜잭션이 사용할 수 없다.</p>
<p>예를 들어 X Lock은 한 트랜잭션만 보유할 수 있다.</p>
<hr />
<h2 id="462-hold-and-wait">46.2 Hold and Wait</h2>
<p>트랜잭션이 이미 자원을 보유한 상태에서 다른 자원을 기다린다.</p>
<pre><code class="language-text">X 잠금 보유
+
Y 잠금 대기</code></pre>
<hr />
<h2 id="463-no-preemption">46.3 No Preemption</h2>
<p>트랜잭션이 가진 자원을 강제로 빼앗을 수 없다.</p>
<p>일반적으로 잠금을 보유한 트랜잭션이 종료하거나 롤백해야 잠금이 해제된다.</p>
<hr />
<h2 id="464-circular-wait">46.4 Circular Wait</h2>
<p>여러 트랜잭션의 대기 관계가 순환한다.</p>
<pre><code class="language-text">T₁은 T₂를 기다림
T₂는 T₃를 기다림
T₃는 T₁을 기다림</code></pre>
<p>네 조건 중 하나라도 제거하면 데드락을 방지할 수 있다.</p>
<hr />
<h1 id="47-wait-for-graph">47. Wait-For Graph</h1>
<p>데드락을 탐지하기 위해 Wait-For Graph를 사용할 수 있다.</p>
<pre><code class="language-text">각 트랜잭션
→ 정점

Tᵢ가 Tⱼ의 잠금 해제를 기다림
→ Tᵢ에서 Tⱼ로 간선</code></pre>
<p>예:</p>
<pre><code class="language-text">T₁ → T₂
T₂ → T₁</code></pre>
<p>그래프에 사이클이 존재하면 데드락이 발생한 것이다.</p>
<p>데드락을 발견하면 시스템은 하나 이상의 트랜잭션을 희생자로 선택해 롤백한다.</p>
<hr />
<h1 id="48-데드락-처리-전략">48. 데드락 처리 전략</h1>
<h2 id="481-예방">48.1 예방</h2>
<p>데드락의 필요조건이 성립하지 않도록 한다.</p>
<p>대표적인 방법:</p>
<pre><code class="language-text">모든 잠금을 미리 획득
잠금 획득 순서 통일
트랜잭션 타임스탬프 기반 대기 규칙</code></pre>
<hr />
<h2 id="482-회피">48.2 회피</h2>
<p>자원 할당 전에 해당 할당이 안전한 상태를 유지하는지 판단한다.</p>
<p>운영체제의 Banker’s Algorithm과 유사한 개념이 있지만, 데이터베이스에서는 트랜잭션이 앞으로 필요한 모든 자원을 알기 어렵기 때문에 일반적으로 적용하기 까다롭다.</p>
<hr />
<h2 id="483-탐지와-복구">48.3 탐지와 복구</h2>
<p>일단 대기를 허용한 뒤 Wait-For Graph 등을 이용해 데드락을 탐지한다.</p>
<pre><code class="language-text">데드락 탐지
→ 희생자 트랜잭션 선택
→ 롤백
→ 잠금 해제
→ 나머지 트랜잭션 진행</code></pre>
<p>희생자 선택 시 다음 요소를 고려할 수 있다.</p>
<pre><code class="language-text">이미 수행한 작업량
보유한 잠금 수
변경한 데이터 양
롤백 비용
재시도 횟수
트랜잭션 우선순위</code></pre>
<hr />
<h2 id="484-timeout">48.4 Timeout</h2>
<p>일정 시간 이상 잠금을 기다리면 실패 처리한다.</p>
<pre><code class="language-text">대기시간 초과
→ 트랜잭션 중단</code></pre>
<p>구현이 단순하지만 다음 한계가 있다.</p>
<pre><code class="language-text">실제 데드락이 아닌데도 긴 작업을 중단할 수 있음
Timeout이 너무 길면 응답 지연
Timeout이 너무 짧으면 불필요한 실패 증가</code></pre>
<hr />
<h1 id="49-잠금-순서-통일">49. 잠금 순서 통일</h1>
<p>데드락을 줄이는 가장 실용적인 방법 중 하나는 모든 트랜잭션이 같은 순서로 자원을 잠그도록 하는 것이다.</p>
<p>잘못된 예:</p>
<pre><code class="language-text">T₁: account A → account B
T₂: account B → account A</code></pre>
<p>개선:</p>
<pre><code class="language-text">항상 작은 account_id부터 잠금

T₁: account A → account B
T₂: account A → account B</code></pre>
<p>여러 테이블을 변경한다면 테이블 접근 순서도 통일할 수 있다.</p>
<pre><code class="language-text">항상:
accounts
→ payments
→ ledger
→ audit_logs</code></pre>
<p>잠금 순서 통일은 Circular Wait 가능성을 낮춘다.</p>
<hr />
<h1 id="50-wait-die와-wound-wait">50. Wait-Die와 Wound-Wait</h1>
<p>트랜잭션에 타임스탬프를 부여하여 데드락을 예방할 수 있다.</p>
<pre><code class="language-text">타임스탬프가 작음
→ 오래된 트랜잭션

타임스탬프가 큼
→ 새로운 트랜잭션</code></pre>
<hr />
<h2 id="501-wait-die">50.1 Wait-Die</h2>
<pre><code class="language-text">오래된 트랜잭션이 새로운 트랜잭션을 기다림
→ WAIT

새로운 트랜잭션이 오래된 트랜잭션을 기다려야 함
→ 새로운 트랜잭션 ROLLBACK</code></pre>
<p>즉:</p>
<pre><code class="language-text">Old waits for Young
Young dies for Old</code></pre>
<p>예:</p>
<pre><code class="language-text">T₁이 오래됨
T₂가 새로움

T₁이 T₂의 자원 요청
→ T₁ 대기 가능

T₂가 T₁의 자원 요청
→ T₂ 중단</code></pre>
<hr />
<h2 id="502-wound-wait">50.2 Wound-Wait</h2>
<pre><code class="language-text">오래된 트랜잭션이 새로운 트랜잭션의 자원을 요청
→ 새로운 트랜잭션을 중단시킴

새로운 트랜잭션이 오래된 트랜잭션의 자원을 요청
→ 새로운 트랜잭션이 대기</code></pre>
<p>즉:</p>
<pre><code class="language-text">Old wounds Young
Young waits for Old</code></pre>
<p>두 방식 모두 대기 방향을 타임스탬프 순서로 제한하여 순환 대기를 방지한다.</p>
<p>재시도되는 트랜잭션은 일반적으로 기존 타임스탬프를 유지해야 기아 상태를 줄일 수 있다.</p>
<hr />
<h1 id="51-starvation">51. Starvation</h1>
<p>Starvation은 특정 트랜잭션이 반복적으로 대기하거나 중단되어 오랫동안 완료되지 못하는 현상이다.</p>
<p>예:</p>
<pre><code class="language-text">낮은 우선순위 트랜잭션이 계속 뒤로 밀림
데드락 희생자로 같은 트랜잭션이 반복 선택됨
낙관적 검증에서 계속 실패함</code></pre>
<p>해결 방법:</p>
<pre><code class="language-text">대기시간에 따라 우선순위 증가
재시도 횟수 고려
기존 타임스탬프 유지
희생자 선택 기준 조정
공정한 잠금 대기 큐</code></pre>
<p>동시성 제어는 데드락만 피하면 끝나는 것이 아니라 특정 트랜잭션이 영원히 완료되지 못하는 문제도 고려해야 한다.</p>
<hr />
<h1 id="52-timestamp-ordering">52. Timestamp Ordering</h1>
<p>Timestamp Ordering은 트랜잭션마다 고유한 타임스탬프를 부여하고 모든 충돌 연산이 그 순서와 일치하도록 제어하는 방식이다.</p>
<pre><code class="language-text">TS(T₁) &lt; TS(T₂)
→ T₁이 논리적으로 T₂보다 먼저 실행된 것으로 취급</code></pre>
<p>각 데이터 항목 X에는 다음 정보가 유지될 수 있다.</p>
<pre><code class="language-text">read_TS(X)
→ X를 성공적으로 읽은 가장 최신 트랜잭션의 타임스탬프

write_TS(X)
→ X를 성공적으로 기록한 가장 최신 트랜잭션의 타임스탬프</code></pre>
<hr />
<h1 id="53-timestamp-ordering의-읽기-규칙">53. Timestamp Ordering의 읽기 규칙</h1>
<p>트랜잭션 T가 X를 읽으려 한다고 하자.</p>
<pre><code class="language-text">TS(T) &lt; write_TS(X)</code></pre>
<p>라면 T보다 새로운 트랜잭션이 이미 X를 기록한 것이다.</p>
<p>T가 이제 X를 읽으면 타임스탬프 순서를 위반한다.</p>
<p>따라서 T의 읽기를 거부하고 T를 롤백할 수 있다.</p>
<p>반대로 읽기가 허용되면:</p>
<pre><code class="language-text">read_TS(X)
= max(read_TS(X), TS(T))</code></pre>
<p>로 갱신한다.</p>
<hr />
<h1 id="54-timestamp-ordering의-쓰기-규칙">54. Timestamp Ordering의 쓰기 규칙</h1>
<p>트랜잭션 T가 X를 기록하려 한다고 하자.</p>
<p>다음 조건이면 문제가 발생한다.</p>
<pre><code class="language-text">TS(T) &lt; read_TS(X)</code></pre>
<p>T보다 새로운 트랜잭션이 이미 X를 읽었다.</p>
<p>T가 뒤늦게 X를 기록하면 새로운 트랜잭션이 과거 값을 읽은 셈이 되어 타임스탬프 순서를 위반한다.</p>
<p>또한:</p>
<pre><code class="language-text">TS(T) &lt; write_TS(X)</code></pre>
<p>라면 T보다 새로운 트랜잭션이 이미 X를 기록했다.</p>
<p>기본 Timestamp Ordering에서는 T를 롤백할 수 있다.</p>
<hr />
<h1 id="55-timestamp-ordering의-특징">55. Timestamp Ordering의 특징</h1>
<p>장점:</p>
<pre><code class="language-text">잠금 대기 불필요
데드락이 발생하지 않음
타임스탬프 순서로 직렬 가능성 보장 가능</code></pre>
<p>단점:</p>
<pre><code class="language-text">충돌 시 트랜잭션 롤백 증가
긴 트랜잭션이 반복 실패할 수 있음
Starvation 가능
연쇄 롤백을 막기 위한 추가 규칙 필요</code></pre>
<p>잠금 기반 방식이 충돌을 만나면 기다리는 경향이 있다면 Timestamp Ordering은 순서에 맞지 않는 작업을 중단시키는 경향이 있다.</p>
<hr />
<h1 id="56-thomas-write-rule">56. Thomas Write Rule</h1>
<p>기본 Timestamp Ordering에서 다음 조건이면 T의 쓰기를 거부한다.</p>
<pre><code class="language-text">TS(T) &lt; write_TS(X)</code></pre>
<p>하지만 이 쓰기는 이미 더 새로운 쓰기에 의해 덮어써질 오래된 값일 수 있다.</p>
<p>Thomas Write Rule은 이러한 쓰기를 롤백 사유로 삼지 않고 무시할 수 있도록 한다.</p>
<pre><code class="language-text">오래된 쓰기
→ 어차피 최신 쓰기에 가려짐
→ 실행하지 않고 무시</code></pre>
<p>이를 통해 불필요한 롤백을 줄이고 기본 Timestamp Ordering보다 더 많은 스케줄을 허용할 수 있다.</p>
<hr />
<h1 id="57-optimistic-concurrency-control">57. Optimistic Concurrency Control</h1>
<p>Optimistic Concurrency Control, OCC는 충돌이 자주 발생하지 않을 것이라고 가정한다.</p>
<pre><code class="language-text">일단 잠금 없이 작업 수행
→ 커밋 직전에 충돌 검증
→ 충돌이 없으면 반영
→ 충돌이 있으면 롤백</code></pre>
<p>잠금을 먼저 획득하는 비관적 방식과 대비된다.</p>
<pre><code class="language-text">Pessimistic
→ 충돌이 발생할 것이라고 보고 미리 잠금

Optimistic
→ 충돌이 드물다고 보고 나중에 검증</code></pre>
<hr />
<h1 id="58-occ의-세-단계">58. OCC의 세 단계</h1>
<h2 id="581-read-phase">58.1 Read Phase</h2>
<p>트랜잭션은 필요한 데이터를 읽고 변경 내용을 자신의 로컬 작업공간에 저장한다.</p>
<pre><code class="language-text">공유 데이터베이스에는 아직 실제 변경을 반영하지 않음</code></pre>
<p>트랜잭션은 다음 집합을 기록할 수 있다.</p>
<pre><code class="language-text">Read Set
→ 읽은 데이터 집합

Write Set
→ 변경하려는 데이터 집합</code></pre>
<hr />
<h2 id="582-validation-phase">58.2 Validation Phase</h2>
<p>커밋 전에 다른 트랜잭션과 충돌하는지 검사한다.</p>
<p>예를 들어 다음 관계를 확인할 수 있다.</p>
<pre><code class="language-text">내 Read Set과 다른 트랜잭션의 Write Set이 충돌하는가?
내 Write Set과 다른 트랜잭션의 Read 또는 Write Set이 충돌하는가?</code></pre>
<p>직렬 실행 순서를 유지할 수 없다면 검증에 실패한다.</p>
<hr />
<h2 id="583-write-phase">58.3 Write Phase</h2>
<p>검증에 성공하면 로컬 변경 내용을 실제 데이터베이스에 반영한다.</p>
<pre><code class="language-text">검증 성공
→ Write Set 반영
→ COMMIT

검증 실패
→ ROLLBACK
→ 필요하면 재시도</code></pre>
<hr />
<h1 id="59-occ가-적합한-환경">59. OCC가 적합한 환경</h1>
<p>OCC는 다음 상황에 적합하다.</p>
<pre><code class="language-text">읽기 작업이 많음
쓰기 충돌이 드묾
트랜잭션이 짧음
데이터 경쟁이 낮음
재시도 비용이 작음</code></pre>
<p>반대로 다음 상황에서는 비효율적일 수 있다.</p>
<pre><code class="language-text">동일 데이터에 쓰기가 집중됨
트랜잭션이 김
검증 시점에 자주 충돌
재실행 비용이 큼</code></pre>
<p>오랜 작업을 모두 수행한 뒤 마지막에 검증 실패하면 낭비가 크다.</p>
<hr />
<h1 id="60-애플리케이션의-낙관적-잠금">60. 애플리케이션의 낙관적 잠금</h1>
<p>애플리케이션에서는 버전 컬럼을 이용해 낙관적 동시성 제어를 구현할 수 있다.</p>
<p>초기 데이터:</p>
<pre><code class="language-text">id = 1
balance = 1000
version = 5</code></pre>
<p>조회:</p>
<pre><code class="language-sql">SELECT id, balance, version
FROM accounts
WHERE id = 1;</code></pre>
<p>갱신:</p>
<pre><code class="language-sql">UPDATE accounts
SET balance = 900,
    version = version + 1
WHERE id = 1
  AND version = 5;</code></pre>
<p>다른 트랜잭션이 먼저 변경했다면 현재 버전은 더 이상 5가 아니다.</p>
<pre><code class="language-text">영향받은 행 수 = 0
→ 동시 변경 감지</code></pre>
<p>애플리케이션은 다음 중 하나를 선택할 수 있다.</p>
<pre><code class="language-text">사용자에게 충돌 알림
최신 데이터 다시 조회
자동 재시도
병합 화면 제공</code></pre>
<p>이 방식은 긴 시간 동안 데이터베이스 잠금을 유지하지 않아도 되는 장점이 있다.</p>
<hr />
<h1 id="61-multi-version-concurrency-control">61. Multi-Version Concurrency Control</h1>
<p>MVCC는 Multi-Version Concurrency Control의 약자다.</p>
<p>데이터를 변경할 때 기존 값을 즉시 덮어쓰기만 하는 대신 여러 버전을 유지하여 트랜잭션이 자신의 시점에 맞는 버전을 읽도록 한다.</p>
<p>개념적으로 다음과 같다.</p>
<pre><code class="language-text">X의 버전

V1: X = 100
V2: X = 200
V3: X = 300</code></pre>
<p>각 버전에는 다음과 같은 정보가 연결될 수 있다.</p>
<pre><code class="language-text">생성한 트랜잭션
유효 시작 시점
유효 종료 시점
삭제 또는 대체한 트랜잭션</code></pre>
<p>트랜잭션은 자신의 스냅샷을 기준으로 보이는 버전을 선택한다.</p>
<hr />
<h1 id="62-snapshot">62. Snapshot</h1>
<p>Snapshot은 특정 트랜잭션이 데이터를 읽을 때 어떤 트랜잭션의 변경을 볼 수 있는지를 나타내는 논리적인 시점이다.</p>
<p>예를 들어 T₁의 스냅샷이 만들어진 뒤 T₂가 새로운 버전을 커밋했다고 하자.</p>
<pre><code class="language-text">T₁의 Snapshot 생성
→ X = 100이 보임

T₂가 X = 200으로 변경 후 COMMIT

T₁이 X를 다시 읽음
→ Snapshot 정책에 따라 X = 100을 계속 볼 수 있음</code></pre>
<p>스냅샷은 데이터베이스 전체를 실제로 복사한 파일이 아니다.</p>
<pre><code class="language-text">트랜잭션 상태
버전의 생성·종료 정보
가시성 규칙</code></pre>
<p>을 이용해 어떤 버전을 보여줄지 결정하는 논리적 관점이다.</p>
<hr />
<h1 id="63-mvcc의-장점">63. MVCC의 장점</h1>
<p>MVCC의 대표적인 장점은 읽기와 쓰기의 충돌을 줄일 수 있다는 것이다.</p>
<pre><code class="language-text">Writer
→ 새로운 버전 생성

Reader
→ 자신의 Snapshot에 맞는 기존 버전 읽기</code></pre>
<p>따라서 일반적인 읽기가 쓰기 작업의 종료를 기다리지 않을 수 있다.</p>
<pre><code class="language-text">Read-Write 충돌 감소
긴 조회가 쓰기를 막는 문제 감소
일관된 시점 조회 가능
읽기 중심 워크로드의 동시성 향상</code></pre>
<hr />
<h1 id="64-mvcc도-잠금이-필요-없는가">64. MVCC도 잠금이 필요 없는가?</h1>
<p>그렇지 않다.</p>
<p>MVCC는 주로 읽기와 쓰기의 충돌을 줄인다.</p>
<p>하지만 다음 상황에서는 여전히 충돌 제어가 필요하다.</p>
<pre><code class="language-text">두 트랜잭션이 같은 데이터를 동시에 수정
같은 행 삭제와 수정
고유성 제약 검사
외래 키 검사
DDL 수행
명시적 잠금 요청</code></pre>
<p>즉:</p>
<pre><code class="language-text">MVCC
→ Lock을 완전히 제거

가 아니라

MVCC
→ Read와 Write 충돌을 버전으로 줄임
→ Write와 Write 충돌은 별도 제어</code></pre>
<p>다.</p>
<hr />
<h1 id="65-mvcc의-비용">65. MVCC의 비용</h1>
<p>여러 버전을 유지하면 다음 비용이 발생한다.</p>
<pre><code class="language-text">이전 버전 저장 공간
버전 가시성 검사
오래된 버전 정리
긴 트랜잭션으로 인한 정리 지연
저장공간 팽창</code></pre>
<p>오래 실행되는 트랜잭션이 오래된 Snapshot을 유지하면 시스템은 해당 트랜잭션이 볼 수 있는 이전 버전을 제거할 수 없다.</p>
<pre><code class="language-text">Long Transaction
→ 오래된 버전 보존 필요
→ 버전 정리 지연
→ 저장공간과 검색 비용 증가</code></pre>
<p>따라서 MVCC에서도 트랜잭션을 짧게 유지하는 것이 중요하다.</p>
<hr />
<h1 id="66-snapshot-isolation">66. Snapshot Isolation</h1>
<p>Snapshot Isolation은 각 트랜잭션이 일관된 Snapshot을 기준으로 읽고, 동시에 같은 데이터를 수정하는 Write-Write 충돌을 제어하는 격리 방식이다.</p>
<p>일반적인 개념은 다음과 같다.</p>
<pre><code class="language-text">트랜잭션 시작 시점의 일관된 Snapshot 읽기
+
동일 데이터에 대한 동시 쓰기 충돌 검사</code></pre>
<p>많은 구현에서 두 트랜잭션이 같은 데이터 항목을 수정하면 하나만 커밋하도록 한다.</p>
<pre><code class="language-text">First Committer Wins</code></pre>
<p>Snapshot Isolation은 다음 현상을 대체로 방지한다.</p>
<pre><code class="language-text">Dirty Read
Non-Repeatable Read
일반적인 Phantom 관찰
Lost Update 형태의 동일 행 쓰기 충돌
Read Skew</code></pre>
<p>하지만 Serializable과 동일하지 않다.</p>
<hr />
<h1 id="67-snapshot-isolation과-write-skew">67. Snapshot Isolation과 Write Skew</h1>
<p>당직 의사 예시를 다시 보자.</p>
<p>초기 상태:</p>
<pre><code class="language-text">A 의사: 당직
B 의사: 당직</code></pre>
<p>T₁과 T₂는 같은 Snapshot을 읽는다.</p>
<pre><code class="language-text">T₁: 당직 의사 2명 확인
T₂: 당직 의사 2명 확인</code></pre>
<p>각각 서로 다른 행을 수정한다.</p>
<pre><code class="language-text">T₁: A를 당직 해제
T₂: B를 당직 해제</code></pre>
<p>수정 대상이 다르므로 직접적인 Write-Write 충돌은 없다.</p>
<pre><code class="language-text">T₁의 Write Set: A
T₂의 Write Set: B</code></pre>
<p>두 트랜잭션이 모두 커밋하면 최소 한 명이 당직이어야 한다는 규칙이 깨진다.</p>
<pre><code class="language-text">Snapshot Isolation
→ 동일 행 Write-Write 충돌은 감지
→ 서로 다른 행에 대한 논리적 Write Skew는 놓칠 수 있음</code></pre>
<p>따라서:</p>
<pre><code class="language-text">Snapshot Isolation
≠
Serializable</code></pre>
<p>이다.</p>
<hr />
<h1 id="68-snapshot-isolation에서-write-skew-방지">68. Snapshot Isolation에서 Write Skew 방지</h1>
<p>다음 방법을 사용할 수 있다.</p>
<hr />
<h2 id="681-serializable-사용">68.1 Serializable 사용</h2>
<p>직렬 가능성을 보장하는 격리수준을 사용한다.</p>
<p>동시 실행 결과가 업무 규칙을 깨뜨린다면 트랜잭션 하나를 중단시킬 수 있다.</p>
<hr />
<h2 id="682-관련-데이터를-명시적으로-잠금">68.2 관련 데이터를 명시적으로 잠금</h2>
<p>업무 규칙 판정에 사용되는 행을 잠근다.</p>
<pre><code class="language-text">당직 의사 목록을 읽을 때
→ 관련 행들을 수정 불가능하게 잠금</code></pre>
<p>다만 조건에 해당하는 행의 추가·삭제까지 보호해야 한다면 범위 또는 Predicate 보호가 필요할 수 있다.</p>
<hr />
<h2 id="683-제약조건으로-표현">68.3 제약조건으로 표현</h2>
<p>가능하다면 업무 규칙을 데이터베이스 제약조건으로 표현한다.</p>
<pre><code class="language-text">UNIQUE
FOREIGN KEY
CHECK
Exclusion Constraint</code></pre>
<p>하지만 “항상 당직 의사가 최소 한 명이어야 한다”처럼 여러 행 전체를 검사해야 하는 규칙은 단순한 행 단위 제약으로 표현하기 어려울 수 있다.</p>
<hr />
<h2 id="684-충돌-지점을-같은-행으로-모으기">68.4 충돌 지점을 같은 행으로 모으기</h2>
<p>업무 규칙을 대표하는 별도 행을 만들어 모든 트랜잭션이 해당 행을 수정하거나 잠그도록 설계할 수 있다.</p>
<pre><code class="language-text">on_call_state 행
→ 모든 당직 변경 트랜잭션이 잠금</code></pre>
<p>서로 다른 행만 수정하던 트랜잭션 사이에 명시적인 충돌 지점을 만드는 방식이다.</p>
<hr />
<h1 id="69-serializable-snapshot-isolation">69. Serializable Snapshot Isolation</h1>
<p>Serializable Snapshot Isolation, SSI는 Snapshot 기반 읽기의 장점을 유지하면서 직렬화 이상을 탐지하려는 방식이다.</p>
<p>모든 읽기를 잠금으로 막는 대신 트랜잭션 사이의 읽기·쓰기 의존 관계를 추적한다.</p>
<p>특히 다음과 같은 관계를 감시한다.</p>
<pre><code class="language-text">T₁이 어떤 데이터를 읽음
→ 이후 T₂가 그 데이터를 변경

하지만 T₁의 Snapshot에는 T₂의 변경이 보이지 않음</code></pre>
<p>이러한 관계를 Read-Write Anti-Dependency라고 볼 수 있다.</p>
<p>여러 트랜잭션의 의존 관계가 직렬화 그래프에서 위험한 순환을 만들 가능성이 있으면 트랜잭션 하나를 중단시킨다.</p>
<pre><code class="language-text">직렬 가능성 위반 가능성 탐지
→ 트랜잭션 Abort
→ 애플리케이션 재시도</code></pre>
<p>SSI의 장점:</p>
<pre><code class="language-text">일반 Snapshot 읽기의 높은 동시성 유지
많은 읽기 작업이 서로를 차단하지 않음
Write Skew와 직렬화 이상 방지</code></pre>
<p>비용:</p>
<pre><code class="language-text">의존 관계 추적 비용
직렬화 실패 가능
애플리케이션 재시도 필요
긴 트랜잭션에서 충돌 가능성 증가</code></pre>
<hr />
<h1 id="70-비관적-동시성-제어와-낙관적-동시성-제어">70. 비관적 동시성 제어와 낙관적 동시성 제어</h1>
<h2 id="701-비관적-방식">70.1 비관적 방식</h2>
<p>충돌이 발생할 가능성이 높다고 가정한다.</p>
<pre><code class="language-text">데이터 접근 전 잠금
→ 다른 트랜잭션의 접근 차단
→ 작업 수행
→ 잠금 해제</code></pre>
<p>적합한 상황:</p>
<pre><code class="language-text">같은 데이터에 갱신이 집중됨
충돌 확률이 높음
충돌 후 재실행 비용이 큼
재고·잔액처럼 즉시 정확한 제어가 필요함</code></pre>
<p>단점:</p>
<pre><code class="language-text">대기
데드락
잠금 보유시간
동시성 저하</code></pre>
<hr />
<h2 id="702-낙관적-방식">70.2 낙관적 방식</h2>
<p>충돌이 드물다고 가정한다.</p>
<pre><code class="language-text">잠금 없이 읽고 작업
→ 커밋 시점에 버전 또는 충돌 검사
→ 충돌하면 실패</code></pre>
<p>적합한 상황:</p>
<pre><code class="language-text">읽기 비중이 높음
동일 데이터 충돌이 드묾
사용자 편집 시간이 김
긴 시간 DB 잠금을 유지하면 안 됨</code></pre>
<p>단점:</p>
<pre><code class="language-text">충돌 시 작업 재실행
사용자 변경 병합 필요
충돌이 많으면 성능 급감</code></pre>
<hr />
<h1 id="71-격리수준과-동시성-제어-방식의-관계">71. 격리수준과 동시성 제어 방식의 관계</h1>
<p>격리수준은 애플리케이션에 제공되는 <strong>보장 수준</strong>이다.</p>
<p>Lock, MVCC, Timestamp, OCC는 그 보장을 구현하는 <strong>메커니즘</strong>이다.</p>
<pre><code class="language-text">격리수준
→ 무엇을 보장할 것인가?

동시성 제어 알고리즘
→ 그 보장을 어떻게 구현할 것인가?</code></pre>
<p>따라서 다음과 같이 단순 연결하면 안 된다.</p>
<pre><code class="language-text">Read Committed = Lock
Repeatable Read = MVCC
Serializable = 무조건 전체 잠금</code></pre>
<p>같은 격리수준도 여러 방식으로 구현할 수 있다.</p>
<pre><code class="language-text">Serializable
→ Strict 2PL로 구현 가능
→ Predicate Lock을 포함한 잠금 방식 가능
→ SSI로 구현 가능</code></pre>
<p>반대로 MVCC를 사용한다고 해서 자동으로 Serializable이 되는 것도 아니다.</p>
<hr />
<h1 id="72-명시적-잠금이-필요한-경우">72. 명시적 잠금이 필요한 경우</h1>
<p>높은 격리수준을 항상 사용하지 않고 특정 업무에서만 명시적인 잠금을 사용할 수 있다.</p>
<p>대표적인 패턴은 다음과 같다.</p>
<pre><code class="language-text">데이터 조회
→ 해당 데이터를 기반으로 의사결정
→ 이후 데이터 변경</code></pre>
<p>예:</p>
<pre><code class="language-text">재고 확인
→ 주문 가능 판단
→ 재고 감소

잔액 확인
→ 출금 가능 판단
→ 잔액 감소

예약 가능 여부 확인
→ 좌석 배정</code></pre>
<p>조회와 변경 사이에 다른 트랜잭션이 개입하면 판단이 무효가 될 수 있다.</p>
<p>이 경우 다음 방법을 고려한다.</p>
<pre><code class="language-text">원자적 조건부 UPDATE
비관적 행 잠금
Serializable
버전 컬럼을 이용한 낙관적 검증
고유 제약조건</code></pre>
<hr />
<h1 id="73-nowait와-skip-locked의-일반적-의미">73. NOWAIT와 SKIP LOCKED의 일반적 의미</h1>
<p>구체적인 문법은 DBMS마다 다르지만, 잠금 획득 실패 시의 정책은 크게 다음과 같이 나눌 수 있다.</p>
<hr />
<h2 id="731-wait">73.1 Wait</h2>
<p>잠금이 해제될 때까지 기다린다.</p>
<pre><code class="language-text">장점
→ 작업 성공 가능성이 높음

단점
→ 응답 지연
→ 데드락 가능</code></pre>
<hr />
<h2 id="732-nowait">73.2 NOWAIT</h2>
<p>잠금을 즉시 획득하지 못하면 실패한다.</p>
<pre><code class="language-text">장점
→ 빠른 실패
→ 사용자가 다른 선택 가능

단점
→ 일시적인 충돌에도 작업 실패</code></pre>
<hr />
<h2 id="733-skip-locked">73.3 SKIP LOCKED</h2>
<p>잠긴 데이터는 건너뛰고 잠기지 않은 데이터만 처리한다.</p>
<p>작업 큐에서 여러 워커가 서로 다른 작업을 가져갈 때 유용하다.</p>
<pre><code class="language-text">Worker 1
→ 작업 A 잠금

Worker 2
→ A 건너뜀
→ 작업 B 선택</code></pre>
<p>하지만 정확한 전체 조회에는 적합하지 않다.</p>
<pre><code class="language-text">잠긴 행이 결과에서 일시적으로 사라짐
→ 일관된 전체 결과가 아님</code></pre>
<hr />
<h1 id="74-트랜잭션-재시도">74. 트랜잭션 재시도</h1>
<p>동시성 제어에서 실패는 항상 시스템 오류를 의미하지 않는다.</p>
<p>다음 실패는 정합성을 지키기 위해 의도적으로 발생할 수 있다.</p>
<pre><code class="language-text">데드락 희생자
직렬화 실패
낙관적 버전 충돌
잠금 Timeout
Timestamp 순서 위반</code></pre>
<p>재시도는 일부 SQL만 수행하면 안 되는 경우가 많다.</p>
<p>트랜잭션이 읽은 데이터와 판단 전체가 이전 상태에 기반하기 때문이다.</p>
<pre><code class="language-text">잘못된 방식:
실패한 마지막 UPDATE만 다시 실행

올바른 방식:
트랜잭션 시작
→ 데이터 다시 읽기
→ 조건 다시 판단
→ 전체 변경 다시 실행</code></pre>
<hr />
<h2 id="741-재시도-가능한-트랜잭션의-조건">74.1 재시도 가능한 트랜잭션의 조건</h2>
<p>재시도 로직을 설계할 때 다음을 고려해야 한다.</p>
<pre><code class="language-text">전체 트랜잭션을 함수처럼 다시 실행 가능
외부 부작용 중복 방지
재시도 횟수 제한
백오프 적용
멱등성 확보</code></pre>
<hr />
<h2 id="742-외부-시스템-호출-주의">74.2 외부 시스템 호출 주의</h2>
<p>트랜잭션 안에서 다음 작업을 수행했다고 하자.</p>
<pre><code class="language-text">외부 결제 API 호출
이메일 전송
메시지 발행
파일 업로드</code></pre>
<p>이후 데이터베이스 트랜잭션이 롤백되더라도 외부 작업은 자동으로 취소되지 않는다.</p>
<p>재시도하면 중복 결제나 중복 발송이 발생할 수 있다.</p>
<p>따라서 다음 패턴이 필요할 수 있다.</p>
<pre><code class="language-text">Idempotency Key
Outbox Pattern
상태 기반 재처리
보상 트랜잭션
중복 제거 키</code></pre>
<p>데이터베이스 트랜잭션의 Atomicity는 외부 시스템 전체에 자동으로 확장되지 않는다.</p>
<hr />
<h1 id="75-트랜잭션을-짧게-유지해야-하는-이유">75. 트랜잭션을 짧게 유지해야 하는 이유</h1>
<p>트랜잭션이 길어질수록 다음 문제가 커진다.</p>
<pre><code class="language-text">잠금 보유시간 증가
충돌 확률 증가
데드락 가능성 증가
MVCC 이전 버전 정리 지연
실패 시 재실행 비용 증가
커넥션 점유시간 증가</code></pre>
<p>트랜잭션 내부에서 피해야 할 작업:</p>
<pre><code class="language-text">사용자 입력 대기
긴 계산
대용량 파일 처리
불필요한 네트워크 호출
외부 API 응답 대기
장시간 Sleep</code></pre>
<p>일반적인 원칙은 다음과 같다.</p>
<pre><code class="language-text">트랜잭션 밖에서 준비 가능한 작업 수행
→ 트랜잭션 시작
→ 필요한 데이터 읽기
→ 검증과 변경
→ 빠르게 COMMIT</code></pre>
<p>단, 읽은 데이터가 변경 작업과 반드시 동일한 일관성 경계에 있어야 한다면 무작정 밖으로 분리하면 안 된다.</p>
<hr />
<h1 id="76-커넥션과-트랜잭션의-관계">76. 커넥션과 트랜잭션의 관계</h1>
<p>트랜잭션은 일반적으로 하나의 데이터베이스 커넥션에서 실행된다.</p>
<pre><code class="language-text">Connection 획득
→ BEGIN
→ 여러 SQL 수행
→ COMMIT 또는 ROLLBACK
→ Connection 반환</code></pre>
<p>커넥션 풀은 데이터베이스 연결을 재사용하여 연결 생성 비용을 줄인다.</p>
<p>하지만 커넥션 풀이 트랜잭션 정합성을 자동으로 보장하는 것은 아니다.</p>
<p>애플리케이션은 다음을 지켜야 한다.</p>
<pre><code class="language-text">하나의 트랜잭션 동안 같은 커넥션 사용
예외 발생 시 ROLLBACK
종료 후 커넥션 상태 초기화
장시간 커넥션 점유 방지</code></pre>
<p>트랜잭션이 길면 커넥션 풀의 커넥션도 오래 점유한다.</p>
<pre><code class="language-text">긴 트랜잭션
→ 잠금 장기 보유
→ 커넥션 장기 점유
→ 다른 요청의 커넥션 대기</code></pre>
<p>동시성 문제와 커넥션 풀 고갈은 서로 연결될 수 있다.</p>
<hr />
<h1 id="77-업무별-동시성-제어-예시">77. 업무별 동시성 제어 예시</h1>
<h2 id="771-재고-감소">77.1 재고 감소</h2>
<p>요구사항:</p>
<pre><code class="language-text">재고는 0보다 작아질 수 없다.</code></pre>
<p>권장 방향:</p>
<pre><code class="language-sql">UPDATE products
SET stock = stock - 1
WHERE product_id = ?
  AND stock &gt; 0;</code></pre>
<p>영향받은 행 수:</p>
<pre><code class="language-text">1
→ 구매 성공

0
→ 재고 부족 또는 상품 없음</code></pre>
<p>원자적인 조건부 갱신으로 조회와 변경 사이의 경쟁을 줄인다.</p>
<hr />
<h2 id="772-마지막-좌석-예약">77.2 마지막 좌석 예약</h2>
<p>요구사항:</p>
<pre><code class="language-text">하나의 좌석에는 하나의 예약만 존재해야 한다.</code></pre>
<p>가능한 방법:</p>
<pre><code class="language-text">좌석 ID에 고유 제약조건
원자적 INSERT
충돌 시 예약 실패 처리</code></pre>
<p>단순히 다음처럼 처리하면 경쟁 조건이 생길 수 있다.</p>
<pre><code class="language-text">예약 존재 여부 SELECT
→ 없음 확인
→ INSERT</code></pre>
<p>두 트랜잭션이 동시에 “없음”을 확인할 수 있기 때문이다.</p>
<p>고유 제약조건은 마지막 방어선 역할을 한다.</p>
<hr />
<h2 id="773-문서-수정">77.3 문서 수정</h2>
<p>사용자가 문서를 오랫동안 편집할 수 있다.</p>
<p>이 동안 행 잠금을 유지하면 부적절하다.</p>
<pre><code class="language-text">문서 조회 시 version 확인
→ 사용자가 편집
→ 저장 시 version 조건으로 UPDATE
→ 변경되었으면 충돌 안내</code></pre>
<p>낙관적 잠금이 적합하다.</p>
<hr />
<h2 id="774-작업-큐">77.4 작업 큐</h2>
<p>여러 워커가 처리 대기 중인 작업을 나누어 가져가야 한다.</p>
<pre><code class="language-text">잠기지 않은 READY 작업 선택
→ 선택한 작업 잠금
→ 다른 워커는 잠긴 작업 건너뜀</code></pre>
<p>SKIP LOCKED 계열 처리가 적합할 수 있다.</p>
<p>다만 작업 상태 변경, 실패 복구, 재처리, 중복 실행 방지까지 함께 설계해야 한다.</p>
<hr />
<h2 id="775-계좌이체">77.5 계좌이체</h2>
<p>요구사항:</p>
<pre><code class="language-text">출금과 입금은 하나의 트랜잭션
잔액 부족이면 전체 취소
동일 계좌 동시 변경 제어</code></pre>
<p>주의사항:</p>
<pre><code class="language-text">두 계좌 잠금 순서 통일
조건부 잔액 감소
트랜잭션을 짧게 유지
외부 API 호출을 트랜잭션 안에서 장시간 수행하지 않음</code></pre>
<p>계좌를 항상 ID 순서로 잠그면 서로 반대 방향의 이체에서 발생하는 데드락 가능성을 낮출 수 있다.</p>
<hr />
<h1 id="78-격리수준-선택-기준">78. 격리수준 선택 기준</h1>
<h2 id="read-committed가-적합할-수-있는-경우">Read Committed가 적합할 수 있는 경우</h2>
<pre><code class="language-text">각 SQL 문장의 일관성만 중요
트랜잭션 내 반복 조회가 같은 결과일 필요 없음
높은 동시성이 중요
변경 시 조건부 UPDATE나 명시적 잠금 사용 가능</code></pre>
<p>예:</p>
<pre><code class="language-text">일반적인 단건 조회
독립적인 상태 변경
원자적 UPDATE</code></pre>
<hr />
<h2 id="repeatable-read-또는-snapshot이-적합할-수-있는-경우">Repeatable Read 또는 Snapshot이 적합할 수 있는 경우</h2>
<pre><code class="language-text">트랜잭션 전체에서 동일한 데이터 Snapshot 필요
여러 번 조회해도 같은 분석 결과 필요
장시간 읽기 작업에서 일관된 시점 필요</code></pre>
<p>주의:</p>
<pre><code class="language-text">Write Skew 가능성
구현별 Phantom 처리 차이
쓰기 충돌 시 실패 가능</code></pre>
<hr />
<h2 id="serializable이-적합할-수-있는-경우">Serializable이 적합할 수 있는 경우</h2>
<pre><code class="language-text">여러 행과 조건에 걸친 업무 규칙이 중요
Write Skew를 허용할 수 없음
동시 실행 결과가 반드시 직렬 가능해야 함
트랜잭션 재시도가 가능함</code></pre>
<p>주의:</p>
<pre><code class="language-text">잠금 대기 또는 직렬화 실패
재시도 로직 필요
긴 트랜잭션에서 충돌 증가</code></pre>
<hr />
<h1 id="79-동시성-제어-방식을-선택하는-질문">79. 동시성 제어 방식을 선택하는 질문</h1>
<p>다음 질문을 순서대로 검토하면 좋다.</p>
<pre><code class="language-text">1. 동시에 같은 데이터를 수정할 가능성이 높은가?

2. 읽은 뒤 애플리케이션에서 판단하고 나중에 수정하는가?

3. 하나의 행이 아니라 여러 행의 합계나 존재 조건이 중요한가?

4. 동일 행의 Lost Update만 막으면 되는가?

5. 서로 다른 행을 수정해도 업무 규칙이 깨질 수 있는가?

6. 충돌 시 기다리는 것이 좋은가, 빠르게 실패하는 것이 좋은가?

7. 트랜잭션을 자동으로 다시 실행할 수 있는가?

8. 사용자 편집 시간이 길어 데이터베이스 잠금을 유지하기 어려운가?

9. 제약조건이나 원자적 SQL로 문제를 해결할 수 있는가?

10. 외부 API나 메시지 발행 같은 부작용이 포함되는가?</code></pre>

<h1 id="81-자주-발생하는-오해">81. 자주 발생하는 오해</h1>
<h2 id="오해-1-트랜잭션을-사용하면-모든-동시성-문제가-해결된다">오해 1. 트랜잭션을 사용하면 모든 동시성 문제가 해결된다</h2>
<p>트랜잭션은 Atomicity와 복구 경계를 제공하지만 격리수준과 동시성 제어가 적절하지 않으면 Lost Update나 Write Skew가 발생할 수 있다.</p>
<pre><code class="language-text">BEGIN과 COMMIT 사용
≠
모든 동시성 문제 해결</code></pre>
<hr />
<h2 id="오해-2-격리수준이-높으면-무조건-기다리기만-한다">오해 2. 격리수준이 높으면 무조건 기다리기만 한다</h2>
<p>Serializable 구현은 잠금 대기뿐 아니라 위험한 트랜잭션을 실패시키는 방식도 사용할 수 있다.</p>
<pre><code class="language-text">높은 격리수준
→ 대기할 수 있음
→ 실패할 수 있음
→ 재시도가 필요할 수 있음</code></pre>
<hr />
<h2 id="오해-3-mvcc는-lock을-사용하지-않는다">오해 3. MVCC는 Lock을 사용하지 않는다</h2>
<p>MVCC는 읽기와 쓰기의 충돌을 줄이지만 쓰기 간 충돌, DDL, 제약조건 검사 등에는 잠금이나 다른 동시성 제어가 필요하다.</p>
<hr />
<h2 id="오해-4-repeatable-read는-모든-dbms에서-같은-의미다">오해 4. Repeatable Read는 모든 DBMS에서 같은 의미다</h2>
<p>SQL 표준의 최소 보장과 실제 구현은 다를 수 있다.</p>
<p>어떤 시스템은 Repeatable Read를 Lock 기반으로 구현하고, 다른 시스템은 Snapshot Isolation과 유사하게 구현할 수 있다.</p>
<hr />
<h2 id="오해-5-phantom이-없으면-serializable이다">오해 5. Phantom이 없으면 Serializable이다</h2>
<p>Snapshot 기반 격리에서는 같은 Snapshot을 계속 보기 때문에 Phantom이 관찰되지 않을 수 있다.</p>
<p>하지만 서로 다른 행을 변경하는 Write Skew가 발생할 수 있으므로 직렬 가능성이 완전히 보장된다고 할 수 없다.</p>
<hr />
<h2 id="오해-6-데드락은-잘못된-시스템에서만-발생한다">오해 6. 데드락은 잘못된 시스템에서만 발생한다</h2>
<p>데드락은 정상적인 잠금 기반 동시성 제어에서도 발생할 수 있다.</p>
<p>중요한 것은 데드락을 완전히 없애는 것뿐 아니라 다음을 갖추는 것이다.</p>
<pre><code class="language-text">발생 가능성을 줄이는 잠금 순서
탐지와 희생자 선택
전체 트랜잭션 재시도
적절한 Timeout
모니터링</code></pre>
<hr />
<h2 id="오해-7-재시도는-실패한-sql-하나만-다시-실행하면-된다">오해 7. 재시도는 실패한 SQL 하나만 다시 실행하면 된다</h2>
<p>직렬화 실패나 데드락이 발생하면 이전에 읽은 데이터와 판단이 더 이상 유효하지 않을 수 있다.</p>
<p>따라서 일반적으로 전체 트랜잭션을 처음부터 다시 실행해야 한다.</p>
<hr />
<h1 id="82-전체-핵심-흐름">82. 전체 핵심 흐름</h1>
<p>트랜잭션과 동시성 제어를 다음 흐름으로 이해할 수 있다.</p>
<pre><code class="language-text">여러 SQL을 하나의 논리적 작업으로 묶음
→ 트랜잭션

여러 트랜잭션을 동시에 실행
→ 성능과 처리량 향상

연산 순서가 섞임
→ 스케줄

동시 실행 결과가 직렬 실행과 같은지 판단
→ 직렬 가능성

부적절한 동시 실행
→ Dirty Read, Lost Update, Write Skew 등 발생

허용할 현상의 수준 선택
→ 격리수준

충돌을 제어하는 실제 방법
→ Lock, Timestamp, OCC, MVCC

잠금 순환
→ Deadlock

충돌 또는 직렬화 위험
→ 대기, 실패, 롤백, 재시도</code></pre>
<hr />
<h1 id="83-반드시-기억해야-할-핵심-문장">83. 반드시 기억해야 할 핵심 문장</h1>
<pre><code class="language-text">1. 트랜잭션은 여러 연산을 하나의 논리적 상태 전이로 묶는 단위다.

2. 동시성 제어의 목적은 동시 실행을 없애는 것이 아니라,
   정확성을 해치지 않는 범위에서 최대한 허용하는 것이다.

3. 직렬 스케줄은 안전하지만 동시성이 낮다.

4. 비직렬 스케줄도 어떤 직렬 스케줄과 동등하면 안전할 수 있다.

5. 선행 그래프에 사이클이 없으면 충돌 직렬 가능하다.

6. 직렬 가능성과 복구 가능성은 서로 다른 기준이다.

7. Strict Schedule은 Dirty Read와 Dirty Write,
   연쇄 롤백을 방지한다.

8. Dirty Read는 미커밋 값을 읽는 현상이다.

9. Non-Repeatable Read는 같은 행을 다시 읽었을 때
   값이 달라지는 현상이다.

10. Phantom Read는 같은 조건의 결과 집합이 달라지는 현상이다.

11. Lost Update는 한 트랜잭션의 변경이 다른 변경에 덮여
    사라지는 현상이다.

12. Read Skew는 서로 관련된 데이터를 서로 다른 시점으로
    읽어 일관되지 않은 상태를 보는 현상이다.

13. Write Skew는 서로 다른 행을 변경하더라도
    전체 업무 규칙을 위반할 수 있는 현상이다.

14. Snapshot Isolation은 Serializable과 동일하지 않다.

15. MVCC는 읽기와 쓰기의 충돌을 줄이지만
    쓰기 간 충돌 제어를 제거하지는 않는다.

16. 2PL은 잠금 획득 단계와 해제 단계를 분리해
    충돌 직렬 가능성을 보장한다.

17. Strict 2PL은 X Lock을 트랜잭션 종료까지 유지해
    복구를 단순하게 한다.

18. Phantom을 막으려면 현재 행뿐 아니라
    검색 조건이나 키 범위까지 보호해야 할 수 있다.

19. 데드락은 순환 대기로 발생하며,
    탐지 후 트랜잭션 하나를 롤백해 해결할 수 있다.

20. 잠금 순서를 통일하고 트랜잭션을 짧게 유지하면
    데드락과 잠금 경합을 줄일 수 있다.

21. Timestamp Ordering은 잠금 대신 논리적 시간 순서를 강제한다.

22. OCC는 일단 실행한 뒤 커밋 전에 충돌을 검증한다.

23. 충돌이 적으면 낙관적 방식이 유리할 수 있고,
    충돌이 많으면 비관적 방식이 유리할 수 있다.

24. Serializable이나 데드락 실패는 정상적인 동시성 제어 결과일 수 있다.

25. 재시도할 때는 실패한 SQL 하나가 아니라
    전체 트랜잭션을 다시 실행해야 한다.</code></pre>

<h1 id="84-최종-정리">84. 최종 정리</h1>
<p>데이터베이스 동시성 제어는 단순히 행에 잠금을 거는 기술이 아니다.</p>
<p>다음 문제를 함께 다루는 이론과 구현의 집합이다.</p>
<pre><code class="language-text">트랜잭션의 원자성과 복구
동시 실행 순서
직렬 가능성
미커밋 데이터 접근
동시 갱신 충돌
조건 범위의 보호
잠금 대기와 데드락
여러 데이터 버전의 가시성
충돌 검증과 재시도</code></pre>
<p>가장 중요한 구분은 다음과 같다.</p>
<pre><code class="language-text">격리수준
→ 사용자에게 어떤 동시성 보장을 제공할 것인가

동시성 제어 기법
→ 그 보장을 내부적으로 어떻게 구현할 것인가</code></pre>
<p>그리고 실무에서는 한 가지 기술만으로 모든 문제를 해결하지 않는다.</p>
<pre><code class="language-text">원자적 SQL
+
데이터베이스 제약조건
+
적절한 격리수준
+
비관적 또는 낙관적 충돌 제어
+
짧은 트랜잭션
+
재시도와 멱등성</code></pre>
<p>을 함께 설계해야 한다.</p>
<p>궁극적인 목표는 다음과 같다.</p>
<blockquote>
<p>여러 트랜잭션을 가능한 한 동시에 실행하면서도, 그 결과는 데이터베이스가 허용한 정확한 상태 중 하나로만 남게 하는 것.</p>
</blockquote>
<p>이 관점을 이해하면 격리수준을 단순한 네 단계의 암기표로 보는 것을 넘어, 왜 Lock·MVCC·Timestamp·OCC가 필요하고 각각 어떤 문제를 해결하는지 체계적으로 판단할 수 있다.</p>
