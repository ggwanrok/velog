<h2 id="데이터를-불러오는-것부터-분석하고-예측하고-자동화하기까지">데이터를 불러오는 것부터 분석하고, 예측하고, 자동화하기까지</h2>
<p>데이터 분석을 처음 공부하면 <code>Pandas</code>, <code>Matplotlib</code>, <code>Seaborn</code>, <code>scikit-learn</code>처럼 수많은 라이브러리를 먼저 접하게 된다.</p>
<p>그러다 보면 데이터 분석이 여러 라이브러리의 사용법을 배우는 일처럼 느껴지기 쉽다.</p>
<p>하지만 실제 분석은 라이브러리에서 시작하지 않는다.</p>
<p>데이터 분석의 시작은 <strong>질문</strong>이다.</p>
<pre><code class="language-text">무엇을 알고 싶은가?
        ↓
그 질문에 필요한 데이터는 무엇인가?
        ↓
데이터를 어디에서, 어떤 형태로 가져올 것인가?
        ↓
데이터는 분석할 수 있는 상태인가?
        ↓
어떤 특징과 패턴이 있는가?
        ↓
발견한 관계를 어느 정도 믿을 수 있는가?
        ↓
새로운 데이터에도 활용할 수 있는가?
        ↓
이 과정을 반복 가능하게 만들 수 있는가?</code></pre>
<p>Python의 여러 라이브러리는 결국 이 과정의 특정 단계를 해결하기 위한 도구들이다.</p>
<blockquote>
<p><strong>데이터 분석은 도구를 나열하는 과정이 아니라, 문제를 정의하고 데이터를 근거로 답을 만들어가는 과정이다.</strong></p>
</blockquote>
<hr />
<h1 id="데이터-분석의-목적">데이터 분석의 목적</h1>
<p>데이터가 많다고 바로 분석을 시작하는 것은 아니다.</p>
<p>가장 먼저 정해야 하는 것은</p>
<blockquote>
<p><strong>“이 데이터를 통해 무엇을 알고 싶은가?”</strong></p>
</blockquote>
<p>이다.</p>
<p>예를 들어 택시 운행 데이터가 있다고 해보자.</p>
<p>같은 데이터로도 전혀 다른 질문을 할 수 있다.</p>
<pre><code class="language-text">하루 중 택시 이용량이 가장 많은 시간은 언제인가?

어떤 지역에서 손님이 많이 탑승하는가?

운행거리가 길수록 요금도 증가하는가?

어떤 시간과 지역에서 운행하는 것이 수익성이 높은가?

시간과 지역만 보고 운행 효율을 미리 예측할 수 있는가?</code></pre>
<p>질문이 달라지면 이후 분석 방법도 달라진다.</p>
<p>예를 들어 <strong>수요가 높은 지역을 찾는 것</strong>이 목적이라면 운행 건수를 집계하면 된다.</p>
<p>하지만 <strong>택시기사의 입장에서 어디에서 운행하는 것이 효율적인지</strong> 알고 싶다면 운행 건수만으로는 부족하다.</p>
<p>손님이 많더라도 한 번 운행하는 데 시간이 오래 걸리거나 수익성이 낮다면 실제 운행 효율은 높지 않을 수 있기 때문이다.</p>
<p>NYC Taxi 데이터를 분석할 때도 단순 요금 예측보다</p>
<blockquote>
<p><strong>“택시기사의 입장에서 언제, 어디에서 손님을 태우는 것이 효율적인가?”</strong></p>
</blockquote>
<p>라는 문제를 정의하고, 수요와 시간당 수익을 함께 분석했다.</p>
<p>이처럼 <strong>문제 정의는 이후 모든 분석 판단의 기준</strong>이 된다.</p>
<pre><code class="language-text">분석 목적
   ↓
필요한 데이터
   ↓
정제 기준
   ↓
집계 기준
   ↓
통계 방법
   ↓
모델 입력</code></pre>
<p>좋은 데이터 분석은 모델을 먼저 고르는 것이 아니라 <strong>올바른 질문을 먼저 정하는 것</strong>에서 시작한다.</p>
<hr />
<h1 id="데이터-확보">데이터 확보</h1>
<p>문제가 정해졌다면 다음은 필요한 데이터를 확보하는 단계다.</p>
<p>이때 <strong>데이터의 출처</strong>와 <strong>데이터의 저장 형식</strong>을 구분해서 생각하면 이해하기 쉽다.</p>
<pre><code class="language-text">데이터의 출처
├─ File
├─ API
└─ Database

파일·응답의 데이터 형식
├─ CSV
├─ JSON
└─ Parquet</code></pre>
<p>예를 들어 API를 호출하면 JSON 형식의 응답을 받을 수 있고, 데이터베이스에 저장된 데이터를 SQL로 조회한 뒤 분석할 수도 있다.</p>
<hr />
<h2 id="csv">CSV</h2>
<p>CSV는 가장 익숙한 테이블 형태의 파일이다.</p>
<pre><code class="language-text">date,region,amount
2026-08-01,Seoul,12000
2026-08-01,Busan,18000
2026-08-02,Seoul,15000</code></pre>
<p>구조가 단순하고 사람이 직접 열어보기 쉬우며 거의 모든 데이터 도구에서 읽을 수 있다.</p>
<p>반면 파일 자체가 데이터 타입에 대한 정보를 충분히 가지고 있지 않기 때문에 날짜인지 문자열인지, 숫자인지 등을 데이터를 읽는 과정에서 다시 확인해야 할 수 있다.</p>
<p>또한 데이터가 커질수록 필요한 몇 개 컬럼만 분석하더라도 파일 전체를 읽는 비용이 부담이 될 수 있다.</p>
<hr />
<h2 id="json">JSON</h2>
<p>JSON은 API 통신에서 특히 많이 사용된다.</p>
<pre><code class="language-json">{
  &quot;date&quot;: &quot;2026-08-01&quot;,
  &quot;region&quot;: &quot;Seoul&quot;,
  &quot;amount&quot;: 12000
}</code></pre>
<p>CSV와 달리 객체와 배열을 이용해 중첩된 구조를 표현할 수 있다.</p>
<p>따라서 웹 API처럼 구조가 조금 복잡한 데이터를 주고받는 데 유리하다.</p>
<p>다만 실제 분석 단계에서는 필요한 필드를 꺼내 <strong>행과 열을 가진 테이블 형태</strong>로 정리하는 경우가 많다.</p>
<hr />
<h2 id="parquet">Parquet</h2>
<p>Parquet은 대규모 데이터 분석에서 특히 유용한 컬럼 기반 파일 형식이다.</p>
<p>예를 들어 50개의 컬럼이 있는 데이터에서</p>
<pre><code class="language-text">date
region
amount</code></pre>
<p>세 컬럼만 필요하다면 필요한 컬럼을 중심으로 읽을 수 있다.</p>
<p>또한 데이터 타입 정보와 압축을 지원하기 때문에 반복적인 대용량 분석에서는 CSV보다 효율적인 경우가 많다.</p>
<hr />
<h1 id="확보한-데이터를-python으로-불러오기">확보한 데이터를 Python으로 불러오기</h1>
<p>데이터를 확보했다고 바로 분석할 수 있는 것은 아니다.</p>
<p>파일이나 API 응답처럼 외부에 존재하는 데이터를 <strong>Python에서 계산할 수 있는 구조로 가져오는 과정</strong>이 필요하다.</p>
<p>가장 대표적인 방법이 Pandas의 <code>DataFrame</code>이다.</p>
<pre><code class="language-python">import pandas as pd

df = pd.read_csv(&quot;sales.csv&quot;)</code></pre>
<p>이 과정을 단순화하면 다음과 같다.</p>
<pre><code class="language-text">sales.csv
   ↓
파일 읽기
   ↓
행과 열 해석
   ↓
컬럼 구성
   ↓
데이터 타입 추론
   ↓
DataFrame 생성</code></pre>
<p>Parquet 파일도 비슷하다.</p>
<pre><code class="language-python">df = pd.read_parquet(&quot;sales.parquet&quot;)</code></pre>
<p>데이터의 출처가 달라지면 가져오는 방법도 달라진다.</p>
<pre><code class="language-text">File
→ read_csv / read_parquet
→ DataFrame

API
→ HTTP 요청
→ JSON 응답
→ 필요한 필드 정리
→ DataFrame

Database
→ SQL Query
→ 조회 결과
→ DataFrame</code></pre>
<hr />
<h2 id="dataframe이란">DataFrame이란?</h2>
<p>DataFrame은 <strong>행과 열을 가진 2차원 테이블 데이터를 Python에서 다루기 위한 구조</strong>다.</p>
<pre><code class="language-text">index    date          region    amount
0        2026-08-01    Seoul      12000
1        2026-08-01    Busan      18000
2        2026-08-02    Seoul      15000</code></pre>
<p>각 열은 하나의 변수 또는 속성을 나타내고, 각 행은 하나의 관측값을 나타낸다.</p>
<p>예를 들어 위 데이터에서는</p>
<pre><code class="language-text">컬럼
→ date, region, amount

하나의 행
→ 특정 날짜·지역의 하나의 관측</code></pre>
<p>이라고 볼 수 있다.</p>
<p>Pandas를 이용한 데이터 분석에서 대부분의 필터링, 집계, 결합, 통계 계산은 이 DataFrame을 중심으로 이루어진다.</p>
<hr />
<h1 id="데이터-구조-확인">데이터 구조 확인</h1>
<p>데이터를 불러온 뒤 바로 그래프를 그리거나 모델을 만들기보다 먼저 <strong>내가 제대로 된 데이터를 읽었는지 확인해야 한다.</strong></p>
<p>대표적으로 다음을 확인할 수 있다.</p>
<pre><code class="language-python">df.shape
df.head()
df.info()
df.describe()</code></pre>
<p>중요한 것은 함수 이름을 외우는 것이 아니라 각 함수가 어떤 질문에 답하기 위한 것인지 이해하는 것이다.</p>
<pre><code class="language-text">shape
→ 데이터가 몇 행, 몇 열인가?

head / sample
→ 실제 값은 어떤 모습인가?

info
→ 어떤 컬럼이 있는가?
→ 타입은 무엇인가?
→ 결측치는 있는가?

describe
→ 수치 데이터의 중심과 범위는 어떤가?</code></pre>
<p>예를 들어 금액 컬럼이 문자열로 들어왔다면 평균을 바로 계산할 수 없다.</p>
<p>날짜가 문자열로만 처리되어 있다면 시간, 요일, 월 등의 정보를 추출하기 어렵다.</p>
<p>따라서 분석의 초반 흐름은 다음과 같다.</p>
<pre><code class="language-text">Load
 ↓
Understand
 ↓
Clean
 ↓
Analyze</code></pre>
<hr />
<h1 id="다양한-분석도구">다양한 분석도구</h1>
<p>데이터를 가져온 뒤 처리하는 방법에는 여러 선택지가 있다.</p>
<p>대표적으로 <code>Pandas</code>, <code>Polars</code>, <code>DuckDB</code>를 생각할 수 있다.</p>
<p>이들을 각각 따로 외우기보다 <strong>현재 데이터의 크기와 처리 방식에 따라 선택하는 도구</strong>라고 이해하면 좋다.</p>
<hr />
<h2 id="pandas--데이터를-직접-살펴보며-분석하기-좋다">Pandas — 데이터를 직접 살펴보며 분석하기 좋다</h2>
<p>Pandas는 데이터를 DataFrame으로 다루면서 필터링, 집계, 결합, 통계 계산 등을 수행한다.</p>
<pre><code class="language-text">파일
 ↓
Pandas DataFrame
 ↓
필터
집계
결합
통계
시각화</code></pre>
<p>코드 한 줄씩 실행하면서 결과를 바로 확인하기 쉬워 EDA와 Notebook 기반 탐색에 특히 편리하다.</p>
<p>다른 Python 시각화·통계·머신러닝 라이브러리와 연결하기 쉽다는 것도 큰 장점이다.</p>
<p>다만 데이터가 매우 커지면 메모리 사용량과 처리 속도를 함께 고려해야 한다.</p>
<hr />
<h2 id="polars--큰-데이터를-효율적으로-처리한다">Polars — 큰 데이터를 효율적으로 처리한다</h2>
<p>Polars에서는 <code>Eager</code>와 <code>Lazy</code> 두 가지 실행 방식을 이해하는 것이 중요하다.</p>
<h3 id="eager">Eager</h3>
<p>명령을 작성하면 바로 실행한다.</p>
<pre><code class="language-text">읽기 → 실행
필터 → 실행
집계 → 실행</code></pre>
<p>결과를 단계별로 확인하기 편하다.</p>
<h3 id="lazy">Lazy</h3>
<p>반대로 Lazy 방식은 명령을 바로 계산하지 않는다.</p>
<pre><code class="language-text">읽기
 ↓
필터
 ↓
컬럼 선택
 ↓
집계
 ↓
실행 계획 최적화
 ↓
collect()
 ↓
실제 실행</code></pre>
<p>해야 할 작업을 먼저 모은 뒤 전체 흐름을 보고 실행 계획을 최적화한다.</p>
<p>대표적인 최적화가 <code>Predicate Pushdown</code>과 <code>Projection Pushdown</code>이다.</p>
<h3 id="predicate-pushdown">Predicate Pushdown</h3>
<p>필터 조건을 가능한 한 앞쪽에서 처리한다.</p>
<pre><code class="language-text">전체 1,000만 행 처리
→ 마지막에 10만 행 선택</code></pre>
<p>하는 것보다</p>
<pre><code class="language-text">필요한 10만 행 먼저 선택
→ 이후 연산 수행</code></pre>
<p>하는 것이 효율적이다.</p>
<h3 id="projection-pushdown">Projection Pushdown</h3>
<p>필요한 컬럼을 가능한 한 먼저 선택한다.</p>
<pre><code class="language-text">50개 컬럼 전체 처리</code></pre>
<p>보다</p>
<pre><code class="language-text">실제 분석에 필요한
date / region / amount
만 처리</code></pre>
<p>하는 것이 낭비를 줄일 수 있다.</p>
<p>즉 Polars의 Lazy 방식은 <strong>무엇을 계산할지 먼저 확인한 뒤 불필요한 작업을 줄이는 방식</strong>이라고 이해할 수 있다.</p>
<hr />
<h2 id="duckdb--파일을-sql로-직접-분석한다">DuckDB — 파일을 SQL로 직접 분석한다</h2>
<p>DuckDB는 DataFrame 중심의 Pandas나 Polars와 조금 다른 접근을 취한다.</p>
<p>CSV나 Parquet 파일을 별도의 서버형 데이터베이스에 먼저 적재하지 않고도 SQL로 직접 조회할 수 있다.</p>
<pre><code class="language-text">CSV / Parquet
      ↓
     SQL
      ↓
 필요한 결과</code></pre>
<p>예를 들어 다음과 같이 집계할 수 있다.</p>
<pre><code class="language-sql">SELECT
    region,
    SUM(amount)
FROM 'sales.parquet'
GROUP BY region;</code></pre>
<p>큰 파일에서 일부 집계 결과만 필요한 경우 모든 데이터를 먼저 Pandas DataFrame으로 올릴 필요가 없다.</p>
<p>또한 <code>JOIN</code>, <code>GROUP BY</code>, Window Function 등 SQL에 익숙한 분석을 그대로 활용할 수 있고, 최종 결과만 Pandas나 Polars로 가져올 수도 있다.</p>

<p>중요한 것은 특정 도구가 항상 가장 좋다는 것이 아니라 <strong>분석 목적과 데이터 규모에 따라 선택하는 것</strong>이다.</p>

<h1 id="데이터-전처리">데이터 전처리</h1>
<p>현실의 데이터는 바로 분석할 수 있을 정도로 깔끔하지 않은 경우가 많다.</p>
<p>대표적으로 다음과 같은 문제를 확인해야 한다.</p>
<pre><code class="language-text">결측치
중복
잘못된 타입
비정상 값
이상치
변수끼리 서로 맞지 않는 값</code></pre>
<p>이를 분석 목적에 맞는 형태로 정리하는 것이 데이터 전처리다.</p>
<hr />
<h2 id="결측치">결측치</h2>
<p>다음 데이터가 있다고 하자.</p>
<pre><code class="language-text">나이    소득
25      3500
32      NaN
41      5100</code></pre>
<p>단순히 비어 있는 값을 평균이나 중앙값으로 채울 수도 있다.</p>
<p>하지만 그 전에 더 중요한 질문이 있다.</p>
<blockquote>
<p><strong>왜 이 값이 비어 있는가?</strong></p>
</blockquote>
<pre><code class="language-text">실제로 측정하지 못했는가?

수집 시스템의 문제인가?

특정 조건의 데이터에서만 비는가?

애초에 정상적인 관측이 아닌가?</code></pre>
<p>원인과 분석 목적에 따라</p>
<pre><code class="language-text">제거
평균 대체
중앙값 대체
최빈값 대체
별도 범주 처리
그대로 유지</code></pre>
<p>등의 판단이 달라질 수 있다.</p>
<p>결측치는 단순히 <code>NaN</code>을 없애는 문제가 아니라 <strong>결측이 무엇을 의미하는지 해석하는 문제</strong>이기도 하다.</p>
<hr />
<h2 id="이상치">이상치</h2>
<p>대표적인 이상치 탐색 방법 중 하나가 IQR이다.</p>
<pre><code class="language-text">IQR = Q3 - Q1</code></pre>
<p>보통 다음 범위를 벗어난 값을 이상치 후보로 본다.</p>
<pre><code class="language-text">Q1 - 1.5 × IQR
~
Q3 + 1.5 × IQR</code></pre>
<p>하지만 이 기준을 벗어났다고 무조건 제거해야 하는 것은 아니다.</p>
<p>예를 들어 월 매출이 평소보다 매우 높게 나타났다면 데이터 오류일 수도 있지만,</p>
<pre><code class="language-text">대형 행사
프로모션
계절적 특수</code></pre>
<p>때문에 실제로 발생한 값일 수도 있다.</p>
<p>그래서 이상치는</p>
<pre><code class="language-text">통계적인 기준
        +
데이터가 현실에서 가져야 하는 의미</code></pre>
<p>를 함께 고려해야 한다.</p>
<hr />
<h2 id="하나의-컬럼만-봐서는-부족할-수-있다">하나의 컬럼만 봐서는 부족할 수 있다</h2>
<p>때로는 각 컬럼이 정상 범위에 있더라도 <strong>변수의 조합이 비현실적인 경우</strong>가 있다.</p>
<p>예를 들어 택시 데이터에서</p>
<pre><code class="language-text">거리
→ 정상 범위

운행 시간
→ 정상 범위</code></pre>
<p>라고 하더라도 두 값을 조합해 계산한 속도가 지나치게 높다면 정상적인 운행이라고 보기 어렵다.</p>
<pre><code class="language-text">거리 검증
+
시간 검증
+
거리 / 시간으로 계산한 평균속도 검증</code></pre>
<p>처럼 여러 변수의 관계를 함께 확인할 수 있다.</p>
<blockquote>
<p><strong>좋은 전처리는 이상한 숫자를 기계적으로 제거하는 과정이 아니라, 어떤 데이터를 정상적인 관측으로 인정할 것인지 정의하는 과정이다.</strong></p>
</blockquote>
<hr />
<h1 id="질문에-맞게-데이터-구조-변경">질문에 맞게 데이터 구조 변경</h1>
<p>정제가 끝났다고 원하는 답이 바로 나오는 것은 아니다.</p>
<p>택시 운행 데이터 수백만 행을 그대로 바라보면서</p>
<blockquote>
<p>어느 시간대가 가장 좋은가?</p>
</blockquote>
<p>라고 판단하기는 어렵다.</p>
<p>분석 질문에 맞는 단위로 데이터를 다시 정리해야 한다.</p>
<p>대표적으로 <code>GroupBy</code>, <code>Pivot Table</code>, <code>Merge</code>를 사용할 수 있다.</p>
<hr />
<h2 id="groupby--같은-기준끼리-묶는다">GroupBy — 같은 기준끼리 묶는다</h2>
<p>다음과 같은 질문을 생각해보자.</p>
<pre><code class="language-text">시간대별 운행 건수는?

지역별 총매출은?

요일별 평균 운행시간은?</code></pre>
<p>개별 행을 원하는 기준으로 그룹화한 뒤 집계하면 된다.</p>
<pre><code class="language-text">개별 운행
    ↓
시간 / 지역 / 요일별 그룹
    ↓
count / sum / mean</code></pre>
<p>즉 GroupBy는 <strong>개별 데이터를 집단 단위의 정보로 요약하는 과정</strong>이다.</p>
<hr />
<h2 id="pivot-table--두-기준의-조합을-본다">Pivot Table — 두 기준의 조합을 본다</h2>
<p>예를 들어 요일과 시간을 동시에 비교하고 싶다면 다음과 같은 형태로 데이터를 정리할 수 있다.</p>
<pre><code class="language-text">       0시  1시  2시 ... 23시
월
화
수
목
금
토
일</code></pre>
<p>이처럼 행과 열에 각각 기준을 두고 값을 집계하는 방식이 Pivot Table이다.</p>
<p>이 결과를 Heatmap으로 표현하면 <strong>요일 × 시간 조합에서 어느 구간의 수요가 높은지</strong> 한눈에 확인할 수 있다.</p>
<hr />
<h2 id="merge--서로-다른-데이터를-연결한다">Merge — 서로 다른 데이터를 연결한다</h2>
<p>하나의 데이터에 모든 정보가 들어 있는 경우는 많지 않다.</p>
<p>예를 들어 택시 운행 데이터에는 <code>PULocationID</code>만 있고 실제 지역 이름은 별도 데이터에 존재할 수 있다.</p>
<pre><code class="language-text">운행 데이터
PULocationID
        +
지역 정보
PULocationID → 지역명
        ↓
결합된 데이터</code></pre>
<p>이때 두 데이터를 공통 키를 기준으로 연결한다.</p>
<p>SQL의 <code>JOIN</code>과 같은 개념이다.</p>
<hr />
<h1 id="eda">EDA</h1>
<p>전처리와 데이터 구조 변환을 마쳤다면 본격적으로 데이터를 탐색할 수 있다.</p>
<p>EDA(Exploratory Data Analysis)의 목적은</p>
<blockquote>
<p><strong>데이터가 어떤 모습을 가지고 있고, 어떤 패턴과 관계가 존재하는지 탐색하는 것</strong></p>
</blockquote>
<p>이다.</p>
<p>EDA에서는 크게 두 가지 접근을 함께 사용한다.</p>
<pre><code class="language-text">숫자로 요약
→ 기술통계

눈으로 확인
→ 시각화</code></pre>
<p>둘 중 하나만 사용하는 것이 아니라 서로를 보완한다.</p>
<hr />
<h2 id="기술통계">기술통계</h2>
<p>기술통계는 현재 가지고 있는 데이터를 요약한다.</p>
<p>크게 <strong>중심, 퍼짐, 분포의 형태</strong>를 살펴볼 수 있다.</p>
<h3 id="중심">중심</h3>
<pre><code class="language-text">평균
중앙값
최빈값</code></pre>
<p>데이터가 어느 지점에 모여 있는지를 본다.</p>
<p>평균은 모든 값을 반영한다는 장점이 있지만 이상치의 영향을 크게 받을 수 있다.</p>
<p>중앙값은 데이터를 크기순으로 정렬했을 때 가운데에 위치한 값이므로 극단적인 값의 영향을 상대적으로 덜 받는다.</p>
<p>따라서 평균과 중앙값의 차이가 크다면 데이터가 한쪽으로 치우쳐 있거나 이상치가 존재하는지 추가로 확인해볼 수 있다.</p>
<h3 id="퍼짐">퍼짐</h3>
<pre><code class="language-text">분산
표준편차
범위
IQR</code></pre>
<p>은 데이터가 중심을 기준으로 얼마나 흩어져 있는지 보여준다.</p>
<pre><code class="language-text">A : 49, 50, 51

B : 10, 50, 90</code></pre>
<p>두 데이터의 평균은 모두 50이지만 퍼짐은 전혀 다르다.</p>
<p>평균만으로는 데이터의 전체 모습을 설명할 수 없는 이유다.</p>
<h3 id="분포의-형태">분포의 형태</h3>
<pre><code class="language-text">왜도
첨도</code></pre>
<p>등을 통해 분포가 한쪽으로 치우쳐 있는지, 극단적인 값이 얼마나 나타나는지 등을 살펴볼 수 있다.</p>
<p><code>describe()</code>를 활용하면 데이터 개수, 평균, 표준편차, 최솟값·최댓값과 분위수를 한 번에 확인할 수 있다.</p>
<p>중앙값은 50% 분위수로 확인할 수 있으며, 분산·IQR·왜도·첨도 등은 필요한 경우 별도로 계산해 분포를 더 자세히 살펴볼 수 있다.</p>
<hr />
<h2 id="시각화">시각화</h2>
<p>숫자만으로 데이터의 전체 형태를 이해하기는 어렵다.</p>
<p>그래서 기술통계와 함께 시각화를 사용한다.</p>
<p>중요한 것은 그래프 이름을 외우는 것이 아니라 <strong>현재 질문에 맞는 그래프를 고르는 것</strong>이다.</p>
<table>
<thead>
<tr>
<th>알고 싶은 것</th>
<th>대표적인 시각화</th>
</tr>
</thead>
<tbody><tr>
<td>하나의 값은 어떻게 분포하는가?</td>
<td>Histogram</td>
</tr>
<tr>
<td>중앙값·범위·이상치는?</td>
<td>Box Plot</td>
</tr>
<tr>
<td>범주마다 값이 다른가?</td>
<td>Bar / Box Plot</td>
</tr>
<tr>
<td>두 수치형 변수는 어떤 관계가 있는가?</td>
<td>Scatter Plot</td>
</tr>
<tr>
<td>요일 × 시간 같은 조합의 패턴은?</td>
<td>Heatmap</td>
</tr>
<tr>
<td>시간이 지나며 어떻게 변하는가?</td>
<td>Line Plot</td>
</tr>
</tbody></table>
<p>예를 들어 Histogram의 오른쪽 꼬리가 길다면 일부 큰 값이 평균에 영향을 미치고 있을 가능성을 생각할 수 있다.</p>
<p>Box Plot에서 특정 집단에 이상치가 유난히 많다면 해당 집단을 따로 살펴볼 수 있다.</p>
<p>Scatter Plot에서 두 변수가 함께 증가하는 패턴이 보인다면 상관관계를 계산해볼 수 있다.</p>
<p>즉 EDA는 다음처럼 이어진다.</p>
<pre><code class="language-text">기술통계
→ 숫자로 특징 확인

시각화
→ 형태와 패턴 발견

두 결과를 함께 해석</code></pre>
<p><code>Seaborn</code>은 Histogram, Box Plot, Heatmap 등 통계적 시각화를 편리하게 만들 수 있고, <code>Plotly</code>는 Hover, 확대·축소가 가능한 인터랙티브 시각화에 활용할 수 있다.</p>

</blockquote>

<h1 id="발견한-관계를-통계적으로-확인한다">발견한 관계를 통계적으로 확인한다</h1>
<p>EDA에서 패턴이 보였다고 해서 바로 결론을 내릴 수 있는 것은 아니다.</p>
<p>예를 들어 그래프에서</p>
<pre><code class="language-text">피크 시간대 평균 수익
&gt;
비피크 시간대 평균 수익</code></pre>
<p>처럼 보일 수 있다.</p>
<p>하지만 이 차이가 단순한 표본의 우연인지, 일정한 근거가 있는 차이인지 추가로 확인할 필요가 있다.</p>
<p>이때 추론통계와 가설검정을 활용할 수 있다.</p>
<hr />
<h2 id="상관관계">상관관계</h2>
<p>상관계수는 두 수치형 변수가 함께 움직이는 방향과 정도를 확인하는 데 사용한다.</p>
<pre><code class="language-text">+1에 가까움
→ 함께 증가하는 선형 경향이 강함

-1에 가까움
→ 하나가 증가할 때 다른 하나가 감소하는 선형 경향이 강함

0에 가까움
→ 선형적인 관계가 약함</code></pre>
<p>다만 <strong>상관관계가 존재한다고 인과관계가 증명되는 것은 아니다.</strong></p>
<p>상관분석은 관계를 발견하는 도구이지 원인을 확정하는 도구는 아니다.</p>
<hr />
<h2 id="t-test">t-test</h2>
<p>두 집단의 평균 차이를 검정할 때 t-test를 사용할 수 있다.</p>
<pre><code class="language-text">H0
→ 두 집단의 평균 차이가 없다.

H1
→ 두 집단의 평균 차이가 있다.</code></pre>
<p>p-value는 <strong>귀무가설이 참이라고 가정했을 때, 현재 관찰한 결과와 같거나 더 극단적인 결과가 나타날 가능성</strong>을 나타낸다.</p>
<p>미리 정한 유의수준보다 p-value가 충분히 작다면 관찰된 결과를 단순한 우연만으로 설명하기 어렵다고 판단하고 귀무가설을 기각한다.</p>
<p>하지만 여기서 중요한 점이 있다.</p>
<blockquote>
<p><strong>통계적으로 유의하다 = 실제 차이가 크다</strong></p>
</blockquote>
<p>는 의미가 아니다.</p>
<p>NYC Taxi 분석에서도 혼잡 시간대와 다른 시간대의 추천 점수 평균을 비교했을 때 p-value는 매우 작았지만, 실제 평균은 약 <code>0.369</code>와 <code>0.375</code>로 차이가 크지 않았다.</p>
<p>따라서 다음 두 질문을 구분해야 한다.</p>
<pre><code class="language-text">통계적으로 차이가 존재한다고 볼 근거가 있는가?
        +
그 차이가 실제로도 의미 있을 만큼 큰가?</code></pre>
<p>데이터가 매우 많다면 아주 작은 차이도 통계적으로 유의하게 나타날 수 있기 때문이다.</p>
<hr />
<h2 id="카이제곱-검정">카이제곱 검정</h2>
<p>두 범주형 변수 사이의 관계를 확인할 때 카이제곱 검정을 사용할 수 있다.</p>
<p>예를 들어</p>
<pre><code class="language-text">지역
×
구매 여부</code></pre>
<p>처럼 두 범주의 분포가 서로 독립적인지를 확인할 수 있다.</p>
<p>결국 통계 분석은 단순히 p-value를 계산하는 작업이 아니라</p>
<blockquote>
<p><strong>EDA에서 발견한 패턴을 어느 정도까지 믿을 수 있는지 확인하는 과정</strong></p>
</blockquote>
<p>이라고 볼 수 있다.</p>
<hr />
<h1 id="필요하다면-머신러닝으로-확장한다">필요하다면 머신러닝으로 확장한다</h1>
<p>여기까지 분석했는데 질문에 대한 답을 얻었다면 반드시 머신러닝까지 사용할 필요는 없다.</p>
<p>예를 들어</p>
<blockquote>
<p>어느 시간대의 평균 수익이 가장 높은가?</p>
</blockquote>
<p>라는 질문은 집계와 통계 분석만으로도 답할 수 있다.</p>
<p>머신러닝은 질문이 다음 단계로 넘어갈 때 필요하다.</p>
<pre><code class="language-text">현재 데이터에서 어떤 패턴이 있는가?</code></pre>
<p>에서</p>
<pre><code class="language-text">이 패턴을 이용해
새로운 데이터의 결과도 예측할 수 있는가?</code></pre>
<p>로 문제를 확장하는 것이다.</p>
<hr />
<h2 id="모델이-사용할-수-있는-형태로-데이터를-조정한다">모델이 사용할 수 있는 형태로 데이터를 조정한다</h2>
<p>머신러닝 모델에는 데이터를 모델이 이해할 수 있는 형태로 넣어야 한다.</p>
<p>예를 들어 다음 컬럼이 있다고 하자.</p>
<pre><code class="language-text">hour
weekday
location
income</code></pre>
<p><code>income</code>은 값의 크기 차이가 실제 의미를 가진다.</p>
<p>하지만 <code>location=200</code>이 <code>location=100</code>보다 두 배 큰 지역이라는 의미는 아니다.</p>
<p>숫자로 저장되어 있지만 실제 의미는 <strong>범주형 데이터</strong>다.</p>
<p>따라서 변수의 의미에 따라 다른 전처리가 필요할 수 있다.</p>
<pre><code class="language-text">수치형
→ 결측치 처리
→ Scaling

범주형
→ 결측치 처리
→ One-Hot Encoding</code></pre>
<p><code>ColumnTransformer</code>를 이용하면 수치형 컬럼과 범주형 컬럼에 서로 다른 전처리를 적용한 뒤 하나의 모델 입력으로 합칠 수 있다.</p>
<hr />
<h2 id="학습-데이터와-평가-데이터를-나눈다">학습 데이터와 평가 데이터를 나눈다</h2>
<p>모델을 학습시킨 데이터로 다시 성능을 측정하면 모델이 새로운 데이터에서도 잘 작동하는지 알기 어렵다.</p>
<p>따라서 일반적으로 데이터를 학습용과 평가용으로 나눈다.</p>
<pre><code class="language-text">전체 데이터
   ↓
Train
→ 모델 학습

Test
→ 학습하지 않은 데이터에서 평가</code></pre>
<p>특히 시간의 흐름이 있는 데이터라면 무작위 분할만 사용하는 것도 주의해야 한다.</p>
<p>실제 서비스에서는 과거 정보를 이용해 미래를 예측하는 경우가 많기 때문이다.</p>
<pre><code class="language-text">과거 데이터
→ Train

미래 데이터
→ Test</code></pre>
<p>처럼 시간 순서를 유지하면 실제 예측 상황과 더 가까운 조건에서 평가할 수 있다.</p>
<hr />
<h2 id="data-leakage--예측-시점에-알-수-없는-정보는-넣지-않는다">Data Leakage — 예측 시점에 알 수 없는 정보는 넣지 않는다</h2>
<p>머신러닝에서 특히 조심해야 하는 것이 <code>Data Leakage</code>다.</p>
<p>예측하려는 순간에는 아직 알 수 없는 정보가 모델 입력에 포함되면 실제 서비스에서는 사용할 수 없는 모델이 만들어질 수 있다.</p>
<p>예를 들어 택시가 승객을 태우기 전에 효율적인 승차 위치를 추천한다고 하자.</p>
<pre><code class="language-text">시간
요일
현재 승차 지역
→ 예측 시점에 알 수 있음

실제 운행거리
실제 운행시간
최종 요금
→ 운행이 끝난 뒤 알 수 있음</code></pre>
<p>후자의 정보를 모델 입력으로 사용하면 평가 성능은 높게 나올 수 있지만 실제 추천 시점에는 사용할 수 없다.</p>
<p>따라서 Feature를 고를 때는 항상</p>
<blockquote>
<p><strong>“이 값은 예측하는 바로 그 순간에 실제로 알 수 있는가?”</strong></p>
</blockquote>
<p>를 확인해야 한다.</p>
<hr />
<h2 id="sklearn-pipeline">sklearn Pipeline</h2>
<p>머신러닝에서는 전처리와 모델을 각각 따로 실행할 수도 있다.</p>
<p>하지만 학습할 때</p>
<pre><code class="language-text">결측치 처리
→ Scaling
→ Encoding
→ 모델 학습</code></pre>
<p>을 수행하고 실제 예측에서는 Scaling이나 Encoding을 하나 빠뜨린다면 학습 당시와 입력 조건이 달라진다.</p>
<p>이를 방지하기 위해 scikit-learn에서는 <strong>전처리와 모델을 하나의 객체로 연결</strong>할 수 있다.</p>
<pre><code class="language-text">             ┌→ 수치형 처리 ─┐
입력 데이터 ─┤               ├→ 모델 → 예측
             └→ 범주형 처리 ─┘</code></pre>
<p><code>ColumnTransformer</code>를 이용해 수치형과 범주형 컬럼의 전처리를 정의한 뒤 모델과 함께 <code>Pipeline</code>으로 묶는다.</p>
<pre><code class="language-text">sklearn Pipeline
┌────────────────────┐
│ ColumnTransformer  │
│        ↓           │
│      Model         │
└────────────────────┘
        ↓
   fit / predict</code></pre>
<h3 id="sklearn-pipeline의-핵심">sklearn Pipeline의 핵심</h3>
<p>Pipeline을 사용하는 이유는 단순히 코드를 짧게 만드는 데 있지 않다.</p>
<blockquote>
<p><strong>학습할 때 사용한 전처리 과정과 실제 예측할 때 사용되는 전처리 과정을 동일하게 보장하는 것</strong></p>
</blockquote>
<p>이 핵심이다.</p>
<hr />
<h2 id="모델을-평가한다">모델을 평가한다</h2>
<p>모델을 학습한 뒤에는 학습에 사용하지 않은 데이터에서 어느 정도의 성능을 보이는지 확인해야 한다.</p>
<p>회귀 문제에서는 대표적으로 <code>MAE</code>, <code>RMSE</code>, <code>R²</code> 같은 지표를 사용할 수 있다.</p>
<pre><code class="language-text">MAE
→ 실제값과 예측값이 평균적으로 얼마나 차이나는가?

RMSE
→ 큰 오차에 더 큰 영향을 주어 평가

R²
→ Target의 변동을 모델이 어느 정도 설명하는가?</code></pre>
<p>중요한 것은 평가 지표 하나만 높게 만드는 것이 아니다.</p>
<pre><code class="language-text">왜 이 정도의 성능이 나왔는가?

어떤 Feature가 예측에 도움이 되었는가?

실제 예측 시점에도 사용할 수 있는 Feature인가?

현재 오차가 실제 문제에서 허용 가능한 수준인가?</code></pre>
<p>까지 함께 해석해야 한다.</p>
<hr />
<h2 id="재사용성">재사용성</h2>
<p>학습이 끝난 Pipeline을 프로그램을 실행할 때마다 다시 학습할 필요는 없다.</p>
<p><code>joblib</code>을 이용하면 전처리와 모델이 묶인 Pipeline 전체를 저장할 수 있다.</p>
<pre><code class="language-text">sklearn Pipeline
[결측치 처리 + Encoding + Scaling + Model]
    ↓
model.joblib</code></pre>
<p>이후 파일을 다시 불러와 동일한 전처리와 모델을 그대로 사용할 수 있다.</p>
<p>모델만 저장하는 것이 아니라 <strong>모델이 기대하는 전처리까지 함께 저장할 수 있다는 점</strong>이 중요하다.</p>
<hr />
<h1 id="데이터-분석-pipeline">데이터 분석 Pipeline</h1>
<p>지금까지 수행한 분석을 다시 보면 다음과 같다.</p>
<pre><code class="language-text">데이터 가져오기
→ 구조 확인
→ 정제
→ 집계
→ EDA
→ 통계 분석
→ 필요하다면 머신러닝
→ 결과 저장</code></pre>
<p>한 번만 수행하는 분석이라면 Notebook에서 사람이 직접 순서대로 실행해도 충분할 수 있다.</p>
<p>하지만 같은 분석을 매일 또는 매주 반복해야 한다면 상황이 달라진다.</p>
<p>각 단계를 함수와 모듈로 분리하고 정해진 순서로 연결하면 하나의 <strong>데이터 분석 Pipeline</strong>을 만들 수 있다.</p>
<blockquote>
<img height="50%" src="https://velog.velcdn.com/images/klmcw1004/post/0fa25bdf-6911-4791-a5ea-bd7052226700/image.png" width="70%" />
</blockquote>
<hr />
<h2 id="1-extract--데이터를-가져온다">1. Extract — 데이터를 가져온다</h2>
<p>분석에 필요한 데이터를 외부에서 가져오는 단계다.</p>
<pre><code class="language-text">File
API
Database</code></pre>
<p>파일 형식으로는 CSV, JSON, Parquet 등을 사용할 수 있다.</p>
<p>이 단계의 목적은 이후 단계가 동일한 방식으로 처리할 수 있도록 <strong>분석의 입력 데이터를 확보하는 것</strong>이다.</p>
<hr />
<h2 id="2-validate--데이터가-예상한-형태인지-검증한다">2. Validate — 데이터가 예상한 형태인지 검증한다</h2>
<p>데이터를 가져왔다고 바로 사용할 수 있는 것은 아니다.</p>
<pre><code class="language-text">필수 컬럼이 존재하는가?

amount는 숫자인가?

허용되지 않는 값은 없는가?

날짜 형식은 정상적인가?</code></pre>
<p>처럼 입력 데이터의 형태와 기본 규칙을 확인해야 한다.</p>
<p>이 단계에서 Pydantic 같은 데이터 모델링 도구를 이용해 API JSON이나 CSV 행의 타입과 필수값을 검증할 수도 있다.</p>
<p>Validate의 목적은 <strong>잘못된 데이터가 뒤쪽 분석 단계까지 흘러가 문제를 만드는 것을 조기에 막는 것</strong>이다.</p>
<hr />
<h2 id="3-transform--분석-가능한-형태로-바꾼다">3. Transform — 분석 가능한 형태로 바꾼다</h2>
<p>검증된 데이터를 실제 분석 질문에 맞게 정리한다.</p>
<pre><code class="language-text">결측치 처리
이상치 처리
타입 변환
파생변수 생성
GroupBy
Pivot
Merge</code></pre>
<p>등이 포함될 수 있다.</p>
<p>앞에서 살펴본 데이터 전처리와 구조 변환이 이 단계에 해당한다.</p>
<hr />
<h2 id="4-analyze--데이터를-해석한다">4. Analyze — 데이터를 해석한다</h2>
<p>정리된 데이터를 이용해 실제 질문에 답하는 단계다.</p>
<pre><code class="language-text">EDA
기술통계
시각화
상관분석
가설검정
머신러닝
모델 평가</code></pre>
<p>등이 들어갈 수 있다.</p>
<p>모든 분석에서 머신러닝을 사용해야 하는 것은 아니며, 문제에 따라 EDA와 통계 분석에서 끝날 수도 있다.</p>
<hr />
<h2 id="5-report--결과를-사용할-수-있는-형태로-남긴다">5. Report — 결과를 사용할 수 있는 형태로 남긴다</h2>
<p>분석이 끝나면 결과를 사람이 확인하거나 다른 프로그램에서 다시 사용할 수 있는 형태로 저장한다.</p>
<pre><code class="language-text">CSV
Parquet
Chart
Markdown
HTML
Model File</code></pre>
<p>분석 자체가 잘 되었더라도 결과가 전달되지 않는다면 실제 활용으로 이어지기 어렵다.</p>
<p>Report 단계는 <strong>분석 결과를 산출물로 만드는 단계</strong>라고 볼 수 있다.</p>
<hr />
<h1 id="pipeline을-자동으로-실행한다">Pipeline을 자동으로 실행한다</h1>
<p>Pipeline은</p>
<blockquote>
<p><strong>무엇을 어떤 순서로 실행할 것인가</strong></p>
</blockquote>
<p>를 정의한다.</p>
<p>하지만 Pipeline을 만들었다고 자동으로 실행되는 것은 아니다.</p>
<p>자동화는</p>
<blockquote>
<p><strong>그 Pipeline을 언제, 어떤 주기로 실행할 것인가</strong></p>
</blockquote>
<p>에 대한 문제다.</p>
<pre><code class="language-text">Pipeline
→ 실행 순서

Automation
→ 실행 시점과 반복 주기</code></pre>
<p>예를 들어 매일 오전 8시에 분석 Pipeline을 실행하고 싶다면 Python의 <code>schedule</code>을 사용할 수 있다.
이 방식은 Python 프로그램이 실행 중인 상태에서 정해진 시간을 확인해 작업을 실행한다.</p>
<p>반면 운영체제 수준에서는 <code>cron</code>이나 macOS의 <code>launchd</code> 등을 이용할 수 있다.</p>
<pre><code class="language-text">schedule
→ 실행 중인 Python 프로그램 내부에서 주기 관리

cron / launchd
→ 운영체제가 정해진 시간에 Python 프로그램 자체를 실행</code></pre>
<p>즉 Pipeline 그림에서 <code>Automation</code>은 특정 한 단계가 아니라</p>
<pre><code class="language-text">Extract
→ Validate
→ Transform
→ Analyze
→ Report</code></pre>
<p>전체 Pipeline을 반복 실행시키는 바깥쪽 역할이라고 이해하면 된다.</p>
<hr />
<h1 id="report-자동화--jinja2">Report 자동화 — Jinja2</h1>
<p>분석 결과가 자동으로 계산되어도 사람이 매번 숫자와 그래프를 복사해 보고서를 작성한다면 반복 작업이 남아 있다.</p>
<p>Jinja2 같은 템플릿 엔진을 이용하면 분석 결과를 미리 만들어 둔 HTML 양식에 자동으로 삽입할 수 있다.</p>
<pre><code class="language-text">분석 결과
+
HTML Template
        ↓
자동 Report</code></pre>
<p>예를 들어 Template을 다음처럼 만들어 둘 수 있다.</p>
<pre><code class="language-text">오늘 매출: {{ revenue }}

전일 대비: {{ change }}

지역별 TOP 5:
{{ ranking }}

[매출 그래프]</code></pre>
<p>그러면 Python이 계산한 값과 생성한 차트를 이용해 동일한 구조의 보고서를 반복해서 만들 수 있다.</p>
<hr />
<h1 id="안정적인-pipeline-운영법">안정적인 Pipeline 운영법</h1>
<p>사람이 직접 프로그램을 실행한다면 화면에 발생한 오류를 바로 확인할 수 있다.</p>
<p>하지만 새벽에 자동 실행되는 Pipeline이라면 그렇지 않다.</p>
<p>따라서 실행 과정의 상태를 기록해야 한다.</p>
<pre><code class="language-text">INFO
→ 데이터 읽기 완료
→ 전처리 완료
→ 리포트 생성 완료

WARNING
→ 일부 데이터 검증 실패

ERROR
→ API 요청 실패
→ 파일 저장 실패</code></pre>
<p>이런 기록을 <code>logging</code>으로 남기면 어느 단계에서 문제가 발생했는지 확인하기 쉽다.</p>
<p>또 각 단계가 독립적인 함수로 나뉘어 있다면 테스트도 가능하다.</p>
<pre><code class="language-text">결측치가 예상한 방식으로 처리되는가?

잘못된 값이 제거되는가?

필수 컬럼이 없을 때 오류가 발생하는가?

<h1 id="마치며">마치며</h1>
<p>데이터 분석을 처음 배우면 <code>Pandas</code>에서 어떤 함수를 쓰는지, 어떤 그래프를 그려야 하는지에 집중하기 쉽다.</p>
<p>하지만 하나의 분석을 처음부터 끝까지 수행해보면 더 중요한 것은 따로 있다.</p>
<p>먼저 <strong>무엇을 알고 싶은지 정의하고</strong>, 그 질문에 필요한 데이터를 확보해야 한다.</p>
<p>그다음 데이터를 바로 믿는 것이 아니라 구조와 품질을 확인하고, 결측치와 이상치를 분석 목적에 맞게 처리해야 한다.</p>
<p>정리된 데이터는 기술통계와 시각화를 통해 탐색하고, 발견한 관계는 필요한 경우 통계적으로 검정한다.</p>
<p>그리고 문제의 목적이 새로운 데이터에 대한 예측까지 이어진다면 머신러닝을 연결한다.</p>
<pre><code class="language-text">문제 정의
→ 데이터 확보
→ 데이터 검증
→ 전처리
→ EDA
→ 통계 분석
→ 필요하다면 머신러닝</code></pre>
<p>여기까지가 <strong>데이터를 이용해 문제에 답하는 분석 과정</strong>이다.</p>
<p>그리고 이 과정을 반복해서 사용할 필요가 생기면</p>
<pre><code class="language-text">Extract
→ Validate
→ Transform
→ Analyze
→ Report</code></pre>
<p>처럼 각 단계를 분리해 하나의 <strong>데이터 분석 Pipeline</strong>으로 구성할 수 있다.</p>
<p>여기에</p>
<pre><code class="language-text">schedule / cron
→ 반복 실행

logging
→ 실행 상태 기록

test
→ 각 단계의 결과 검증</code></pre>
<p>을 추가하면 분석은 한 번 실행하고 끝나는 Notebook에서 <strong>반복해서 신뢰할 수 있게 실행하는 하나의 시스템</strong>으로 발전한다.</p>
