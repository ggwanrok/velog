<p>RAG에서 가장 먼저 구현하는 검색은 보통 Vector Search다.</p>
<p>질문과 문서를 Embedding Vector로 변환하고, 서로 가까운 문서를 Top-K로 가져온다.</p>
<p>구조가 단순해서 시작하기 좋지만, 실제 질문을 넣어보면 다음과 같은 문제가 발생한다.</p>
<pre><code class="language-text">질문에 정확한 코드가 있는데 검색되지 않는다.

의미가 비슷한 문서가 너무 많이 검색된다.

상위 결과가 모두 같은 내용을 반복한다.

오래된 문서가 최신 문서보다 높은 순위에 올라온다.</code></pre>
<p>따라서 Retrieval은 Vector Search 하나만으로 완성되는 것이 아니다.</p>
<p>이번 글에서는 Dense Retrieval, Sparse Retrieval, Hybrid Search, MMR, Re-ranking과 Query Transformation을 비교해 본다.</p>
<h2 id="vector-search">Vector Search</h2>
<p>Vector Search는 질문과 문서를 같은 Embedding 공간으로 변환한 뒤 의미적 유사도를 계산한다.</p>
<pre><code class="language-text">질문: 휴가를 등록하는 방법
문서: 연차 신청 절차</code></pre>
<p>두 문장이 같은 단어를 사용하지 않아도 의미가 비슷하면 검색될 수 있다.</p>
<pre><code class="language-pseudo">query_vector = embed(question)

results = vector_store.search(
    vector = query_vector,
    top_k = 5
)</code></pre>
<p>Vector Search의 장점은 표현이 다른 질문과 문서를 연결할 수 있다는 것이다.</p>
<pre><code class="language-text">&quot;휴가를 올리는 방법&quot;

        ↓

&quot;연차 신청 절차&quot;</code></pre>
<p>하지만 다음과 같은 검색에서는 약할 수 있다.</p>
<pre><code class="language-text">SKA-3928
HTTP 429
RFC-9457
v2.3.1
제17조</code></pre>
<p>이런 값들은 의미가 비슷한지보다 정확하게 포함되어 있는지가 중요하다.</p>
<h3 id="유사도는-확률이-아니다">유사도는 확률이 아니다</h3>
<p>Vector Search의 Score는 문서가 정답일 확률이 아니다.</p>
<p>일반적으로 질문 Vector와 문서 Vector 사이의 거리를 변환한 값이므로, 같은 Score라도 Embedding Model과 데이터 분포와 거리 함수에 따라 의미가 달라진다.</p>
<pre><code class="language-text">질문 A
Top 1: 0.91 관련 문서

질문 B
Top 1: 0.72 무관 문서</code></pre>
<p>두 질문의 Score를 서로 비교해 “A가 B보다 0.19만큼 더 정답에 가깝다”고 해석할 수는 없다. Score는 같은 검색 조건 안에서 후보를 정렬하는 신호로 사용하고, 실제 관련성은 평가 질문과 근거 내용을 통해 확인해야 한다.</p>
<p>또한 질문과 문서에 서로 다른 Embedding Model을 사용하거나, 적재 당시의 모델과 검색 당시의 모델이 달라지면 같은 공간에서 비교한다는 전제가 깨진다.</p>
<h2 id="keyword-search">Keyword Search</h2>
<p>Keyword Search는 질문에 포함된 단어가 문서에 어떻게 등장하는지를 기준으로 검색한다.</p>
<p>대표적인 방식으로 BM25가 있다.</p>
<pre><code class="language-pseudo">results = keyword_index.search(
    query = question,
    top_k = 5
)</code></pre>
<p>BM25는 단어의 등장 빈도와 문서 전체에서의 희소성과 문서 길이를 함께 고려한다.</p>
<p>개념적으로는 다음과 같은 요소를 사용한다.</p>
<pre><code class="language-text">단어가 이 문서에 자주 등장하는가?
단어가 전체 문서에는 드문가?
문서가 너무 길어서 단어가 많이 포함된 것은 아닌가?</code></pre>
<p>그래서 오류 코드와 제품 번호와 조항 번호처럼 정확한 문자열이 중요한 검색에 강하다. 반대로 <code>신청</code>, <code>등록</code>, <code>접수</code>처럼 표현이 다른 단어를 같은 의미로 연결하지는 못한다.</p>
<p>다음 질문을 생각해 보자.</p>
<pre><code class="language-text">HTTP 429 오류가 발생하는 조건은?</code></pre>
<p>이 질문에서는 429라는 오류 코드가 핵심이다. 정확한 문자열을 찾는 Keyword Search가 적합할 수 있다.</p>
<p>반대로 다음 질문은 표현이 다양할 수 있다.</p>
<pre><code class="language-text">휴가를 등록하는 방법이 궁금해.</code></pre>
<p>문서가 신청, 등록, 결재라는 표현을 사용한다면 단어가 정확하게 일치하지 않을 수 있다. 이때는 Vector Search가 더 유리할 수 있다.</p>
<p>두 검색 방식은 서로 다른 강점을 가진다.</p>
<pre><code class="language-text">Vector Search
→ 의미가 비슷한 표현을 찾는다.

Keyword Search
→ 정확한 단어와 숫자와 고유명사를 찾는다.</code></pre>
<h2 id="hybrid-search">Hybrid Search</h2>
<p>Vector Search와 Keyword Search를 함께 사용하는 방식이 Hybrid Search다.</p>
<pre><code class="language-text">                 Query
                   │
        ┌──────────┴──────────┐
        ↓                     ↓
  Keyword Search        Vector Search
        │                     │
        └──────────┬──────────┘
                   ↓
                결과 통합</code></pre>
<p>예를 들어 다음 질문은 두 가지 특성을 모두 포함한다.</p>
<pre><code class="language-text">SKA-3928 배터리 교체 방법</code></pre>
<p>SKA-3928은 정확한 문자열 검색이 필요하고, 배터리 교체 방법은 의미 검색이 필요하다.</p>
<p>Hybrid Search는 두 검색 결과를 합친 뒤 중복을 제거하고 최종 순위를 다시 계산한다.</p>
<pre><code class="language-pseudo">dense_results = dense_search(question, top_k = 10)
sparse_results = keyword_search(question, top_k = 10)

candidates = merge_by_document_id(
    dense_results,
    sparse_results
)

results = rerank(question, candidates)
return results.take(5)</code></pre>
<p>두 검색기의 Score 범위가 다를 수 있기 때문에 Score를 단순히 더하면 안 된다.</p>
<p>Score를 정규화하거나 결과의 순위를 이용해 결합하는 방법을 사용할 수 있다.</p>
<h3 id="결과를-합치는-방법">결과를 합치는 방법</h3>
<p>Dense Search와 Sparse Search의 Score는 계산 방식이 다르다.</p>
<pre><code class="language-text">Dense Score
→ Vector 거리 또는 유사도

Sparse Score
→ 단어 빈도와 역문서 빈도 기반 점수</code></pre>
<p>따라서 다음처럼 원래 Score를 그대로 더하면 특정 검색기가 결과를 독점할 수 있다.</p>
<pre><code class="language-pseudo">combined_score = dense_score + sparse_score</code></pre>
<p>두 결과의 순위만 사용해 결합하는 방식은 Score의 스케일 차이를 줄일 수 있다.</p>
<pre><code class="language-text">각 검색 결과의 순위
        ↓
순위 기반 결합
        ↓
중복 문서 제거
        ↓
최종 후보</code></pre>
<p>어떤 결합 방식이 좋은지는 데이터와 질문 유형에 따라 달라진다. 정확한 코드 질문과 자연어 질문을 같은 비율로 섞어 평가해야 결합 전략의 효과를 확인할 수 있다.</p>
<h2 id="검색-결과를-조정하기">검색 결과를 조정하기</h2>
<h3 id="top-k와-similarity-threshold">Top-K와 Similarity Threshold</h3>
<p>Top-K는 검색 결과를 몇 개 가져올지 결정한다.</p>
<pre><code class="language-text">전체 문서
    ↓
질문과 가까운 문서 검색
    ↓
Top-K Chunk</code></pre>
<p>Top-K가 너무 작으면 필요한 문서를 놓칠 수 있다.</p>
<p>반대로 너무 크면 질문과 관계없는 문서가 Context에 포함되고 입력 토큰과 비용이 증가한다.</p>
<p>Similarity Threshold는 일정 기준보다 낮은 결과를 제외하는 값이다.</p>
<pre><code class="language-pseudo">candidates = search(question, top_k = 10)

results = [
    item for item in candidates
    if item.score &gt;= threshold
]</code></pre>
<p>Threshold는 임베딩 모델과 데이터와 거리 함수에 따라 분포가 달라진다.</p>
<p>따라서 0.8이라는 값을 모든 데이터에 동일하게 적용할 수는 없다.</p>
<pre><code class="language-text">질문 A
Top 1: 0.91 관련 문서
Top 2: 0.86 관련 문서

질문 B
Top 1: 0.72 무관 문서
Top 2: 0.70 무관 문서</code></pre>
<p>Score와 실제 관련성을 함께 확인하면서 기준을 정해야 한다.</p>
<h3 id="recall과-context-예산-사이의-균형">Recall과 Context 예산 사이의 균형</h3>
<p>검색 단계의 Top-K와 LLM에 전달하는 최종 문서 수는 같은 값일 필요가 없다.</p>
<pre><code class="language-text">넓게 검색
→ Top 20 후보 확보

후보 정리
→ 중복 제거와 Re-ranking

좁게 전달
→ 최종 Context 4개</code></pre>
<p>Top-K를 작게 고정하면 정답 문서를 놓칠 수 있다. 반대로 검색 결과를 모두 Context에 넣으면 Recall은 높아져도 관련 없는 문서와 비용이 함께 증가한다.</p>
<p>Retrieval은 후보를 넓게 확보하고, Post-Retrieval은 Context 예산 안에서 근거를 좁히는 두 단계로 나누어 생각하는 편이 좋다.</p>
<h3 id="mmr">MMR</h3>
<p>유사도만 기준으로 Top-K를 가져오면 비슷한 문서들이 결과를 독점할 수 있다.</p>
<pre><code class="language-text">휴가 규정 원문
휴가 규정 요약
휴가 규정 FAQ
휴가 규정 복사본</code></pre>
<p>검색 결과는 네 개지만 사실상 같은 내용일 수 있다.</p>
<p>MMR(Maximal Marginal Relevance)은 질문과의 관련성뿐만 아니라 결과 간 다양성도 함께 고려한다.</p>
<pre><code class="language-text">MMR
=
질문과의 관련성
+
결과 간 다양성</code></pre>
<p>이렇게 하면 다음과 같이 서로 다른 근거를 구성할 수 있다.</p>
<pre><code class="language-text">휴가 대상
휴가 기간
신청 절차
급여
복직 절차</code></pre>
<p>MMR은 여러 조건을 포함한 질문이나 서로 다른 출처를 비교해야 하는 질문에서 유용할 수 있다.</p>
<p>하지만 정답이 하나의 문서에만 있는 질문이라면 관련성이 높은 인접 Chunk가 여러 개 선택되는 편이 더 나을 수 있다.</p>
<p>다양성과 관련성 사이의 균형도 질문 세트로 확인해야 한다.</p>
<h3 id="re-ranking">Re-ranking</h3>
<p>Vector Search의 순위가 실제 질문에 가장 유용한 순위와 항상 같은 것은 아니다.</p>
<p>따라서 먼저 후보를 넓게 가져온 뒤, 별도의 Re-ranker로 다시 평가할 수 있다.</p>
<pre><code class="language-text">Vector Search
    ↓
Top 20
    ↓
Re-ranking
    ↓
Top 4
    ↓
LLM</code></pre>
<p>Vector Search는 빠르게 후보를 찾는 역할을 하고, Re-ranker는 후보 중 실제로 중요한 근거를 선별하는 역할을 담당한다.</p>
<p>즉,</p>
<blockquote>
<p>넓게 찾고, 좁게 넣는다.</p>
</blockquote>
<p>라는 방식이다.</p>
<p>Re-ranking은 검색 품질을 높일 수 있지만 추가 지연 시간과 비용이 발생한다.</p>
<p>모든 문서를 다시 평가하기보다 1차 검색에서 후보를 충분히 확보한 뒤 최종 Context에 들어갈 문서만 선별하는 방식이 일반적이다.</p>
<h2 id="query를-검색에-맞게-바꾸기">Query를 검색에 맞게 바꾸기</h2>
<h3 id="query-rewrite">Query Rewrite</h3>
<p>사용자가 항상 검색 시스템이 이해하기 좋은 질문을 작성하는 것은 아니다.</p>
<pre><code class="language-text">사용자: 휴가 신청은 어떻게 해?
사용자: 그러면 승인은?</code></pre>
<p>두 번째 질문만 검색하면 무엇의 승인인지 알기 어렵다.</p>
<p>이전 대화의 문맥을 이용해 Query를 복원할 수 있다.</p>
<pre><code class="language-text">&quot;퇴사 시 회사에서 지급받은 노트북은
언제까지 반납해야 하는가?&quot;</code></pre>
<p>흐름은 단순하다.</p>
<pre><code class="language-text">사용자 질문
    ↓
Query Rewrite
    ↓
검색 가능한 Query
    ↓
검색</code></pre>
<p>Rewrite 과정에서 원래 질문에 없는 내용을 추가하면 안 된다.</p>
<p>고유명사와 날짜와 버전과 숫자와 사용자가 지정한 조건은 보존해야 한다.</p>
<p>Rewrite는 검색 성능을 높일 수 있지만 원래 질문의 의미를 바꾸는 새로운 모델 호출이기도 하다.</p>
<pre><code class="language-text">원래 질문: v2.3.1에서 HTTP 429가 발생하는 조건은?
잘못된 Rewrite: API 사용 제한은 언제 발생하는가?</code></pre>
<p>잘못된 Rewrite는 제품 버전과 오류 코드를 지워 검색 범위를 넓히는 대신 정답에 필요한 조건을 없앤다. 따라서 Rewrite 결과만 사용하기보다 원래 질문과 재작성된 질문을 함께 검색하고 결과를 비교하는 방식도 고려할 수 있다.</p>
<h3 id="multi-query">Multi-Query</h3>
<p>하나의 질문을 여러 관점으로 표현해 검색할 수도 있다.</p>
<pre><code class="language-text">회사 노트북 반납 규정

        ↓

퇴사 시 노트북 반환 절차

회사 자산 반납 기한

업무 장비 반환 정책</code></pre>
<p>각 Query가 서로 다른 문서를 찾을 수 있으므로 하나의 표현에 의존하는 것보다 관련 근거를 놓칠 가능성이 줄어든다.</p>
<pre><code class="language-text">              질문
               ↓
            MultiQuery
          ┌─────┼─────┐
          ↓     ↓     ↓
        Query  Query  Query
          ↓     ↓     ↓
        검색   검색   검색
          └─────┼─────┘
                ↓
             결과 통합</code></pre>
<p>Multi-Query는 Recall을 높일 수 있지만 검색 횟수가 늘어난다.</p>
<p>검색 결과가 부족한 질문에만 조건부로 적용하거나, 검색 결과를 합친 뒤 중복 제거와 Re-ranking을 함께 적용하는 것이 좋다.</p>
<h2 id="metadata-filter">Metadata Filter</h2>
<p>질문과 관련된 모든 Vector를 탐색할 필요가 없는 경우 Metadata를 통해 검색 범위를 먼저 제한할 수 있다.</p>
<pre><code class="language-text">전체 Vector Store
    ↓
department = HR
version = 2025
status = ACTIVE
    ↓
Vector Search</code></pre>
<p>특히 사용자 권한이나 특정 문서 집합을 구분해야 한다면 Metadata Filter는 단순한 검색 최적화를 넘어 검색 가능 범위를 제어하는 장치가 된다.</p>
<p>사용자가 질문에 다른 부서나 테넌트를 입력했다고 해서 필터가 바뀌어서는 안 된다. 검색 범위는 인증 정보와 서버 정책으로 계산해야 한다.</p>
<h2 id="검색-전략을-선택하는-기준">검색 전략을 선택하는 기준</h2>
<pre><code class="language-text">표현이 다양하다
→ Vector Search

제품 코드와 숫자가 중요하다
→ Keyword Search

두 특성이 모두 필요하다
→ Hybrid Search

결과가 같은 문서에 치우친다
→ MMR

후보의 순위가 아쉽다
→ Re-ranking

질문이 짧고 모호하다
→ Query Rewrite

한 질문에 여러 표현이 필요하다
→ Multi-Query</code></pre>
<p>이것은 모든 시스템에 그대로 적용하는 규칙이 아니다.</p>
<p>질문의 형태와 문서의 특성과 평가 결과에 따라 필요한 전략을 선택해야 한다.</p>
<h2 id="마무리">마무리</h2>
<p>검색 전략의 목표는 가장 많은 문서를 가져오는 것이 아니다.</p>
<p>질문에 답하는 데 필요한 근거를 적절한 수와 순서로 가져오는 것이다.</p>
<p>Vector Search는 의미가 비슷한 표현을 찾는 데 강하고, Keyword Search는 정확한 문자열과 숫자와 고유명사를 찾는 데 강하다. 두 검색을 결합하면 서로 다른 검색 실패를 보완할 수 있다.</p>
<p>검색 결과가 너무 반복되면 MMR을 적용할 수 있고, 후보의 순위가 아쉽다면 Re-ranking을 사용할 수 있다. 질문이 검색에 적합하지 않다면 Query Rewrite와 Multi-Query를 고려할 수 있다.</p>
<p>다만 기능을 많이 추가한다고 검색 품질이 자동으로 좋아지는 것은 아니다.</p>
<p>어떤 질문에서 검색이 실패했는지 먼저 확인하고, 해당 실패를 줄이는 전략만 선택하는 것이 중요하다.</p>
<p>검색 전략을 고를 때는 다음 순서로 실패를 분류할 수 있다.</p>
<pre><code class="language-text">정확한 단어와 코드가 누락됨
→ Keyword 또는 Hybrid 확인

표현이 다른 질문이 누락됨
→ Embedding과 Vector Search 확인

정답 후보는 있지만 순위가 낮음
→ Query Rewrite 또는 Re-ranking 확인

같은 문서가 반복됨
→ 중복 제거와 MMR 확인

권한 밖의 문서가 섞임
→ Metadata Filter와 인증 흐름 확인</code></pre>
<p>이렇게 실패 원인과 개선 모듈을 연결해야 Retrieval Pipeline이 기능의 모음이 아니라 판단 가능한 구조가 된다.</p>
<p>다음 글에서는 검색된 문서가 있어도 답변이 틀리는 이유와 근거 있는 Generation을 살펴보자.</p>
