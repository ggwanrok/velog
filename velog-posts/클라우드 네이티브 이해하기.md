<p>앞서 IaaS, PaaS, SaaS와 같은 <strong>Cloud Service를 어떤 형태로 제공받는가</strong>에 대해 살펴봤다.</p>
<p>그렇다면 기존에 사용하던 애플리케이션을 AWS EC2 같은 Cloud VM에 그대로 올리기만 하면 <strong>Cloud Native Application</strong>이라고 할 수 있을까?</p>
<p>그렇지는 않다.</p>
<h2 id="cloud와-cloud-native는-다르다">Cloud와 Cloud Native는 다르다</h2>
<p>Cloud는 컴퓨팅, 스토리지, 네트워크와 같은 IT 자원을 필요할 때 서비스 형태로 사용할 수 있도록 만들어준다.</p>
<p>예를 들어 기존 On-Premise 서버에서 실행하던 애플리케이션을 구조의 변화 없이 그대로 EC2에 옮겼다고 해보자.</p>
<pre><code class="language-text">기존 On-Premise Server

Application
Database
File</code></pre>
<p>↓</p>
<pre><code class="language-text">AWS EC2

Application
Database
File</code></pre>
<p>분명 <strong>Cloud 환경을 사용하고 있는 것</strong>은 맞다.</p>
<p>하지만 애플리케이션의 구조나 배포, 운영 방식 자체는 기존과 크게 달라지지 않았다.</p>
<p>즉,</p>
<pre><code class="language-text">Cloud
→ 애플리케이션을 &quot;어디에서 실행할 것인가&quot;

Cloud Native
→ Cloud 환경을 잘 활용할 수 있도록
   애플리케이션을 &quot;어떻게 만들고 운영할 것인가&quot;</code></pre>
<p>의 차이로 이해해볼 수 있다.</p>
<p>Cloud에서는 필요에 따라 컴퓨팅 자원을 추가하거나 제거할 수 있고, 새로운 서버를 비교적 빠르게 생성할 수 있다.</p>
<p>그런데 애플리케이션이 하나의 거대한 구조로 강하게 결합되어 있고, 배포나 운영 과정 역시 모두 수동이라면 이러한 Cloud의 이점을 제대로 활용하기 어렵다.</p>
<p>결국 <strong>Infrastructure가 유연해졌다면, 그 위에서 실행되는 Application의 구조와 운영 방식 역시 유연해질 필요가 있다.</strong></p>
<p>이러한 생각에서 출발하는 것이 <strong>Cloud Native</strong>이다.</p>
<hr />
<h2 id="cloud-native-application-개념">Cloud Native Application 개념</h2>
<p><strong>Cloud Native Application</strong>이란 Cloud가 제공하는 <strong>확장성, 탄력성, 자동화 등의 특성을 적극적으로 활용할 수 있도록 설계되고 개발·배포·운영되는 애플리케이션</strong>이라고 이해할 수 있다.</p>
<p>단순히 애플리케이션을 Cloud Server에 올려놓는 것이 아니라,</p>
<pre><code class="language-text">  Application 설계
        +
     실행 환경
        +
      배포 방법
        +
     운영 방법</code></pre>
<p>전체를 Cloud 환경에 적합하게 구성하는 것이다.</p>
<blockquote>
<p><strong>CNCF의 Cloud Native 정의</strong></p>
</blockquote>
<ul>
<li>퍼블릭, 프라이빗, 하이브리드 클라우드와 같은 환경에서 확장성 있는 애플리케이션을 만들고 운영할 수 있다.</li>
<li>Container, Service Mesh, Microservice, Immutable Infrastructure, Declarative API 등이 대표적인 접근 방식에 해당한다.</li>
<li>회복성이 있고, 관리 및 관찰이 용이한 느슨하게 결합된 시스템을 지향한다.</li>
<li>강력한 자동화를 통해 적은 운영 부담으로도 빈번하고 예측 가능한 변경을 수행할 수 있도록 한다.</li>
</ul>
<blockquote>
<p><strong>CNCF(Cloud Native Computing Foundation)</strong>
Kubernetes를 비롯한 Cloud Native 생태계의 여러 오픈소스 프로젝트를 지원하고 관리하는 재단이다.</p>
</blockquote>
<p>K-PaaS 역시 이러한 Cloud Native 생태계의 여러 기술과 오픈소스를 활용하여 구성된다.</p>
<hr />
<h2 id="왜-cloud-native가-필요한가">왜 Cloud Native가 필요한가?</h2>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/0356b795-0a63-46fb-a621-ccc117c5d661/image.png" /></p>
<p>기존의 애플리케이션 개발과 운영 환경은 비교적 <strong>고정된 서버 환경</strong>을 기준으로 구성되는 경우가 많았다.</p>
<pre><code class="language-text">Server 준비
    ↓
OS / Runtime 환경 구성
    ↓
Application 배포
    ↓
운영</code></pre>
<p>새로운 버전을 배포하거나 트래픽이 증가하면 사람이 새로운 환경을 준비하고, 프로그램을 설치하고, 설정을 변경하는 과정이 추가적으로 필요했다.</p>
<p>Cloud의 등장으로 인프라는 훨씬 유연해졌다.</p>
<pre><code class="language-text">필요하면 자원을 늘리고
        ↓
필요하지 않으면 줄이고

새로운 서버가 필요하면
        ↓
빠르게 생성하고

장애가 발생하면
        ↓
다른 실행 환경으로 교체</code></pre>
<p>할 수 있게 되었다.</p>
<p>하지만 <strong>Application 자체가 이러한 변화에 대응하기 어려운 구조라면 Cloud의 이점을 충분히 활용할 수 없다.</strong></p>
<p>따라서 애플리케이션 역시</p>
<ul>
<li>필요한 부분을 독립적으로 변경하고</li>
<li>동일한 실행 환경을 빠르게 만들어내고</li>
<li>변경된 코드를 지속적으로 검증하고 배포하며</li>
<li>트래픽 증가나 장애 상황에 유연하게 대응할 수 있는</li>
</ul>
<p>구조와 운영 방식을 가질 필요가 있다.</p>
<p>Cloud Native는 이러한 문제를 해결하기 위한 <strong>애플리케이션 설계 및 운영 방식</strong>이라고 볼 수 있다.</p>
<hr />
<h2 id="특징">특징</h2>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/4b7fc3d7-9ea8-4622-b343-4f8c43df0db4/image.png" /></p>
<p>Cloud Native Application은 Cloud 환경의 특성을 적극적으로 활용하면서 다음과 같은 이점을 얻는 것을 목표로 한다.</p>
<ul>
<li><strong>민첩성</strong> : 기능을 작은 단위로 변경하고 빠르게 배포할 수 있다.</li>
<li><strong>확장성</strong> : 트래픽이나 상황에 따라 필요한 서비스의 실행 단위를 유연하게 확장할 수 있다.</li>
<li><strong>이식성</strong> : 표준화된 실행 환경을 활용해 다양한 인프라에서 실행하기 쉬워진다.</li>
<li><strong>회복성</strong> : 일부 구성 요소의 장애가 전체 서비스 장애로 확대되지 않도록 설계할 수 있다.</li>
<li><strong>자동화</strong> : 빌드, 테스트, 배포, 확장 등의 운영 과정을 자동화하기 좋다.</li>
<li><strong>협력성</strong> : 서비스가 작은 책임 단위로 분리되면서 여러 팀이 병렬적으로 개발하기 쉬워진다.</li>
</ul>
<h3 id="이점-알아보기">이점 알아보기</h3>
<p>특정 업무의 트래픽이 갑자기 증가했다고 생각해보자.</p>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/ce1abd14-c261-4d0a-b348-18b606721314/image.png" /></p>
<p>기존의 거대한 애플리케이션에서는 일부 기능의 부하가 증가하더라도 애플리케이션 전체를 확장해야 할 수 있다.</p>
<p>반면 기능과 실행 단위가 적절히 분리되어 있다면 실제 부하가 발생하는 서비스만 확장하는 방식으로 대응할 수 있다.</p>
<pre><code class="language-text">전체 Application 확장

        ↓

필요한 Service만 확장</code></pre>
<p>이러한 구조는 Cloud가 제공하는 동적인 자원 할당 방식과 잘 어울린다.</p>
<h3 id="효과">효과</h3>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/7fbd06d8-3531-4238-9625-31292ec56701/image.png" /></p>
<p>결과적으로 Cloud Native는 <strong>빠르게 변화하는 비즈니스 요구사항과 트래픽 변화에 보다 유연하고 민첩하게 대응하는 것</strong>을 목표로 한다.</p>
<hr />
<h2 id="핵심-요소">핵심 요소</h2>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/155d50e1-a9e3-490d-955f-62601650b4cc/image.png" /></p>
<p>Cloud Native를 구현하기 위한 방법이 하나로 정해져 있는 것은 아니다.</p>
<p>다만 대표적으로 다음과 같은 아키텍처와 기술, 개발 문화가 함께 활용된다.</p>
<pre><code class="language-text">MSA
→ Application을 독립적인 변경·배포 단위로 분리

Container
→ Application의 실행 환경을 표준화된 단위로 패키징

CI/CD
→ 변경된 코드를 지속적으로 빌드·검증·배포

DevOps
→ 개발과 운영이 빠르게 협업하고 피드백하며
   Application의 전체 생명주기를 관리</code></pre>
<p>각각 다른 개념이지만 서로 결합되면서 <strong>변경, 배포, 확장, 복구가 빠른 Cloud Native Application 환경</strong>을 구성한다.</p>
<hr />
<h3 id="1-msa-micro-service-architecture">1. MSA (Micro Service Architecture)</h3>
<p>MSA는 하나의 거대한 애플리케이션을 <strong>독립적으로 개발하고 배포할 수 있는 작은 서비스 단위</strong>로 분리하는 아키텍처이다.</p>
<blockquote>
<p>MSA는 Cloud Native를 구현하기 좋은 대표적인 아키텍처 중 하나이며, 모든 Cloud Native Application이 반드시 MSA 구조를 가져야 하는 것은 아니다.</p>
</blockquote>
<p>각 Microservice는 자신이 담당하는 기능을 독립적으로 수행하고, 다른 서비스와는 API 등을 통해 통신한다.</p>
<h4 id="개념">개념</h4>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/0383e3b3-163e-43ce-b340-714ecde138dc/image.png" /></p>
<p>기존의 Monolithic Application이 여러 기능을 하나의 거대한 애플리케이션 안에 구성한다면,</p>
<p>MSA에서는 기능을 각각의 서비스 단위로 분리한다.</p>
<pre><code class="language-text">Monolithic

Application
├─ User
├─ Order
├─ Product
└─ Payment</code></pre>
<p>↓</p>
<pre><code class="language-text">MSA

User Service

Order Service

Product Service

Payment Service</code></pre>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/9cd59bfb-d064-4187-b90e-553b6f3b1df1/image.png" /></p>
<p>각 서비스는 독립적인 역할을 수행하는 하나의 컴포넌트로 구성된다.</p>
<p>데이터 역시 서비스 간 결합도를 낮추기 위해 가능한 한 각 서비스의 책임에 맞게 분리하여 관리한다.</p>
<h4 id="장점">장점</h4>
<p>MSA에서는 각 서비스가 비교적 독립적인 개발·배포 단위가 된다.</p>
<p>따라서 여러 팀이나 개발자가 서로 다른 서비스를 병렬적으로 개발할 수 있고, 특정 기능에 변경이 발생했을 때 전체 애플리케이션을 함께 변경하지 않아도 되는 장점이 있다.</p>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/fbff8d54-93fb-4fb1-ba82-daa542b796d4/image.png" /></p>
<p>또한 특정 서비스에만 트래픽이 증가한다면 해당 서비스만 별도로 확장하는 구조 역시 가능해진다.</p>
<h4 id="단점">단점</h4>
<p>반대로 하나의 프로세스 내부에서 처리되던 기능들이 여러 서비스로 분리되면서 새로운 복잡성도 발생한다.</p>
<ul>
<li>서비스 간 네트워크 통신</li>
<li>장애 전파</li>
<li>분산 데이터 관리</li>
<li>트랜잭션 처리</li>
<li>로그 및 모니터링</li>
<li>서비스 배포 및 버전 관리</li>
</ul>
<p>등을 추가적으로 고려해야 한다.</p>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/6eb1dc0d-9bf8-4126-bad2-4ea3e1178726/image.png" /></p>
<p>따라서</p>
<blockquote>
<p><strong>서비스를 작게 나누는 것 자체가 목적은 아니다.</strong></p>
</blockquote>
<p>서비스의 독립적인 변경·배포 필요성이나 조직 구조, 도메인 경계 등을 고려하여 적절한 단위로 분리하는 것이 중요하다.</p>
<h4 id="도입-시-검토사항">도입 시 검토사항</h4>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/1986d243-fbd1-492c-86ec-ccb21dc4c50c/image.png" /></p>
<hr />
<h3 id="2-container">2. Container</h3>
<p>MSA를 통해 Application을 여러 서비스로 분리했다고 해보자.</p>
<p>그러면 각각의 서비스를 실행하기 위한 환경 역시 필요하다.</p>
<pre><code class="language-text">User Service
→ Java 21

Order Service
→ Java 17

AI Service
→ Python

Frontend
→ Nginx</code></pre>
<p>각 서버마다 Runtime과 Library를 직접 설치하고 설정한다면 서비스가 많아질수록 환경 관리가 복잡해진다.</p>
<p>Container는 <strong>애플리케이션과 실행에 필요한 환경을 하나의 표준화된 단위로 패키징</strong>하여 이러한 문제를 줄여준다.</p>
<h4 id="개념-1">개념</h4>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/ce4f030c-96b6-439a-9821-3e2431015261/image.png" /></p>
<p>앞서 IaaS 부분에서 살펴봤듯 Container는 VM처럼 실행 단위마다 별도의 Guest Kernel을 가지지 않는다.</p>
<p>Host의 Kernel을 공유하면서 Application 실행에 필요한</p>
<ul>
<li>Runtime</li>
<li>Library</li>
<li>Binary</li>
<li>Application Code</li>
</ul>
<p>등을 Container Image로 묶어서 실행한다.</p>
<h4 id="특징-1">특징</h4>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/a25c8ec2-c6fc-4b95-bad2-1655662e8a60/image.png" /></p>
<p>VM보다 상대적으로 가볍고 빠르게 생성·종료할 수 있기 때문에,</p>
<pre><code class="language-text">필요할 때 생성
      ↓
실행
      ↓
필요 없으면 제거</code></pre>
<p>하는 Cloud의 동적인 운영 환경과 잘 어울린다.</p>
<p>또한 동일한 Container Image를 사용하면 개발, 테스트, 운영 환경에서 애플리케이션 실행 환경을 보다 일관되게 유지할 수 있다.</p>
<blockquote>
<p>Container 내부 구조와 Docker Image, Layer, Volume 등의 구체적인 동작 방식은 다음 글에서 자세히 살펴본다.</p>
</blockquote>
<h4 id="container-orchestration">Container Orchestration</h4>
<p>Container가 몇 개 정도라면 직접 관리할 수도 있다.</p>
<p>하지만 서비스 규모가 커져 Container가 수십, 수백 개가 되기 시작하면 이야기가 달라진다.</p>
<pre><code class="language-text">Container 생성

Container 배포

Container 장애 복구

Container 개수 확장

Network 연결

Version Update</code></pre>
<p>등을 사람이 직접 관리하는 것은 현실적으로 어렵다.</p>
<p>이러한 Container의 <strong>프로비저닝, 배포, 네트워킹, 확장, 가용성 및 생명주기 관리 등을 자동화하는 것</strong>을 <strong>Container Orchestration</strong>이라고 한다.</p>
<p>대표적인 Container Orchestration Platform이 <strong>Kubernetes</strong>이다.</p>
<ul>
<li>주요 플랫폼으로 Kubernetes가 있으며, Docker Swarm이나 Apache Mesos와 같은 기술 역시 Container Orchestration 영역에서 사용되어 왔다.</li>
</ul>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/008f9e8e-db7f-4452-80a0-c514f09e3ad3/image.png" /></p>
<p>아주 단순화하면,</p>
<pre><code class="language-text">원하는 상태를 정의
        ↓
배포
        ↓
Orchestrator가 실제 상태를 관리</code></pre>
<p>하는 구조로 생각해볼 수 있다.</p>
<hr />
<h3 id="3-devops">3. DevOps</h3>
<h4 id="정의">정의</h4>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/c252545c-0982-421b-8b44-b7098d0657f1/image.png" /></p>
<p>DevOps는 간단하게 말하면 <strong>개발(Development)과 운영(Operations)이 분리되어 일하던 경계를 줄이고, 하나의 서비스 생명주기를 함께 책임지기 위한 문화와 업무 방식</strong>이라고 볼 수 있다.</p>
<p>단순히 하나의 기술이나 도구를 의미하는 것은 아니다.</p>
<h4 id="등장-배경">등장 배경</h4>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/d2e91252-956e-473d-9914-ead4f00fe197/image.png" /></p>
<p>전통적인 개발 환경에서는 개발과 운영의 역할이 명확하게 분리되는 경우가 많았다.</p>
<pre><code class="language-text">개발팀
   ↓
개발 완료
   ↓
테스트
   ↓
운영팀 전달
   ↓
배포</code></pre>
<p>개발팀이 빠르게 새로운 기능을 만들어도 실제 운영 환경에 반영되는 과정이 느리다면 전체 서비스의 개선 속도 역시 느려질 수밖에 없다.</p>
<p>Agile 방식이 확산되면서 개발 측면에서는</p>
<pre><code class="language-text">작게 개발
   ↓
빠르게 확인
   ↓
피드백
   ↓
다시 개선</code></pre>
<p>하는 짧은 개발 주기가 중요해졌다.</p>
<p>하지만 개발 속도만 빨라지고 빌드, 테스트, 배포, 운영 과정이 그대로라면 결국 <strong>운영 단계가 새로운 병목</strong>이 된다.</p>
<p>그래서 개발과 운영이 더 긴밀하게 협업하고,</p>
<ul>
<li>개발</li>
<li>테스트</li>
<li>배포</li>
<li>운영</li>
<li>모니터링</li>
<li>피드백</li>
</ul>
<p>을 하나의 반복되는 흐름으로 연결하는 <strong>DevOps 문화</strong>가 중요해졌다.</p>
<pre><code class="language-text">Plan
 ↓
Develop
 ↓
Build
 ↓
Test
 ↓
Release
 ↓
Deploy
 ↓
Operate
 ↓
Monitor
 └────────→ 다시 Plan</code></pre>
<p>Container나 CI/CD와 같은 기술은 DevOps 자체가 아니라, <strong>이러한 빠른 반복과 자동화를 구현하기 좋은 기술적 수단</strong>이라고 볼 수 있다.</p>
<h4 id="개념-2">개념</h4>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/9f538649-0a88-4849-880f-10e61fedec01/image.png" /></p>
<p>기존에 개발 업무와 운영 업무로 나누어져 있던 역할 사이의</p>
<ul>
<li>커뮤니케이션</li>
<li>협업</li>
<li>자동화</li>
<li>빠른 피드백</li>
</ul>
<p>을 강화하는 것이 DevOps의 핵심이다.</p>
<h4 id="효과-1">효과</h4>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/945e1a4b-0eab-4859-8676-4c6073398c83/image.png" /></p>
<p>DevOps가 제대로 자리 잡으면 개발한 기능을 운영 환경까지 전달하는 시간이 줄어들고, 실제 서비스의 상태를 빠르게 확인하여 다시 개발에 반영할 수 있다.</p>
<p>결국</p>
<pre><code class="language-text">개발
 ↓
배포
 ↓
운영
 ↓
관찰
 ↓
피드백
 ↓
다시 개발</code></pre>
<p>이라는 <strong>짧은 Feedback Loop</strong>를 만드는 것이 중요하다.</p>
<hr />
<h3 id="4-cicd">4. CI/CD</h3>
<h4 id="정의-1">정의</h4>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/157cc73b-037b-447a-91bc-b05707950c6f/image.png" /></p>
<p>앞에서 DevOps는 개발과 운영이 함께 빠른 피드백을 주고받으며 서비스를 개선하는 <strong>문화와 업무 방식</strong>이라고 설명했다.</p>
<p>그렇다면</p>
<pre><code class="language-text">Code 수정
   ↓
Build
   ↓
Test
   ↓
Deploy</code></pre>
<p>를 매번 사람이 직접 실행한다면 빠른 반복은 어렵다.</p>
<p>이 과정을 자동화하기 위한 대표적인 방법이 <strong>CI/CD</strong>이다.</p>
<blockquote>
<p>CI/CD는 DevOps를 실천하기 위한 대표적인 자동화 방식 중 하나라고 이해하면 좋다.</p>
</blockquote>
<hr />
<h4 id="cicd-파이프라인">CI/CD 파이프라인</h4>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/ef5bba1e-fe32-4e79-bcc8-e65de8f045d0/image.png" /></p>
<p>CI/CD Pipeline은 Application Code가 개발 환경에서 시작하여</p>
<pre><code class="language-text">Source Code
    ↓
Build
    ↓
Test
    ↓
Package
    ↓
Deploy
    ↓
Service</code></pre>
<p>의 과정을 거쳐 사용자에게 전달되는 일련의 흐름을 자동화한 것이다.</p>
<p>이러한 과정을 Pipeline으로 구성하면 매번 사람이 동일한 명령과 작업을 반복하지 않아도 된다.</p>
<p>또한 각 단계에서 문제가 발생하면 이후 배포를 중단하도록 구성할 수 있기 때문에 <strong>빠른 피드백과 배포 안정성</strong>을 함께 확보할 수 있다.</p>
<p>예를 들어,</p>
<pre><code class="language-text">Commit
   ↓
Compile
   ↓
Unit Test
   ↓
Container Image Build
   ↓
Integration Test
   ↓
Deploy</code></pre>
<p>와 같이 여러 단계로 나누어 검증할 수 있다.</p>
<p>필요한 경우 서로 독립적인 작업은 병렬로 수행하여 Pipeline의 전체 실행 시간을 줄이는 것도 가능하다.</p>
<hr />
<h4 id="개념-3">개념</h4>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/9a9b4ae3-192c-4055-9c33-51afaf7e5dd5/image.png" /></p>
<blockquote>
<p><strong>CI 개념</strong></p>
</blockquote>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/3d4c1908-a03d-4a13-983d-0ad0303f62ac/image.png" /></p>
<p><strong>CI(Continuous Integration)</strong> 는 여러 개발자의 변경 사항을 지속적으로 하나의 코드베이스에 통합하고,</p>
<pre><code class="language-text">Code 변경
   ↓
Build
   ↓
Test</code></pre>
<p>를 자동으로 수행하여 문제가 발생했는지 빠르게 확인하는 것을 의미한다.</p>
<p>즉,</p>
<blockquote>
<p><strong>변경된 코드를 자주 합치고, 합칠 때마다 자동으로 검증하자.</strong></p>
</blockquote>
<p>에 가깝다.</p>
<blockquote>
<p><strong>CD 개념</strong></p>
</blockquote>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/b7d6d0b9-f2cf-4b44-95ee-b6df2aac1dc9/image.png" /></p>
<p>CD는 일반적으로 <strong>Continuous Delivery</strong> 또는 <strong>Continuous Deployment</strong>를 의미한다.</p>
<p><strong>Continuous Delivery</strong>는 검증된 결과물이 언제든 운영 환경에 배포될 수 있는 상태까지 자동으로 준비하는 것을 의미하고,</p>
<p><strong>Continuous Deployment</strong>는 검증을 통과한 변경 사항을 운영 환경까지 자동으로 배포하는 단계까지 포함한다.</p>
<pre><code class="language-text">CI

Code
 ↓
Build
 ↓
Test</code></pre>
<p>↓</p>
<pre><code class="language-text">Continuous Delivery

Deploy 가능한 상태까지 자동화</code></pre>
<p>↓</p>
<pre><code class="language-text">Continuous Deployment

운영 환경 배포까지 자동화</code></pre>
<blockquote>
<p><strong>이해가 잘 안된다면 읽어보기</strong></p>
</blockquote>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/27ed4e22-1dc4-4743-88a0-4709bf5569cd/image.png" /></p>
<p><img alt="" src="https://velog.velcdn.com/images/klmcw1004/post/f0e7a232-3fe9-43f7-9c47-f808ce55150b/image.png" /></p>
<hr />
<h4 id="cicd와-devops-관계-정리">CI/CD와 DevOps 관계 정리</h4>
<p>DevOps와 CI/CD는 같은 개념이 아니다.</p>
<pre><code class="language-text">DevOps

개발과 운영이 함께
서비스의 전체 생명주기를 관리하는
문화 / 방식</code></pre>
<p>그리고</p>
<pre><code class="language-text">CI/CD

Build / Test / Deploy 등의
반복 작업을 자동화하는 방법</code></pre>
<p>이다.</p>
<p>즉,</p>
<blockquote>
<p><strong>DevOps가 지향하는 빠른 협업과 Feedback Loop를 실제 개발 과정에서 구현하기 위해 CI/CD가 적극적으로 사용된다.</strong></p>
</blockquote>
<p>CI/CD 외에도</p>
<ul>
<li>Infrastructure as Code</li>
<li>Monitoring</li>
<li>Logging</li>
<li>Observability</li>
<li>Container</li>
<li>Orchestration</li>
</ul>
<p>등 여러 기술과 운영 방식이 DevOps 환경에서 함께 활용될 수 있다.</p>
<hr />
<h2 id="cloud-native-핵심-요소-관계-정리">Cloud Native 핵심 요소 관계 정리</h2>
<p>지금까지 살펴본 네 가지 개념은 각각 별개의 개념이다.</p>
<p>하지만 Cloud Native 환경에서는 서로 자연스럽게 연결된다.</p>
<pre><code class="language-text">                Cloud
                  │
                  ▼
        동적으로 변하는 Infrastructure
                  │
                  ▼
            Cloud Native
                  │
       ┌──────────┼──────────┐
       │          │          │
       ▼          ▼          ▼
      MSA     Container    DevOps
       │          │          │
       │          │          ▼
       │          │        CI/CD
       │          │
       └──────────┴──────────┘
                  │
                  ▼
       빠른 개발 · 배포 · 확장 · 복구</code></pre>
<p>각각의 역할을 한 문장으로 정리하면 다음과 같다.</p>
<blockquote>
<p><strong>MSA는 애플리케이션을 독립적인 변경·배포 단위로 나눈다.</strong></p>
</blockquote>
<blockquote>
<p><strong>Container는 각 애플리케이션의 실행 환경을 표준화하고 가볍게 패키징한다.</strong></p>
</blockquote>
<blockquote>
<p><strong>CI/CD는 코드의 변경부터 빌드, 테스트, 배포까지의 반복 작업을 자동화한다.</strong></p>
</blockquote>
<blockquote>
<p><strong>DevOps는 개발과 운영이 이러한 전체 과정에서 빠르게 협업하고 피드백을 주고받을 수 있도록 만드는 문화와 운영 방식이다.</strong></p>
</blockquote>
<p>결국 네 요소가 지향하는 방향은 하나로 모인다.</p>
<pre><code class="language-text">작게 변경하고
      ↓
빠르게 검증하고
      ↓
표준화된 환경으로 배포하고
      ↓
필요하면 확장하고
      ↓
운영 결과를 다시 개발에 반영한다.</code></pre>
<p>이렇게 Application의 <strong>개발 → 배포 → 운영 → 개선</strong> 사이클을 짧고 반복 가능하게 만드는 것이 Cloud Native가 추구하는 중요한 방향이라고 볼 수 있다.</p>
<p>그리고 다음 글에서는 이 중에서 애플리케이션의 실제 실행 단위를 담당하는 <strong>Container가 내부적으로 어떻게 동작하는지</strong>, 그리고 이를 대표적으로 구현하는 <strong>Docker</strong>에 대해 조금 더 깊게 살펴본다.</p>
