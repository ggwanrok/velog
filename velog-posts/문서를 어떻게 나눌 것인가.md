<p>RAG를 만들 때 가장 먼저 바꾸고 싶어지는 것은 Embedding Model이나 LLM이다.</p>
<p>그런데 같은 문서와 같은 모델을 사용하더라도 문서를 어떤 단위로 나누었는지에 따라 검색 결과가 달라진다.</p>
<p>검색 결과가 좋지 않으면 모델을 바꾸기 전에 다음 질문부터 확인해야 한다.</p>
<blockquote>
<p>문서가 검색하기 좋은 형태로 저장되어 있는가?</p>
</blockquote>
<p>이번 글에서는 문서를 왜 Chunk로 나누는지, 문서의 구조에 따라 어떤 분할 전략을 사용할 수 있는지, Metadata를 왜 함께 저장해야 하는지를 살펴본다.</p>
<h2 id="chunk는-검색-단위다">Chunk는 검색 단위다</h2>
<p>문서 전체를 하나의 Vector로 만들면 문서 안의 여러 주제가 하나의 의미로 섞인다.</p>
<p>다음과 같은 문서가 있다고 하자.</p>
<pre><code class="language-text">휴가 신청 방법
휴가 승인 기준
병가 처리 절차
휴직 제도
경비 정산</code></pre>
<p>이 문서를 하나의 Vector로 저장하면 휴가 신청 방법을 검색해도 문서 전체가 검색된다.</p>
<p>질문에 필요한 내용은 포함되어 있을 수 있지만, 필요한 문장만 가져온 것은 아니다. 문서가 길어질수록 질문과 관계없는 내용이 Context에 많이 포함된다.</p>
<p>그래서 원본 문서를 여러 개의 Chunk로 나눈다.</p>
<pre><code class="language-text">원본 문서
    ↓
[휴가 신청 방법]
[휴가 승인 기준]
[병가 처리 절차]
[휴직 제도]
[경비 정산]</code></pre>
<p>Chunk는 단순한 문자열 조각이 아니다.</p>
<p>검색 결과로 반환되고, LLM의 Context에 들어가고, 답변의 근거로 사용되는 기본 단위다.</p>
<h3 id="좋은-chunk의-조건">좋은 Chunk의 조건</h3>
<p>좋은 Chunk는 단순히 길이가 일정한 Chunk가 아니다.</p>
<p>다음 세 가지 조건을 함께 만족해야 한다.</p>
<pre><code class="language-text">스스로 이해할 수 있어야 한다.
→ 앞 문장을 보지 않아도 핵심 대상을 알 수 있어야 한다.

검색으로 구분될 수 있어야 한다.
→ 다른 Chunk와 의미가 지나치게 섞이지 않아야 한다.

원문으로 추적할 수 있어야 한다.
→ 문서와 절과 버전을 다시 확인할 수 있어야 한다.</code></pre>
<p>예를 들어 다음 Chunk는 검색 결과로는 짧지만 근거로 사용하기 어렵다.</p>
<pre><code class="language-text">이 경우에는 14일 이내에 처리한다.</code></pre>
<p>대상이 무엇인지와 어떤 조건에 대한 기간인지 알 수 없기 때문이다. Chunk의 길이보다 중요한 것은 질문에 필요한 대상과 조건과 예외가 함께 남아 있는지다.</p>
<h2 id="chunk가-너무-작다면">Chunk가 너무 작다면</h2>
<p>Chunk를 작게 만들면 검색의 정밀도는 높아질 수 있다.</p>
<p>하지만 문맥이 분리될 수 있다.</p>
<pre><code class="language-text">Chunk A
&quot;계약을 해지할 수 있다.&quot;

Chunk B
&quot;단, 서면 통보 후 14일이 경과해야 한다.&quot;</code></pre>
<p>두 Chunk가 따로 검색되면 B가 무엇을 설명하는지 알기 어렵다.</p>
<p>작은 Chunk는 다음과 같은 상황에서 문제가 된다.</p>
<ul>
<li>조건과 예외 조항이 떨어지는 경우</li>
<li>표의 제목과 값이 분리되는 경우</li>
<li>질문과 답변이 서로 다른 Chunk에 있는 경우</li>
<li>코드의 설명과 코드 블록이 분리되는 경우</li>
</ul>
<p>따라서 Chunk를 작게 나누는 것만으로 검색 품질이 좋아지는 것은 아니다.</p>
<p>질문에 필요한 문맥이 하나의 검색 단위에 함께 있어야 한다.</p>
<h2 id="chunk가-너무-크다면">Chunk가 너무 크다면</h2>
<p>반대로 Chunk를 크게 만들면 문맥은 풍부해진다.</p>
<p>하지만 질문과 관계없는 내용도 함께 검색된다.</p>
<pre><code class="language-text">계약 기간
계약 해지
손해배상
비밀유지
개인정보</code></pre>
<p>사용자는 계약 해지에 대해 질문했는데, Context에는 계약서 전체의 내용이 들어갈 수 있다.</p>
<p>이 경우 다음 문제가 생긴다.</p>
<ul>
<li>검색 결과의 관련성이 낮아진다.</li>
<li>입력 토큰과 비용이 늘어난다.</li>
<li>중요한 문장이 긴 Context 속에 묻힌다.</li>
<li>서로 다른 조건이 하나의 답변에 섞일 수 있다.</li>
</ul>
<p>결국 Chunking에는 작은 Chunk와 큰 Chunk 사이의 Trade-off가 존재한다.</p>
<pre><code class="language-text">작은 Chunk
→ 검색 정밀도는 높음
→ 문맥은 부족함

큰 Chunk
→ 문맥은 풍부함
→ 검색 결과에 불필요한 내용이 포함됨</code></pre>
<h2 id="chunking-전략">Chunking 전략</h2>
<h3 id="고정-길이로-나누기">고정 길이로 나누기</h3>
<p>가장 단순한 방법은 일정한 길이로 문서를 나누는 것이다.</p>
<pre><code class="language-pseudo">chunks = split_by_length(
    text,
    chunk_size = 800,
    overlap = 120
)</code></pre>
<p>고정 길이 분할은 구현하기 쉽고 많은 문서를 빠르게 처리할 수 있다.</p>
<p>하지만 문장이나 표의 중간에서 끊길 수 있다. 그래서 Chunk 사이에 일부 문장을 겹치는 Overlap을 둘 수 있다.</p>
<pre><code class="language-text">Chunk 1: A B C D E F
Chunk 2:             E F G H I J</code></pre>
<p>Overlap은 경계에서 문맥이 끊기는 문제를 줄여준다.</p>
<p>하지만 Overlap을 크게 만들수록 같은 내용이 여러 번 저장되고 검색 결과에도 중복이 늘어난다.</p>
<p>따라서 Chunk Size와 Overlap은 함께 실험해야 한다.</p>
<h3 id="문서-구조에-따라-나누기">문서 구조에 따라 나누기</h3>
<p>모든 문서를 같은 길이로 나누는 것이 항상 좋은 방법은 아니다.</p>
<p>문서의 형식에 따라 의미가 유지되는 경계가 다르기 때문이다.</p>
<pre><code class="language-text">FAQ
→ 질문 + 답변

일반 문서
→ 문장 / 문단

계약서
→ 조항

규정
→ 장 / 절 / 조

기술 문서
→ Section</code></pre>
<p>Markdown이나 HTML처럼 제목 구조가 있는 문서는 Heading 경로를 보존하는 것이 좋다.</p>
<pre><code class="language-text">문서: 인사 규정
경로: 휴가 정책 &gt; 휴가 승인 기준

연차 휴가는 팀 리더의 승인을 받은 후 사용할 수 있다.</code></pre>
<p>본문만 저장하는 것보다 어떤 문서의 어떤 절에 속하는지 함께 보존하는 편이 검색과 답변에 유리하다.</p>
<h3 id="pdf와-표를-처리할-때">PDF와 표를 처리할 때</h3>
<p>PDF는 화면에서 보이는 구조와 추출된 Text의 구조가 다를 수 있다.</p>
<p>다음과 같은 문제가 자주 발생한다.</p>
<ul>
<li>두 개의 열이 섞인다.</li>
<li>머리글과 바닥글이 반복된다.</li>
<li>표의 열 순서가 깨진다.</li>
<li>페이지 경계에서 문장이 끊긴다.</li>
<li>이미지로 된 글자가 추출되지 않는다.</li>
</ul>
<p>따라서 PDF는 바로 Chunking하기보다 추출 결과를 먼저 확인해야 한다.</p>
<pre><code class="language-text">PDF
    ↓
페이지별 Text 확인
    ↓
머리글과 바닥글 제거
    ↓
표와 목록 복원
    ↓
문서 구조 복원
    ↓
Chunking</code></pre>
<p>표는 행 단위로 변환하거나 질문에 필요한 열 이름을 반복해서 넣을 수 있다.</p>
<pre><code class="language-text">항목: 휴가 종류
대상: 연차
승인자: 팀 리더
신청 경로: 사내 포털</code></pre>
<p>표의 시각적 배치가 사라지더라도 질문에 필요한 관계가 남아 있어야 한다.</p>
<p>문서의 시각적 경계와 의미의 경계가 항상 일치하는 것은 아니다.</p>
<p>페이지가 바뀌었다고 문장이 끝나는 것은 아니고, 제목이 바뀌었다고 이전 조건이 사라지는 것도 아니다. 반대로 하나의 표 안에서도 행마다 서로 다른 질문에 답하는 경우가 있다.</p>
<p>따라서 문서 구조를 복원할 때는 다음을 함께 확인해야 한다.</p>
<pre><code class="language-text">표의 제목과 열 이름이 각 행에 연결되어 있는가?

조항의 예외와 단서가 본문과 함께 남아 있는가?

페이지 경계에서 문장이 잘리지 않았는가?

Heading 경로가 Chunk Metadata에 보존되어 있는가?</code></pre>
<h2 id="chunk-문맥을-보존하기">Chunk 문맥을 보존하기</h2>
<h3 id="contextual-retrieval">Contextual Retrieval</h3>
<p>Chunk만 보았을 때 문맥이 부족한 경우가 있다.</p>
<pre><code class="language-text">이 경우에는 14일 이내에 반환해야 한다.</code></pre>
<p>이 문장만 보면 무엇을 반환하는지 알기 어렵다.</p>
<p>이때 Chunk가 원본 문서의 어떤 문맥에 속하는지 설명하는 내용을 앞에 붙일 수 있다.</p>
<pre><code class="language-text">[퇴직자 자산 반납 규정]

본 문서는 퇴직자가 회사에서 지급받은
업무용 장비를 반환하는 절차를 설명한다.

이 경우에는 14일 이내에 반환해야 한다.</code></pre>
<p>이처럼 Contextual Retrieval은 질문을 수정하는 것이 아니라, 검색 대상인 Chunk 자체를 검색하기 좋은 형태로 개선하는 방법이다.</p>
<p>다만 원문에 없는 사실을 추가하면 안 된다.</p>
<p>문서의 제목과 경로와 확인 가능한 요약 정도만 보강하는 것이 안전하다.</p>
<h3 id="parent-child-retrieval">Parent-Child Retrieval</h3>
<p>Chunk에는 구조적인 Trade-off가 존재한다.</p>
<p>작은 Chunk는 검색에 유리하지만 문맥이 부족하다. 큰 Chunk는 문맥이 풍부하지만 검색 정밀도가 떨어질 수 있다.</p>
<p>Parent-Child Retrieval은 검색 단위와 LLM에 전달할 단위를 분리한다.</p>
<pre><code class="language-text">Parent
├─ Child
├─ Child
├─ Child
└─ Child</code></pre>
<p>검색은 작은 Child를 사용한다.</p>
<pre><code class="language-text">질문
    ↓
Child 검색
    ↓
parentId
    ↓
Parent 또는 인접 Chunk
    ↓
LLM</code></pre>
<p>즉 검색은 작은 단위로 정밀하게 수행하고, 생성에는 충분한 문맥을 제공하는 방식이다.</p>
<p>Parent 전체를 항상 전달하면 Context가 다시 커질 수 있다.</p>
<p>검색된 Child가 속한 절이나 앞뒤 Chunk만 확장하는 방식도 함께 고려할 수 있다.</p>
<h2 id="metadata를-함께-저장하기">Metadata를 함께 저장하기</h2>
<p>Metadata는 파일 이름을 표시하기 위한 값만은 아니다.</p>
<p>검색 범위와 출처와 버전을 제어하는 데 사용된다.</p>
<pre><code class="language-json">{
  &quot;documentId&quot;: &quot;leave-policy&quot;,
  &quot;source&quot;: &quot;hr/leave-policy.pdf&quot;,
  &quot;title&quot;: &quot;휴가 정책&quot;,
  &quot;version&quot;: &quot;2025-03&quot;,
  &quot;effectiveFrom&quot;: &quot;2025-03-01&quot;,
  &quot;department&quot;: &quot;HR&quot;,
  &quot;documentType&quot;: &quot;POLICY&quot;,
  &quot;tenantId&quot;: &quot;company-a&quot;,
  &quot;chunkIndex&quot;: 3,
  &quot;parentId&quot;: &quot;leave-policy-section-2&quot;
}</code></pre>
<p>Metadata는 다음과 같은 역할을 한다.</p>
<pre><code class="language-text">검색 범위 제한
    ↓
문서 버전 선택
    ↓
권한 필터 적용
    ↓
답변 출처 생성</code></pre>
<h3 id="metadata를-역할별로-나누기">Metadata를 역할별로 나누기</h3>
<p>Metadata를 하나의 평평한 값 목록으로만 보면 어떤 값이 검색 필터이고 어떤 값이 출처 정보인지 구분하기 어렵다.</p>
<pre><code class="language-text">Identity
→ documentId, chunkId, source

Structure
→ sectionPath, page, chunkIndex, parentId

Lifecycle
→ version, effectiveFrom, effectiveTo, status

Access
→ tenantId, department, accessScope

Provenance
→ parserVersion, embeddingModel, ingestedAt</code></pre>
<p>이 구분은 운영을 위한 장식이 아니다.</p>
<p>문서가 같은 내용인지 비교할 때는 Identity와 Version이 필요하고, 권한을 적용할 때는 Access가 필요하다. 검색 결과를 재현할 때는 Embedding Model과 적재 시점이 필요하다.</p>
<p>모든 Metadata를 Vector에 포함시키는 것도 적절하지 않다. 권한과 상태처럼 반드시 먼저 적용해야 하는 값은 Metadata Filter로 처리하고, 제목과 경로처럼 의미 검색에 도움이 되는 값은 Chunk의 검색 텍스트에 포함할지 별도로 판단해야 한다.</p>
<p>예를 들어 현재 활성화된 문서만 검색하려면 다음과 같은 조건이 필요하다.</p>
<pre><code class="language-pseudo">filters = {
    &quot;tenantId&quot;: authenticated_user.tenant_id,
    &quot;department&quot;: allowed_departments,
    &quot;status&quot;: &quot;ACTIVE&quot;
}

results = vector_store.search(
    query_vector,
    filters = filters
)</code></pre>
<p>권한과 관련된 Metadata는 사용자가 입력한 질문에서 가져오면 안 된다.</p>
<p>사용자가 HR 문서를 보여달라고 입력했다고 해서 HR 문서를 볼 수 있는 것은 아니다. 인증 정보와 서버 정책으로 허용 범위를 계산한 뒤 검색 필터에 적용해야 한다.</p>
<h3 id="문서-버전과-최신성">문서 버전과 최신성</h3>
<p>정책 문서나 기술 문서는 시간이 지나면서 변경된다.</p>
<pre><code class="language-text">휴가 정책 2023
휴가 정책 2024
휴가 정책 2025</code></pre>
<p>같은 주제의 문서가 여러 개 검색되면 어떤 버전을 답변에 사용할지 결정해야 한다.</p>
<p>작성일과 시행일과 폐기일은 다를 수 있다.</p>
<p>따라서 가능하다면 다음 값을 구분해 저장하는 것이 좋다.</p>
<ul>
<li>작성일</li>
<li>시행일</li>
<li>폐기일</li>
<li>현재 활성 상태</li>
<li>변경 대상</li>
</ul>
<p>현재 정책을 묻는 질문에는 ACTIVE 문서를 우선하고, 변경 이력을 묻는 질문에는 과거 버전도 검색할 수 있다.</p>
<h3 id="멱등적인-적재">멱등적인 적재</h3>
<p>같은 문서를 다시 적재했을 때 Chunk가 중복 저장되면 안 된다.</p>
<p>Chunk ID를 원본과 버전과 위치를 이용해 만들 수 있다.</p>
<pre><code class="language-pseudo">chunk_id = hash(
    document_id
    + version
    + section_path
    + chunk_index
)</code></pre>
<p>같은 원본과 같은 버전으로 다시 적재하면 기존 ID가 갱신된다.</p>
<p>문서 내용이 바뀌면 Version이나 Content Hash가 달라져 새로운 적재 작업으로 구분할 수 있다.</p>
<p>적재 상태도 함께 관리하는 것이 좋다.</p>
<pre><code class="language-text">PENDING
    ↓
PROCESSING
    ├─ ACTIVE
    └─ FAILED</code></pre>
<p>적재 중인 문서가 일부만 검색되지 않도록 검증이 완료된 뒤 한 번에 ACTIVE 상태로 전환하는 방식을 사용할 수 있다.</p>
<h2 id="chunking-실험">Chunking 실험</h2>
<h3 id="평가-목표를-먼저-정하기">평가 목표를 먼저 정하기</h3>
<p>Chunking 실험은 Chunk Size를 정하는 실험이 아니라, 어떤 품질을 보존할지 정하는 실험이다.</p>
<pre><code class="language-text">정답 문서를 놓치지 않는 것이 중요한가?
→ Retrieval Recall

관계없는 문서를 줄이는 것이 중요한가?
→ Context Precision

조건과 예외를 답변에 유지하는 것이 중요한가?
→ Faithfulness와 Answer Correctness

짧은 Context와 낮은 비용이 중요한가?
→ Context Length와 Latency</code></pre>
<p>하나의 지표만 높이는 Chunking은 다른 품질을 떨어뜨릴 수 있다. 큰 Chunk는 필요한 문장을 함께 보존할 수 있지만 Context가 불필요하게 커질 수 있고, 작은 Chunk는 검색 후보를 정밀하게 만들지만 조건과 예외를 분리할 수 있다.</p>
<p>Chunk Size는 정답을 외워서 적용하는 값이 아니다.</p>
<p>질문 세트를 준비하고 여러 설정을 비교해야 한다.</p>
<pre><code class="language-text">실험 A: 400 / overlap 40
실험 B: 800 / overlap 120
실험 C: 문단 기준
실험 D: Section 기준 + 인접 Chunk 확장</code></pre>
<p>각 실험에서 다음을 확인한다.</p>
<ul>
<li>정답 문서가 검색되었는가</li>
<li>질문에 필요한 문장이 같은 Chunk에 있는가</li>
<li>중복 Chunk가 많이 검색되는가</li>
<li>Context 길이가 지나치게 커지지 않는가</li>
<li>답변이 문서의 조건과 예외를 유지하는가</li>
</ul>
<p>평균 검색 점수만 보고 결정하면 안 된다.</p>
<p>어떤 질문이 좋아졌고 어떤 질문이 나빠졌는지 확인해야 실제 Chunking 전략을 선택할 수 있다.</p>
<h3 id="같은-질문으로-비교하기">같은 질문으로 비교하기</h3>
<p>Chunking 실험에서는 질문과 문서와 검색 모델을 고정하고 Chunking 설정만 바꾸는 편이 좋다.</p>
<pre><code class="language-text">고정
→ 평가 질문
→ 원본 문서
→ Embedding Model
→ 검색 방식

변경
→ Chunk Size
→ Overlap
→ 구조 기반 분할 여부
→ Parent 확장 범위</code></pre>
<p>여러 조건을 한 번에 바꾸면 결과가 좋아져도 어떤 변경이 영향을 주었는지 알 수 없다.</p>
<p>또한 검색 결과만 보지 말고 최종 Context와 답변까지 확인해야 한다. 정답 문서가 검색되었지만 필요한 문장이 다른 Chunk에 떨어져 있거나, Parent 확장 과정에서 관계없는 내용이 추가될 수 있기 때문이다.</p>
<h2 id="마무리">마무리</h2>
<p>Chunking은 문서를 잘게 자르는 전처리 작업이 아니다.</p>
<p>사용자의 질문에 답할 수 있는 의미 단위를 설계하는 과정이다.</p>
<p>Chunk가 너무 작으면 문맥이 사라지고, 너무 크면 관련 없는 정보가 함께 검색된다. 문서의 구조에 따라 분할 기준을 달리하고, 필요한 경우 Contextual Retrieval이나 Parent-Child Retrieval을 적용할 수 있다.</p>
<p>Metadata는 검색 결과의 출처를 표시하는 값이면서, 버전과 권한과 검색 범위를 관리하는 값이다.</p>
<p>결국 좋은 Chunk는 검색 결과만 보아도 다음 질문에 답할 수 있어야 한다.</p>
<blockquote>
<p>이 내용은 어떤 문서의 어느 위치에서 왔고, 어떤 질문에 사용할 수 있는가?</p>
</blockquote>
