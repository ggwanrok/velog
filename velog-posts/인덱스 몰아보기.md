<h1 id="인덱스-완전-정리">인덱스 완전 정리</h1>
<h2 id="기본-원리부터-btree-postgresql-인덱스-설계까지">기본 원리부터 B+Tree, PostgreSQL 인덱스 설계까지</h2>
<p>데이터베이스에서 인덱스는 단순히 조회를 빠르게 만드는 기능이 아니다.</p>
<p>인덱스를 제대로 이해하려면 다음 내용을 함께 알아야 한다.</p>
<pre><code class="language-text">인덱스는 어떤 정보를 저장하는가?
데이터의 물리적 저장 순서와 어떤 관계가 있는가?
B+Tree는 왜 디스크 기반 DBMS에 적합한가?
인덱스가 있는데도 왜 Sequential Scan이 선택되는가?
PostgreSQL의 Bitmap Scan과 Cluster는 무엇이 다른가?
인덱스가 INSERT·UPDATE·DELETE에 어떤 비용을 발생시키는가?</code></pre>
<p>이 글에서는 인덱스의 기본 원리부터 전통적인 분류, B+Tree 구조, PostgreSQL의 주요 인덱스 종류와 실무 설계 기준까지 순서대로 정리한다.</p>
<hr />
<h1 id="1-인덱스란">1. 인덱스란?</h1>
<p>인덱스(Index, 색인)는 테이블 전체를 처음부터 끝까지 읽지 않고 원하는 데이터의 위치를 빠르게 찾기 위한 보조 자료구조다.</p>
<p>책에서 특정 단어를 찾을 때 모든 페이지를 순서대로 넘기는 대신, 책 뒤의 색인에서 단어와 페이지 번호를 확인하는 것과 비슷하다.</p>
<pre><code class="language-text">탐색 키(Search Key) → 데이터 위치(Pointer)</code></pre>
<p>예를 들어 다음과 같은 테이블이 있다고 하자.</p>
<pre><code class="language-text">employee_id   name
1001          김철수
1002          이영희
1003          박민수</code></pre>
<p><code>employee_id</code>에 인덱스를 생성하면 개념적으로 다음과 같은 정보가 저장된다.</p>
<pre><code class="language-text">1001 → 데이터 위치 A
1002 → 데이터 위치 B
1003 → 데이터 위치 C</code></pre>
<p>따라서 다음 쿼리가 실행될 때 DBMS는 테이블 전체를 순차 탐색하는 대신 인덱스를 먼저 탐색할 수 있다.</p>
<pre><code class="language-sql">SELECT *
FROM employees
WHERE employee_id = 1002;</code></pre>
<p>인덱스가 없다면 테이블의 행을 처음부터 확인해야 할 수 있다.</p>
<pre><code class="language-text">1001인가? → 아니오
1002인가? → 맞음</code></pre>
<p>반면 인덱스가 있다면 정렬된 트리나 해시 구조 등을 이용해 데이터가 저장된 위치를 빠르게 알아낼 수 있다.</p>
<hr />
<h1 id="2-인덱스-엔트리의-기본-구성">2. 인덱스 엔트리의 기본 구성</h1>
<p>인덱스는 일반적으로 다음과 같은 엔트리로 구성된다.</p>
<pre><code class="language-text">&lt;Search Key, Pointer&gt;</code></pre>
<hr />
<h2 id="21-search-key">2.1 Search Key</h2>
<p>Search Key는 데이터를 찾는 기준이 되는 하나 이상의 컬럼이다.</p>
<pre><code class="language-sql">CREATE INDEX idx_employees_name
ON employees(name);</code></pre>
<p>이 경우 <code>name</code>이 탐색 키다.</p>
<p>탐색 키는 반드시 Primary Key일 필요가 없다.</p>
<p>다음과 같은 컬럼도 탐색 키가 될 수 있다.</p>
<pre><code class="language-text">이름
이메일
부서 번호
급여
생성 일시
상태
여러 컬럼의 조합</code></pre>
<p>복합 인덱스는 여러 컬럼을 하나의 탐색 키로 사용한다.</p>
<pre><code class="language-sql">CREATE INDEX idx_orders_customer_status
ON orders(customer_id, status);</code></pre>
<p>이 경우 탐색 키는 다음 컬럼의 조합이다.</p>
<pre><code class="language-text">(customer_id, status)</code></pre>
<hr />
<h2 id="22-pointer">2.2 Pointer</h2>
<p>Pointer는 탐색 키에 해당하는 데이터 또는 다음 탐색 위치를 가리킨다.</p>
<p>구현 방식에 따라 포인터는 다음 중 하나를 가리킬 수 있다.</p>
<pre><code class="language-text">실제 데이터 레코드
데이터가 들어 있는 페이지
동일한 키를 가진 레코드들의 위치 목록
하위 단계의 인덱스 페이지
Primary Key 값
Heap Tuple의 위치</code></pre>
<p>PostgreSQL의 일반적인 인덱스 엔트리는 개념적으로 다음과 같이 볼 수 있다.</p>
<pre><code class="language-text">인덱스 키 + TID</code></pre>
<p>TID, 즉 Tuple Identifier는 Heap에 저장된 행의 물리적 위치를 나타낸다.</p>
<pre><code class="language-text">Heap 페이지 번호 + 페이지 내부 튜플 위치</code></pre>
<p>따라서 PostgreSQL의 일반적인 <code>Index Scan</code>은 다음 흐름으로 동작한다.</p>
<pre><code class="language-text">1. 인덱스에서 조건에 맞는 키 탐색
2. 인덱스 엔트리에서 TID 확인
3. TID가 가리키는 Heap 페이지로 이동
4. MVCC 가시성 확인
5. 조건을 만족하는 행 반환</code></pre>
<hr />
<h1 id="3-인덱스와-페이지">3. 인덱스와 페이지</h1>
<p>디스크 기반 DBMS는 일반적으로 레코드 하나씩 디스크에서 읽지 않는다.</p>
<p>여러 레코드가 들어 있는 페이지 또는 블록 단위로 데이터를 읽는다.</p>
<pre><code class="language-text">디스크
└── 데이터 파일
    ├── Page 1
    ├── Page 2
    ├── Page 3
    └── ...</code></pre>
<p>인덱스 역시 페이지 단위로 저장된다.</p>
<pre><code class="language-text">인덱스 페이지
&lt;Key, Address&gt;</code></pre>
<p>인덱스 검색 과정은 개념적으로 다음과 같다.</p>
<pre><code class="language-text">인덱스 페이지 탐색
        ↓
조건에 맞는 주소 확인
        ↓
데이터 페이지 접근
        ↓
페이지 내부에서 실제 행 확인</code></pre>
<p>따라서 인덱스 성능을 이해할 때는 단순한 비교 연산 횟수뿐 아니라 다음 요소가 중요하다.</p>
<pre><code class="language-text">몇 개의 인덱스 페이지를 읽는가?
몇 개의 데이터 페이지를 읽는가?
데이터 페이지를 순차적으로 읽는가?
여러 위치를 무작위로 읽는가?
필요한 페이지가 메모리에 존재하는가?</code></pre>
<hr />
<h1 id="4-인덱스의-장점과-비용">4. 인덱스의 장점과 비용</h1>
<p>인덱스는 조회 성능을 높일 수 있지만 공짜로 제공되는 기능은 아니다.</p>
<hr />
<h2 id="41-인덱스가-지원하는-작업">4.1 인덱스가 지원하는 작업</h2>
<p>인덱스는 다음 작업의 성능을 개선할 수 있다.</p>
<h3 id="정확한-일치-검색">정확한 일치 검색</h3>
<pre><code class="language-sql">WHERE employee_id = 100</code></pre>
<p>특정 값과 정확히 일치하는 데이터를 찾는다.</p>
<p>이를 Equality Search 또는 Exact Match라고 한다.</p>
<h3 id="범위-검색">범위 검색</h3>
<pre><code class="language-sql">WHERE salary BETWEEN 5000 AND 10000</code></pre>
<pre><code class="language-sql">WHERE created_at &gt;= DATE '2026-01-01'</code></pre>
<p>특정 범위에 포함되는 데이터를 찾는다.</p>
<h3 id="정렬">정렬</h3>
<pre><code class="language-sql">ORDER BY created_at</code></pre>
<p>인덱스가 원하는 순서로 정렬되어 있다면 별도의 Sort 작업을 생략하거나 줄일 수 있다.</p>
<h3 id="조인">조인</h3>
<pre><code class="language-sql">ON employees.department_id = departments.department_id</code></pre>
<p>조인 대상 행을 빠르게 찾는 데 사용할 수 있다.</p>
<h3 id="최솟값과-최댓값">최솟값과 최댓값</h3>
<pre><code class="language-sql">SELECT MIN(salary)
FROM employees;</code></pre>
<p>정렬된 인덱스의 처음이나 마지막 부분을 이용할 수 있다.</p>
<h3 id="고유성-검사">고유성 검사</h3>
<pre><code class="language-sql">CREATE UNIQUE INDEX ...</code></pre>
<p>중복 값을 빠르게 검사할 수 있다.</p>

<hr />
<h2 id="43-postgresql의-mvcc와-인덱스-갱신">4.3 PostgreSQL의 MVCC와 인덱스 갱신</h2>
<p>PostgreSQL은 MVCC를 사용한다.</p>
<p>따라서 UPDATE나 DELETE가 발생했다고 해서 기존 행과 인덱스 엔트리가 즉시 물리적으로 제거되는 것은 아니다.</p>
<h3 id="update">UPDATE</h3>
<pre><code class="language-text">기존 행을 직접 덮어씀</code></pre>
<p>이 아니라 다음과 같이 처리된다.</p>
<pre><code class="language-text">기존 행 버전을 만료 상태로 표시
→ 새로운 행 버전 생성
→ 필요한 경우 새로운 인덱스 엔트리 생성</code></pre>
<h3 id="delete">DELETE</h3>
<pre><code class="language-text">행을 파일에서 즉시 제거</code></pre>
<p>하는 것이 아니라 삭제된 행 버전으로 표시한다.</p>
<p>더 이상 어떤 트랜잭션도 해당 버전을 볼 필요가 없어지면 VACUUM이 공간을 재사용할 수 있도록 정리한다.</p>
<h3 id="hot-update">HOT Update</h3>
<p>PostgreSQL은 조건을 만족하면 HOT, Heap-Only Tuple Update를 사용할 수 있다.</p>
<pre><code class="language-text">인덱스에 포함된 컬럼이 변경되지 않음
+
같은 Heap 페이지에 새 행 버전을 저장할 공간이 있음</code></pre>
<p>이 조건을 만족하면 새로운 인덱스 엔트리를 생성하지 않고 Heap 내부에서 새 행 버전을 연결할 수 있다.</p>
<pre><code class="language-text">일반 UPDATE
→ Heap 갱신 + 인덱스 갱신 가능

HOT UPDATE
→ Heap 내부 행 버전만 연결
→ 새 인덱스 엔트리 생성을 피할 수 있음</code></pre>
<p>이 때문에 PostgreSQL의 UPDATE 비용은 인덱스 개수뿐 아니라 어떤 컬럼을 변경하는지에도 영향을 받는다.</p>
<hr />
<h1 id="5-전통적인-인덱스-분류">5. 전통적인 인덱스 분류</h1>
<p>인덱스는 여러 기준으로 분류할 수 있다.</p>
<p>다음 분류들은 서로 다른 기준을 사용한다.</p>
<pre><code class="language-text">Ordered Index / Hash Index
→ 탐색 키의 순서를 유지하는가?

Primary / Clustering / Secondary Index
→ 인덱스 키와 데이터의 물리적 저장 순서가 어떤 관계인가?

Dense / Sparse Index
→ 인덱스 엔트리를 얼마나 촘촘하게 저장하는가?</code></pre>
<p>따라서 서로 다른 분류를 하나의 개념처럼 연결하면 안 된다.</p>
<hr />
<h1 id="6-ordered-index와-hash-index">6. Ordered Index와 Hash Index</h1>
<h2 id="61-ordered-index">6.1 Ordered Index</h2>
<p>Ordered Index는 탐색 키가 정렬된 순서로 저장되는 인덱스다.</p>
<pre><code class="language-text">10 → 위치 A
20 → 위치 B
30 → 위치 C
40 → 위치 D</code></pre>
<p>값의 순서가 유지되므로 다음 작업에 적합하다.</p>
<pre><code class="language-sql">WHERE id = 20</code></pre>
<pre><code class="language-sql">WHERE id &gt; 20</code></pre>
<pre><code class="language-sql">WHERE id BETWEEN 10 AND 30</code></pre>
<pre><code class="language-sql">ORDER BY id</code></pre>
<p>대표적인 Ordered Index 구조가 B-Tree와 B+Tree다.</p>
<hr />
<h2 id="62-hash-index">6.2 Hash Index</h2>
<p>Hash Index는 탐색 키를 해시 함수에 넣어 버킷 위치를 계산한다.</p>
<pre><code class="language-text">'kim@example.com'
        ↓
      hash()
        ↓
    Bucket 17</code></pre>
<p>정확한 값 검색에 적합하다.</p>
<pre><code class="language-sql">WHERE email = 'kim@example.com'</code></pre>
<p>그러나 해시는 원래 값의 순서를 보존하지 않는다.</p>
<pre><code class="language-text">원래 값: 10, 20, 30
해시값:  81, 13, 55</code></pre>
<p>따라서 다음과 같은 검색에는 적합하지 않다.</p>
<pre><code class="language-sql">WHERE salary &gt; 5000</code></pre>
<pre><code class="language-sql">WHERE age BETWEEN 20 AND 30</code></pre>
<pre><code class="language-sql">ORDER BY salary</code></pre>
<hr />
<h1 id="7-primary-clustering-secondary-index">7. Primary, Clustering, Secondary Index</h1>
<p>이 분류는 다음 질문을 기준으로 한다.</p>
<blockquote>
<p>인덱스 탐색 키의 순서와 실제 데이터 파일의 저장 순서가 일치하는가?</p>
</blockquote>
<p>이 용어는 전통적인 데이터베이스 교재와 상용 DBMS 제품에서 조금씩 다르게 사용될 수 있다.</p>
<p>따라서 특정 DBMS를 설명할 때는 해당 DBMS의 실제 저장 구조를 함께 확인해야 한다.</p>
<hr />
<h2 id="71-primary-index">7.1 Primary Index</h2>
<p>전통적인 데이터베이스 교재에서 Primary Index는 데이터 파일이 고유한 탐색 키 순서로 정렬되어 있고, 그 정렬 기준에 만들어진 인덱스를 의미한다.</p>
<pre><code class="language-text">데이터 파일

1001 김철수
1002 이영희
1003 박민수
1004 최지수</code></pre>
<p>데이터가 <code>employee_id</code> 순서로 저장되어 있고, 해당 컬럼을 탐색 키로 사용한다면 Primary Index로 볼 수 있다.</p>
<p>기본키가 정렬 기준으로 사용되는 경우가 많지만 핵심은 <code>PRIMARY KEY</code>라는 이름 자체가 아니다.</p>
<pre><code class="language-text">고유한 탐색 키
+
실제 데이터 저장 순서</code></pre>
<p>의 관계가 중요하다.</p>
<hr />
<h2 id="72-clustering-index">7.2 Clustering Index</h2>
<p>Clustering Index는 데이터가 특정 탐색 키 값에 따라 물리적으로 모여 있는 구조다.</p>
<p>탐색 키는 중복될 수 있다.</p>
<pre><code class="language-text">department_id 순서로 저장

10 김철수
10 박민수
10 이지수
20 최영희
20 윤서연</code></pre>
<p>같은 <code>department_id</code>를 가진 행이 가까운 페이지에 모여 있다.</p>
<p>인덱스는 각 그룹의 시작 위치를 가리킬 수 있다.</p>
<pre><code class="language-text">10 → 10번 부서 데이터의 시작 위치
20 → 20번 부서 데이터의 시작 위치</code></pre>
<p>범위 검색이나 동일한 값을 가진 여러 행을 읽을 때 관련 데이터가 가까운 페이지에 모여 있으므로 I/O 효율을 높일 수 있다.</p>
<hr />
<h2 id="73-secondary-index">7.3 Secondary Index</h2>
<p>Secondary Index는 인덱스 탐색 키의 순서와 실제 데이터 파일의 저장 순서가 일치하지 않는 인덱스다.</p>
<pre><code class="language-text">실제 데이터: employee_id 순서

1001 김철수 개발팀
1002 이영희 인사팀
1003 박민수 개발팀
1004 최지수 재무팀</code></pre>
<p>여기서 <code>department_name</code>을 기준으로 인덱스를 만들면 인덱스 자체는 다음처럼 정렬될 수 있다.</p>
<pre><code class="language-text">개발팀 → 1001의 위치, 1003의 위치
인사팀 → 1002의 위치
재무팀 → 1004의 위치</code></pre>
<p>하지만 실제 데이터는 여러 블록에 흩어져 있을 수 있다.</p>
<pre><code class="language-text">개발팀 데이터

레코드 1 → Block 2
레코드 2 → Block 19
레코드 3 → Block 7</code></pre>
<p>조회 대상이 많으면 여러 데이터 페이지를 무작위로 방문해야 한다.</p>
<pre><code class="language-text">Block 2
→ Block 19
→ Block 7
→ Block 31
→ ...</code></pre>
<p>이 경우 인덱스를 사용하는 것보다 테이블 전체를 순차적으로 읽는 편이 더 빠를 수 있다.</p>
<hr />
<h1 id="8-dense-index와-sparse-index">8. Dense Index와 Sparse Index</h1>
<p>이 분류는 다음 질문을 기준으로 한다.</p>
<blockquote>
<p>인덱스 엔트리를 얼마나 촘촘하게 저장하는가?</p>
</blockquote>
<p>Primary·Clustering·Secondary는 데이터 저장 순서와의 관계를 기준으로 한다.</p>
<p>반면 Dense·Sparse는 인덱스 엔트리의 밀도를 기준으로 한다.</p>
<p>서로 다른 분류 축이다.</p>
<hr />
<h2 id="81-dense-index">8.1 Dense Index</h2>
<p>Dense Index는 모든 탐색 키 값에 대응하는 인덱스 엔트리가 존재하는 구조다.</p>
<pre><code class="language-text">데이터

1001 김철수
1002 이영희
1003 박민수
1004 최지수</code></pre>
<pre><code class="language-text">Dense Index

1001 → 레코드 위치
1002 → 레코드 위치
1003 → 레코드 위치
1004 → 레코드 위치</code></pre>
<p>중복 키가 있는 경우 반드시 레코드마다 하나의 키 엔트리가 존재해야 한다는 뜻은 아니다.</p>
<p>모든 탐색 키 값에 대한 접근 정보가 존재하면 된다.</p>
<pre><code class="language-text">개발팀 → 포인터 목록
           ├─ 김철수 위치
           ├─ 박민수 위치
           └─ 윤서연 위치</code></pre>
<h3 id="장점">장점</h3>
<pre><code class="language-text">인덱스에서 원하는 키의 위치를 직접 확인할 수 있음
검색 과정이 비교적 빠름
데이터가 탐색 키 순서로 정렬되지 않아도 사용 가능</code></pre>
<h3 id="단점">단점</h3>
<pre><code class="language-text">인덱스 엔트리가 많음
저장 공간 사용량 증가
삽입·삭제·수정 비용 증가</code></pre>
<p>Secondary Index는 일반적으로 Dense한 구조를 사용한다.</p>
<p>데이터가 탐색 키 순서로 저장되어 있지 않기 때문에 각 키가 어디에 존재하는지 개별적으로 기록해야 하기 때문이다.</p>
<hr />
<h2 id="82-sparse-index">8.2 Sparse Index</h2>
<p>Sparse Index는 일부 탐색 키에 대해서만 인덱스 엔트리를 저장한다.</p>
<pre><code class="language-text">데이터 블록

Block 1: 1001, 1002
Block 2: 1003, 1004
Block 3: 1005, 1006</code></pre>
<pre><code class="language-text">Sparse Index

1001 → Block 1
1003 → Block 2
1005 → Block 3</code></pre>
<p><code>1004</code>를 찾는 과정은 다음과 같다.</p>
<pre><code class="language-text">1. 인덱스에서 1004 이하의 가장 큰 대표 키 탐색
2. 1003을 찾음
3. 1003이 가리키는 Block 2로 이동
4. Block 2 내부에서 1004 탐색</code></pre>
<p>Sparse Index가 동작하려면 데이터가 탐색 키 순서로 정렬되어 있어야 한다.</p>
<p>정렬되어 있어야 특정 값이 어느 대표 키 사이에 있는지 추론할 수 있기 때문이다.</p>
<h3 id="장점-1">장점</h3>
<pre><code class="language-text">인덱스 엔트리가 적음
저장 공간을 적게 사용함
인덱스 자체를 읽는 비용이 작음</code></pre>
<h3 id="단점-1">단점</h3>
<pre><code class="language-text">데이터 블록 내부를 추가로 검색해야 함
대표 키가 변경되면 인덱스 수정이 필요함
데이터가 탐색 키 순서로 정렬되어 있어야 함</code></pre>
<hr />
<h2 id="83-각-분류의-관계">8.3 각 분류의 관계</h2>
<table>
<thead>
<tr>
<th>구조</th>
<th align="right">Dense 가능</th>
<th align="right">Sparse 가능</th>
</tr>
</thead>
<tbody><tr>
<td>Primary 또는 Clustering Index</td>
<td align="right">가능</td>
<td align="right">가능</td>
</tr>
<tr>
<td>Secondary 또는 Non-clustered Index</td>
<td align="right">가능</td>
<td align="right">일반적으로 어려움</td>
</tr>
</tbody></table>
<p>핵심 관계는 다음과 같다.</p>
<pre><code class="language-text">Primary 또는 Clustering Index
→ 데이터가 탐색 키 순서로 정렬됨
→ 데이터 블록의 대표 키만 저장하는 Sparse Index 가능

Secondary Index
→ 데이터가 탐색 키 순서로 정렬되지 않음
→ 각 탐색 키의 위치가 필요
→ 일반적으로 Dense Index 사용</code></pre>
<hr />
<h1 id="9-multilevel-index">9. Multilevel Index</h1>
<p>인덱스 파일도 데이터가 많아지면 매우 커진다.</p>
<p>인덱스 전체가 메모리에 들어가지 않는다면 원하는 인덱스 엔트리를 찾기 위해 인덱스 페이지 자체를 여러 개 읽어야 한다.</p>
<p>이를 해결하기 위해 인덱스 위에 다시 인덱스를 구성할 수 있다.</p>
<pre><code class="language-text">상위 인덱스
    ↓
하위 인덱스
    ↓
데이터 파일</code></pre>
<p>예를 들어 하위 인덱스 페이지가 다음과 같다고 하자.</p>
<pre><code class="language-text">Inner Index Block 1: 10, 20, 30
Inner Index Block 2: 40, 50, 60
Inner Index Block 3: 70, 80, 90</code></pre>
<p>상위 인덱스에는 각 하위 페이지의 대표 키만 저장할 수 있다.</p>
<pre><code class="language-text">Outer Index

10 → Inner Block 1
40 → Inner Block 2
70 → Inner Block 3</code></pre>
<p><code>50</code>을 찾는 과정은 다음과 같다.</p>
<pre><code class="language-text">상위 인덱스에서 40 확인
→ Inner Block 2로 이동
→ 하위 페이지에서 50 탐색
→ 실제 데이터 위치로 이동</code></pre>
<p>상위 인덱스는 모든 키를 저장하지 않고 하위 페이지의 대표 키만 저장하므로 Sparse Index와 비슷하게 동작한다.</p>
<p>이 다단계 인덱스 구조를 균형 있게 관리하는 대표적인 자료구조가 B-Tree와 B+Tree다.</p>
<hr />
<h1 id="10-b-tree와-btree">10. B-Tree와 B+Tree</h1>
<p>상용 DBMS에서 일반적으로 B-Tree라고 부르는 인덱스는 실제로 B+Tree 계열의 구조를 사용하는 경우가 많다.</p>
<hr />
<h2 id="101-b-tree-계열이-필요한-이유">10.1 B-Tree 계열이 필요한 이유</h2>
<p>일반적인 이진 탐색 트리는 한 노드가 최대 두 개의 자식을 가진다.</p>
<pre><code class="language-text">Binary Search Tree
→ 한 노드당 자식 최대 2개</code></pre>
<p>데이터가 많아지면 트리의 높이가 커질 수 있다.</p>
<p>디스크 기반 DBMS에서 트리 높이가 증가하면 필요한 페이지 접근 수도 증가한다.</p>
<p>반면 B-Tree 계열은 하나의 노드에 여러 개의 키와 포인터를 저장한다.</p>
<pre><code class="language-text">B-Tree 계열
→ 하나의 노드가 수십~수백 개의 자식을 가질 수 있음</code></pre>
<p>이를 높은 Fan-out이라고 한다.</p>
<pre><code class="language-text">높은 Fan-out
→ 트리 높이 감소
→ 인덱스 페이지 접근 횟수 감소</code></pre>
<p>따라서 데이터가 매우 많아도 비교적 적은 페이지 접근으로 원하는 리프 노드에 도달할 수 있다.</p>
<pre><code class="language-text">Root
 ↓
Internal Node
 ↓
Leaf Node</code></pre>
<hr />
<h2 id="102-btree의-내부-노드">10.2 B+Tree의 내부 노드</h2>
<p>내부 노드는 실제 검색 결과를 직접 제공하기보다 어느 하위 노드로 이동해야 하는지를 알려주는 길잡이 역할을 한다.</p>
<pre><code class="language-text">              [40 | 70]
             /    |    \
         10~30   40~60   70~90</code></pre>
<p>내부 노드는 일반적으로 모든 탐색 키를 저장하지 않는다.</p>
<p>하위 페이지의 범위를 구분하기 위한 대표 키와 포인터를 저장한다.</p>
<pre><code class="language-text">대표 키 → 하위 페이지</code></pre>
<p>따라서 내부 레벨은 하위 레벨을 대상으로 하는 Sparse Index처럼 이해할 수 있다.</p>
<hr />
<h2 id="103-btree의-리프-노드">10.3 B+Tree의 리프 노드</h2>
<p>실제 검색에 사용되는 인덱스 엔트리는 리프 노드에 저장된다.</p>
<pre><code class="language-text">[10, 20, 30] ↔ [40, 50, 60] ↔ [70, 80, 90]</code></pre>
<p>리프 노드는 탐색 키 순서로 정렬되어 있으며, 인접한 리프 노드들이 서로 연결되어 있다.</p>
<p>이 구조 덕분에 범위 검색이 효율적이다.</p>
<pre><code class="language-sql">WHERE salary BETWEEN 5000 AND 10000</code></pre>
<p>처리 과정은 다음과 같다.</p>
<pre><code class="language-text">1. 트리를 따라 5000이 위치할 리프 노드까지 이동
2. 리프 노드에서 5000 이상의 첫 키 탐색
3. 연결된 다음 리프 노드를 순서대로 읽음
4. 10000을 초과하면 탐색 종료</code></pre>
<p>범위에 포함되는 모든 값을 루트부터 각각 다시 검색할 필요가 없다.</p>
<hr />
<h2 id="104-리프-노드에-저장되는-정보">10.4 리프 노드에 저장되는 정보</h2>
<p>리프 노드에 저장되는 내용은 DBMS와 인덱스 종류에 따라 다르다.</p>
<h3 id="clustered-구조">Clustered 구조</h3>
<p>리프 노드가 실제 데이터 페이지이거나 전체 데이터 레코드를 포함할 수 있다.</p>
<pre><code class="language-text">1001 | 김철수 | 개발팀 | 5000
1002 | 이영희 | 인사팀 | 6000</code></pre>
<p>리프 노드에 도달하면 실제 데이터를 바로 얻을 수 있다.</p>
<h3 id="non-clustered-구조">Non-clustered 구조</h3>
<p>리프 노드에 다음 정보가 저장될 수 있다.</p>
<pre><code class="language-text">&lt;탐색 키, 실제 데이터 위치&gt;</code></pre>
<p>또는 DBMS에 따라 다음처럼 저장될 수 있다.</p>
<pre><code class="language-text">&lt;탐색 키, Primary Key&gt;</code></pre>
<p>후자의 경우 Secondary Index에서 Primary Key를 얻은 뒤 실제 데이터가 저장된 Clustered Index를 다시 탐색해야 할 수 있다.</p>
<hr />
<h2 id="105-btree와-dense·sparse의-관계">10.5 B+Tree와 Dense·Sparse의 관계</h2>
<p>B+Tree 전체를 무조건 Dense Index 또는 Sparse Index라고 정의하는 것은 정확하지 않다.</p>
<pre><code class="language-text">B+Tree 내부 노드
→ 하위 페이지의 대표 키 저장
→ Sparse Index와 비슷하게 동작

B+Tree 리프 노드
→ 실제 검색 엔트리 저장
→ 일반적으로 인덱스 키에 대해 Dense한 구조</code></pre>
<p>다만 전통적인 파일 구조에서는 데이터 블록의 대표 키만 리프에 저장하는 Sparse Primary Index도 구성할 수 있다.</p>
<p>따라서 B+Tree는 다음과 같이 이해하는 것이 좋다.</p>
<blockquote>
<p>B+Tree는 정렬된 다단계 인덱스 구조다. 내부 노드는 하위 페이지의 탐색 방향을 제공하고, 리프 노드는 실제 검색 엔트리를 저장한다. 리프 노드의 구체적인 저장 내용은 DBMS와 인덱스 구성 방식에 따라 달라진다.</p>
</blockquote>
<hr />
<h1 id="11-btree의-삽입과-삭제">11. B+Tree의 삽입과 삭제</h1>
<p>다음 내용은 일반적인 B+Tree 자료구조의 갱신 원리다.</p>
<p>실제 페이지 삭제, 재사용, 병합 방식은 DBMS 구현과 MVCC 정책에 따라 다를 수 있다.</p>
<hr />
<h2 id="111-삽입과-노드-분할">11.1 삽입과 노드 분할</h2>
<p>리프 노드에 새로운 키를 추가할 공간이 있다면 정렬 순서에 맞게 키를 삽입한다.</p>
<p>노드가 가득 찬 경우에는 노드 분할이 발생할 수 있다.</p>
<pre><code class="language-text">Node Full
→ 노드를 두 페이지로 분할
→ 부모 노드에 새로운 경계 키 추가</code></pre>
<p>부모 노드도 가득 차 있다면 분할이 상위 노드까지 이어질 수 있다.</p>
<pre><code class="language-text">리프 노드 분할
→ 부모 내부 노드 수정
→ 부모 노드도 가득 차면 추가 분할
→ 필요하면 새로운 Root 생성</code></pre>
<hr />
<h2 id="112-삭제와-재분배">11.2 삭제와 재분배</h2>
<p>일반적인 B+Tree 알고리즘에서는 삭제로 인해 노드의 사용량이 지나치게 낮아지면 다음 작업이 발생할 수 있다.</p>
<pre><code class="language-text">인접 노드와 키 재분배
또는
인접 노드와 병합</code></pre>
<p>다만 PostgreSQL은 MVCC를 사용하므로 DELETE 시 인덱스 엔트리를 즉시 물리적으로 제거하지 않을 수 있다.</p>
<p>더 이상 필요하지 않은 인덱스 엔트리는 VACUUM과 인덱스 내부 정리 과정을 통해 처리된다.</p>
<hr />
<h1 id="12-postgresql의-주요-인덱스-종류">12. PostgreSQL의 주요 인덱스 종류</h1>
<p>PostgreSQL은 데이터의 형태와 검색 연산에 따라 여러 인덱스 접근 방식을 제공한다.</p>
<pre><code class="language-text">일반적인 일치·범위·정렬 검색 → B-Tree
정확한 동등 비교              → Hash
배열·JSONB·전문검색           → GIN
공간·범위·거리·겹침 검색       → GiST
분할 가능한 검색 공간          → SP-GiST
시간순 초대형 데이터           → BRIN</code></pre>
<hr />
<h1 id="13-b-tree-인덱스">13. B-Tree 인덱스</h1>
<p>B-Tree는 PostgreSQL의 기본 인덱스 방식이다.</p>
<pre><code class="language-sql">CREATE INDEX idx_employees_salary
ON employees(salary);</code></pre>
<p>다음 구문과 같은 의미다.</p>
<pre><code class="language-sql">CREATE INDEX idx_employees_salary
ON employees USING BTREE(salary);</code></pre>
<hr />
<h2 id="131-적합한-검색">13.1 적합한 검색</h2>
<p>B-Tree는 다음 연산에 적합하다.</p>
<pre><code class="language-sql">WHERE employee_id = 100</code></pre>
<pre><code class="language-sql">WHERE salary &gt; 5000</code></pre>
<pre><code class="language-sql">WHERE salary BETWEEN 5000 AND 10000</code></pre>
<pre><code class="language-sql">ORDER BY hire_date</code></pre>
<p>지원하기 좋은 연산은 다음과 같다.</p>
<pre><code class="language-text">동등 비교 =
대소 비교 &lt;, &gt;, &lt;=, &gt;=
범위 검색 BETWEEN
정렬 ORDER BY
최솟값과 최댓값
접두사 검색</code></pre>
<p>탐색 비용은 일반적으로 다음과 같이 표현한다.</p>
<pre><code class="language-text">O(log N)</code></pre>
<p>다만 데이터베이스 성능에서는 단순한 시간복잡도보다 실제로 몇 개의 페이지를 읽는지가 더 중요하다.</p>
<hr />
<h2 id="132-like-검색">13.2 LIKE 검색</h2>
<p>다음 조건은 문자열의 시작 부분이 정해져 있다.</p>
<pre><code class="language-sql">WHERE name LIKE 'Kim%'</code></pre>
<p>따라서 B-Tree에서 탐색 시작 범위를 만들 수 있다.</p>
<p>반면 다음 조건은 문자열의 앞부분을 알 수 없다.</p>
<pre><code class="language-sql">WHERE name LIKE '%Kim'</code></pre>
<pre><code class="language-sql">WHERE name LIKE '%Kim%'</code></pre>
<p>정렬된 인덱스에서 검색 시작점을 정하기 어렵기 때문에 일반적인 B-Tree 인덱스로 효율적으로 처리하기 어렵다.</p>
<p>PostgreSQL에서는 Collation 설정에 따라 접두사 검색에서도 일반 B-Tree 인덱스가 기대한 방식으로 사용되지 않을 수 있다.</p>
<p>필요하면 적합한 Operator Class를 적용할 수 있다.</p>
<pre><code class="language-sql">CREATE INDEX idx_users_name_pattern
ON users(name text_pattern_ops);</code></pre>
<hr />
<h1 id="14-hash-인덱스">14. Hash 인덱스</h1>
<p>Hash Index는 탐색 키를 해시 함수에 넣어 버킷 위치를 계산한다.</p>
<pre><code class="language-text">탐색 키
   ↓
해시 함수
   ↓
버킷 번호</code></pre>
<p>PostgreSQL에서는 다음과 같이 생성한다.</p>
<pre><code class="language-sql">CREATE INDEX idx_users_email_hash
ON users USING HASH(email);</code></pre>
<hr />
<h2 id="141-적합한-검색">14.1 적합한 검색</h2>
<p>정확한 동등 비교에 특화되어 있다.</p>
<pre><code class="language-sql">WHERE email = 'kim@example.com'</code></pre>
<pre><code class="language-sql">WHERE session_token = 'abc123'</code></pre>
<hr />
<h2 id="142-범위-검색이-어려운-이유">14.2 범위 검색이 어려운 이유</h2>
<p>해시값은 원래 값의 순서를 유지하지 않는다.</p>
<p>따라서 다음 조건에는 적합하지 않다.</p>
<pre><code class="language-sql">WHERE salary &gt; 5000</code></pre>
<pre><code class="language-sql">WHERE age BETWEEN 20 AND 30</code></pre>
<pre><code class="language-sql">ORDER BY salary</code></pre>
<p>B-Tree 역시 동등 비교를 충분히 효율적으로 처리하면서 범위 검색과 정렬까지 지원한다.</p>
<p>따라서 일반적으로는 다음 순서로 판단한다.</p>
<pre><code class="language-text">우선 B-Tree 검토
→ 검색이 동등 비교에만 집중됨
→ 실제 실행계획과 성능 측정에서 Hash의 이점이 확인됨
→ Hash Index 검토</code></pre>
<hr />
<h1 id="15-gin-인덱스">15. GIN 인덱스</h1>
<p>GIN은 Generalized Inverted Index의 약자로 일반화된 역인덱스다.</p>
<hr />
<h2 id="151-역인덱스란">15.1 역인덱스란?</h2>
<p>일반적인 데이터 구조는 각 문서가 어떤 원소를 포함하는지를 저장한다.</p>
<pre><code class="language-text">문서 1 → PostgreSQL, Index
문서 2 → JSON, Database
문서 3 → PostgreSQL, JSON</code></pre>
<p>역인덱스는 반대로 각 원소가 어느 문서에 포함되어 있는지를 저장한다.</p>
<pre><code class="language-text">PostgreSQL → 문서 1, 문서 3
Index      → 문서 1
JSON       → 문서 2, 문서 3
Database   → 문서 2</code></pre>
<p>하나의 컬럼 안에 여러 검색 대상이 들어 있을 때 효과적이다.</p>
<hr />
<h2 id="152-배열-검색">15.2 배열 검색</h2>
<pre><code class="language-sql">CREATE INDEX idx_posts_tags
ON posts USING GIN(tags);</code></pre>
<pre><code class="language-sql">SELECT *
FROM posts
WHERE tags @&gt; ARRAY['postgresql'];</code></pre>
<hr />
<h2 id="153-jsonb-검색">15.3 JSONB 검색</h2>
<pre><code class="language-sql">CREATE INDEX idx_products_attributes
ON products USING GIN(attributes);</code></pre>
<pre><code class="language-sql">SELECT *
FROM products
WHERE attributes @&gt; '{&quot;color&quot;: &quot;black&quot;}';</code></pre>
<hr />
<h2 id="154-전문검색">15.4 전문검색</h2>
<pre><code class="language-sql">CREATE INDEX idx_articles_content
ON articles
USING GIN(to_tsvector('english', content));</code></pre>
<pre><code class="language-sql">SELECT *
FROM articles
WHERE to_tsvector('english', content)
      @@ plainto_tsquery('english', 'database index');</code></pre>
<hr />
<h2 id="155-특징">15.5 특징</h2>
<p>한 행에 여러 원소가 들어 있으면 하나의 행이 여러 인덱스 엔트리와 연결될 수 있다.</p>
<pre><code class="language-text">한 행의 태그가 10개
→ 여러 태그가 인덱스에 등록됨</code></pre>
<p>따라서 원소 포함 여부 검색에는 강하지만 다음 비용이 증가할 수 있다.</p>
<pre><code class="language-text">인덱스 크기
인덱스 생성 시간
INSERT 비용
UPDATE 비용</code></pre>
<hr />
<h1 id="16-gist-인덱스">16. GiST 인덱스</h1>
<p>GiST는 Generalized Search Tree의 약자다.</p>
<p>GiST는 특정한 하나의 자료형을 위한 고정된 구조라기보다, 여러 검색 방식을 구현할 수 있도록 만든 확장 가능한 검색 프레임워크다.</p>
<hr />
<h2 id="161-대표-용도">16.1 대표 용도</h2>
<pre><code class="language-text">지리·공간 검색
범위 타입
도형의 겹침과 포함 관계
거리 검색
최근접 이웃 검색
일부 유사도 검색</code></pre>
<hr />
<h2 id="162-기간-겹침-검색">16.2 기간 겹침 검색</h2>
<p><code>reservation_period</code>가 <code>tsrange</code> 자료형이라고 하자.</p>
<pre><code class="language-sql">CREATE TABLE reservations (
    reservation_id bigint PRIMARY KEY,
    reservation_period tsrange
);</code></pre>
<p>GiST 인덱스를 생성한다.</p>
<pre><code class="language-sql">CREATE INDEX idx_reservations_period
ON reservations USING GIST(reservation_period);</code></pre>
<p>기간이 겹치는 예약을 찾을 수 있다.</p>
<pre><code class="language-sql">SELECT *
FROM reservations
WHERE reservation_period &amp;&amp;
      tsrange(
          TIMESTAMP '2026-07-01',
          TIMESTAMP '2026-07-05'
      );</code></pre>
<p><code>&amp;&amp;</code> 연산자는 두 범위가 서로 겹치는지를 검사한다.</p>
<hr />
<h2 id="163-공간-검색">16.3 공간 검색</h2>
<pre><code class="language-sql">CREATE INDEX idx_stores_location
ON stores USING GIST(location);</code></pre>
<p>공간 데이터와 적절한 연산자를 이용하면 다음과 같은 검색을 지원할 수 있다.</p>
<pre><code class="language-text">특정 영역 안에 있는 위치
두 도형이 겹치는지
현재 위치에서 가까운 장소</code></pre>
<hr />

<hr />
<h1 id="17-sp-gist-인덱스">17. SP-GiST 인덱스</h1>
<p>SP-GiST는 Space-Partitioned GiST의 약자다.</p>
<p>검색 공간을 서로 겹치지 않는 영역으로 분할하기 좋은 데이터에 적합하다.</p>
<p>대표적으로 다음과 같은 구조를 구현하는 데 사용할 수 있다.</p>
<pre><code class="language-text">Trie
Radix Tree
Quad Tree
K-d Tree와 유사한 공간 분할</code></pre>
<p>활용 가능한 데이터의 예시는 다음과 같다.</p>
<pre><code class="language-text">IP 주소
접두사 검색
점 데이터
공간적으로 분리 가능한 데이터</code></pre>
<p>GiST가 겹칠 수 있는 영역을 포함하는 범용 검색 트리라면, SP-GiST는 검색 공간을 명확한 하위 영역으로 나누는 구조에 적합하다.</p>
<p>일반적인 숫자·문자열 조회에서는 B-Tree가 우선이지만, 데이터의 구조 자체가 공간 분할이나 접두사 분할에 적합하다면 SP-GiST를 검토할 수 있다.</p>
<hr />
<h1 id="18-brin-인덱스">18. BRIN 인덱스</h1>
<p>BRIN은 Block Range Index의 약자다.</p>
<p>행 하나하나의 정확한 위치를 저장하는 대신 여러 데이터 블록을 하나의 범위로 묶어 요약 정보를 저장한다.</p>
<p>대표적인 요약 정보는 최소값과 최대값이다.</p>
<pre><code class="language-text">Block Range 1: 2026-01-01 ~ 2026-01-03
Block Range 2: 2026-01-04 ~ 2026-01-06
Block Range 3: 2026-01-07 ~ 2026-01-09
Block Range 4: 2026-01-10 ~ 2026-01-12</code></pre>
<p>다음 조건이 들어오면:</p>
<pre><code class="language-sql">WHERE created_at &gt;= TIMESTAMP '2026-01-10'</code></pre>
<p>BRIN은 범위의 요약 정보를 확인해 불필요한 블록 범위를 제외한다.</p>
<pre><code class="language-text">Range 1 제외
Range 2 제외
Range 3 제외
Range 4 검사</code></pre>
<hr />
<h2 id="181-postgresql-예시">18.1 PostgreSQL 예시</h2>
<pre><code class="language-sql">CREATE INDEX idx_logs_created_at_brin
ON logs USING BRIN(created_at);</code></pre>
<hr />
<h2 id="182-적합한-데이터">18.2 적합한 데이터</h2>
<pre><code class="language-text">로그
센서 데이터
시계열 데이터
계속 뒤에 추가되는 데이터
수억 건 이상의 초대형 테이블
컬럼 값과 물리적 저장 순서가 유사한 데이터</code></pre>
<hr />
<h2 id="183-장점">18.3 장점</h2>
<pre><code class="language-text">인덱스 크기가 매우 작음
생성 비용이 낮음
쓰기 부담이 비교적 적음
초대형 테이블의 범위 검색에 효과적</code></pre>
<hr />
<h2 id="184-단점">18.4 단점</h2>
<p>BRIN은 정확한 레코드 위치를 직접 알려주는 것이 아니다.</p>
<p>조건을 만족할 가능성이 있는 후보 블록 범위를 알려준다.</p>
<pre><code class="language-text">BRIN으로 후보 블록 선택
→ 후보 블록의 실제 행을 다시 검사</code></pre>
<p>데이터의 물리적 순서와 컬럼 값의 상관관계가 낮으면 효과가 떨어진다.</p>
<pre><code class="language-text">하나의 블록에 과거 데이터와 최근 데이터가 섞임
→ 블록별 최소·최대 범위가 넓어짐
→ 많은 블록이 후보가 됨
→ 검색 효율 감소</code></pre>
<p>BRIN은 전통적인 인덱스 이론에서 데이터 블록의 대표 정보만 저장하는 Sparse Index와 비슷한 발상을 가진다.</p>
<hr />
<h1 id="19-postgresql의-bitmap-scan">19. PostgreSQL의 Bitmap Scan</h1>
<p>Bitmap을 설명할 때는 다음 두 개념을 구분해야 한다.</p>
<pre><code class="language-text">영구 Bitmap Index
PostgreSQL의 Bitmap Scan</code></pre>
<hr />
<h2 id="191-영구-bitmap-index">19.1 영구 Bitmap Index</h2>
<p>Oracle 등 일부 DBMS는 Bitmap Index를 영구적인 인덱스 구조로 제공한다.</p>
<p>특정 조건에 해당하는 행을 비트 배열로 표현한다.</p>
<pre><code class="language-text">행 번호:  1 2 3 4 5 6
성별 M:   1 0 1 0 1 0
등급 VIP: 0 1 1 0 0 1</code></pre>
<p>두 조건은 비트 AND 연산으로 결합할 수 있다.</p>
<pre><code class="language-text">M   : 1 0 1 0 1 0
VIP : 0 1 1 0 0 1
AND : 0 0 1 0 0 0</code></pre>
<p>저카디널리티 컬럼 여러 개를 조합하는 분석 질의에 적합하다.</p>
<pre><code class="language-sql">WHERE gender = 'M'
  AND membership_grade = 'VIP'
  AND active = true</code></pre>
<p>다만 데이터 변경이 빈번한 OLTP 환경에서는 유지 비용과 동시성 문제로 부적합할 수 있다.</p>
<hr />
<h2 id="192-postgresql의-bitmap-scan">19.2 PostgreSQL의 Bitmap Scan</h2>
<p>PostgreSQL에는 다음 문법이 존재하지 않는다.</p>
<pre><code class="language-sql">CREATE BITMAP INDEX ...</code></pre>
<p>대신 쿼리 실행 과정에서 기존 인덱스의 검색 결과를 Bitmap으로 만든다.</p>
<pre><code class="language-text">Bitmap Index Scan
→ BitmapAnd 또는 BitmapOr
→ Bitmap Heap Scan</code></pre>
<p>예를 들어 두 개의 B-Tree 인덱스 결과를 결합할 수 있다.</p>
<pre><code class="language-text">idx_users_region 결과
        +
idx_users_grade 결과
        ↓
BitmapAnd
        ↓
Bitmap Heap Scan</code></pre>
<hr />
<h2 id="193-bitmap-scan이-유리한-상황">19.3 Bitmap Scan이 유리한 상황</h2>
<p>일반적으로 다음과 같은 중간 영역에서 유리할 수 있다.</p>
<pre><code class="language-text">Index Scan으로 행마다 Heap을 방문하기에는 결과가 많음
하지만
Sequential Scan으로 전체 테이블을 읽기에는 결과가 적음</code></pre>
<p>Bitmap은 여러 TID를 페이지 단위로 정리한다.</p>
<pre><code class="language-text">인덱스 순서의 TID
→ Heap 페이지 기준으로 정리
→ 같은 페이지의 행을 묶어서 읽음</code></pre>
<p>이를 통해 무작위 페이지 접근을 줄일 수 있다.</p>
<p>실행계획은 다음과 같은 형태로 나타난다.</p>
<pre><code class="language-text">Bitmap Heap Scan on employees
  Recheck Cond: (department_id = 10)
  → Bitmap Index Scan on idx_employees_department
       Index Cond: (department_id = 10)</code></pre>
<p>Bitmap이 메모리 제약으로 페이지 단위의 대략적인 정보만 저장한 경우 실제 행을 다시 검사해야 한다.</p>
<p>이때 <code>Recheck Cond</code>가 표시될 수 있다.</p>
<hr />
<h1 id="20-clustered-index와-postgresql의-cluster">20. Clustered Index와 PostgreSQL의 CLUSTER</h1>
<p>Clustered 구조는 인덱스 키의 순서에 맞게 데이터 자체를 물리적으로 배치하는 구조다.</p>
<hr />
<h2 id="201-non-clustered-구조">20.1 Non-clustered 구조</h2>
<pre><code class="language-text">인덱스

10 → Data Block 30
20 → Data Block 4
30 → Data Block 91</code></pre>
<p>인덱스는 정렬되어 있지만 실제 데이터는 여러 위치에 흩어져 있다.</p>
<hr />
<h2 id="202-clustered-구조">20.2 Clustered 구조</h2>
<pre><code class="language-text">실제 데이터 저장 순서

10번 데이터
20번 데이터
30번 데이터
40번 데이터</code></pre>
<p>관련 데이터가 가까운 페이지에 모여 있으므로 범위 조회에 유리하다.</p>
<pre><code class="language-sql">WHERE employee_id BETWEEN 1000 AND 2000</code></pre>
<p>한 테이블을 여러 기준으로 동시에 물리 정렬할 수는 없으므로 일반적으로 하나의 Clustered 구조만 가질 수 있다.</p>
<hr />
<h2 id="203-sql-server">20.3 SQL Server</h2>
<p>SQL Server는 Clustered Index를 명시적으로 지원한다.</p>
<pre><code class="language-sql">CREATE CLUSTERED INDEX idx_orders_created_at
ON orders(created_at);</code></pre>
<hr />
<h2 id="204-mysql-innodb">20.4 MySQL InnoDB</h2>
<p>InnoDB는 기본키를 중심으로 테이블 데이터를 저장한다.</p>
<pre><code class="language-text">Primary Key
= Clustered Index</code></pre>
<p>보조 인덱스의 리프에는 실제 행 주소 대신 Primary Key가 저장된다.</p>
<pre><code class="language-text">email 보조 인덱스
email → Primary Key
Primary Key → 실제 데이터</code></pre>
<p>따라서 Secondary Index로 검색한 뒤 Primary Key의 Clustered Index를 다시 탐색할 수 있다.</p>
<hr />
<h2 id="205-postgresql">20.5 PostgreSQL</h2>
<p>PostgreSQL은 데이터가 변경될 때마다 특정 인덱스 순서로 물리적 배치를 자동 유지하는 Clustered Index를 제공하지 않는다.</p>
<p>다만 <code>CLUSTER</code> 명령을 이용해 특정 인덱스 순서로 테이블을 한 번 재배치할 수 있다.</p>
<pre><code class="language-sql">CLUSTER employees
USING idx_employees_hire_date;</code></pre>
<p>실행 직후에는 인덱스 순서와 데이터의 물리적 배치가 비슷해진다.</p>
<p>하지만 이후 INSERT와 UPDATE가 발생하면 순서는 다시 흐트러질 수 있다.</p>
<pre><code class="language-text">CLUSTER 실행
→ 특정 시점에 물리적 재정렬

이후 데이터 변경
→ 물리적 정렬이 점차 흐트러짐</code></pre>
<p>따라서 PostgreSQL의 <code>CLUSTER</code>는 SQL Server의 Clustered Index와 같은 자동 유지 구조가 아니다.</p>
<hr />
<h1 id="21-선택성과-인덱스-효율">21. 선택성과 인덱스 효율</h1>
<p>인덱스가 효율적인지는 조건이 전체 데이터 중 얼마나 적은 행을 선택하는지에 크게 영향을 받는다.</p>
<p>조건 만족 비율은 다음과 같이 표현할 수 있다.</p>
<pre><code class="language-text">조건 만족 비율
= 조건을 만족하는 행 수 / 전체 행 수</code></pre>
<p>예를 들어 전체 100만 건 중 한 건을 조회한다면:</p>
<pre><code class="language-text">1 / 1,000,000</code></pre>
<p>결과 비율이 매우 낮다.</p>
<p>이러한 조건을 흔히 <strong>선택성이 높은 조건</strong>, 또는 <code>highly selective predicate</code>라고 표현한다.</p>
<pre><code class="language-text">선택성이 높은 조건
→ 결과 행이 적음
→ 인덱스로 필요한 위치만 찾는 것이 유리할 가능성이 높음</code></pre>
<p>반면 전체 데이터의 절반을 조회한다면:</p>
<pre><code class="language-text">500,000 / 1,000,000</code></pre>
<p>많은 행을 읽어야 한다.</p>
<pre><code class="language-text">선택성이 낮은 조건
→ 결과 행이 많음
→ 일반 인덱스보다 Sequential Scan이 유리할 수 있음</code></pre>
<hr />
<h2 id="211-선택성이-높은-예">21.1 선택성이 높은 예</h2>
<pre><code class="language-sql">WHERE employee_id = 100</code></pre>
<p>Primary Key나 고유한 이메일처럼 값이 거의 중복되지 않는 컬럼은 일반적으로 단건 조회의 선택성이 높다.</p>
<hr />
<h2 id="212-선택성이-낮은-예">21.2 선택성이 낮은 예</h2>
<pre><code class="language-sql">WHERE gender = 'M'</code></pre>
<p>성별 값이 두 종류이고 전체 데이터의 절반 정도가 <code>M</code>이라면 많은 행을 읽어야 한다.</p>
<p>이 경우 B-Tree 인덱스가 있어도 Sequential Scan이 선택될 수 있다.</p>
<hr />
<h1 id="22-secondary-index-전체-탐색이-비효율적인-이유">22. Secondary Index 전체 탐색이 비효율적인 이유</h1>
<p>Secondary Index의 순서와 실제 데이터의 물리적 저장 순서는 일치하지 않는다.</p>
<pre><code class="language-text">인덱스 순서

개발팀 → Record A
개발팀 → Record B
개발팀 → Record C</code></pre>
<p>실제 위치는 흩어져 있을 수 있다.</p>
<pre><code class="language-text">Record A → Block 2
Record B → Block 91
Record C → Block 17</code></pre>
<p>결과가 한두 건이라면 몇 개의 페이지에만 접근하면 된다.</p>
<p>그러나 조회 결과가 많다면 많은 페이지를 무작위로 방문해야 한다.</p>
<pre><code class="language-text">Block 2
→ Block 91
→ Block 17
→ Block 42
→ ...</code></pre>
<p>이 경우 테이블을 처음부터 끝까지 순차적으로 읽는 편이 효율적일 수 있다.</p>
<p>따라서 PostgreSQL 옵티마이저는 인덱스가 존재하더라도 다음 요소를 비교한다.</p>
<pre><code class="language-text">인덱스 탐색 비용
예상 결과 행 수
Heap 페이지 접근 수
무작위 I/O 비용
Sequential Scan 비용
테이블 크기
데이터 분포</code></pre>
<blockquote>
<p>인덱스가 존재한다는 사실과 실제 실행계획에서 인덱스를 사용한다는 것은 서로 다른 문제다.</p>
</blockquote>
<hr />
<h1 id="23-복합-인덱스">23. 복합 인덱스</h1>
<p>복합 인덱스는 두 개 이상의 컬럼으로 구성된 인덱스다.</p>
<pre><code class="language-sql">CREATE INDEX idx_orders_customer_status
ON orders(customer_id, status);</code></pre>
<p>인덱스는 다음 순서로 정렬된다.</p>
<pre><code class="language-text">customer_id 우선 정렬
→ customer_id가 같으면 status 정렬</code></pre>
<p>예를 들어 다음과 같은 구조다.</p>
<pre><code class="language-text">customer_id | status
100         | CANCELLED
100         | PAID
100         | READY
200         | PAID
200         | READY</code></pre>
<hr />
<h2 id="231-활용하기-좋은-조건">23.1 활용하기 좋은 조건</h2>
<pre><code class="language-sql">WHERE customer_id = 100</code></pre>
<pre><code class="language-sql">WHERE customer_id = 100
  AND status = 'PAID'</code></pre>
<p>첫 번째 컬럼을 기준으로 탐색 범위를 좁힐 수 있다.</p>
<hr />
<h2 id="232-선두-컬럼이-없는-조건">23.2 선두 컬럼이 없는 조건</h2>
<pre><code class="language-sql">WHERE status = 'PAID'</code></pre>
<p><code>status</code>만으로는 인덱스의 어느 부분부터 읽어야 하는지 빠르게 결정하기 어렵다.</p>
<pre><code class="language-text">customer_id = 100 구간의 PAID
customer_id = 200 구간의 PAID
customer_id = 300 구간의 PAID
...</code></pre>
<p>따라서 인덱스를 전혀 사용할 수 없다고 단정할 수는 없지만, 원하는 범위를 효율적으로 좁히기 어렵다.</p>
<p>이를 일반적으로 Leftmost Prefix와 관련된 특성이라고 설명한다.</p>
<pre><code class="language-text">INDEX(a, b, c)

효율적으로 활용하기 좋은 조건:
a
a, b
a, b, c

제한적일 수 있는 조건:
b
c
b, c</code></pre>
<hr />
<h2 id="233-복합-인덱스-컬럼-순서">23.3 복합 인덱스 컬럼 순서</h2>
<p>복합 인덱스 컬럼 순서는 단순히 카디널리티가 높은 컬럼부터 배치하는 방식으로 결정하면 안 된다.</p>
<p>다음 요소를 함께 고려해야 한다.</p>
<pre><code class="language-text">실제 WHERE 조건
동등 비교 조건
범위 조건
JOIN 조건
ORDER BY
자주 단독으로 조회되는 컬럼
쿼리에서 함께 사용되는 컬럼
예상 결과 행 수</code></pre>
<p>일반적인 출발점은 다음과 같다.</p>
<pre><code class="language-text">동등 비교에 사용되는 컬럼
→ 범위 비교에 사용되는 컬럼
→ 정렬이나 추가 필터에 사용되는 컬럼</code></pre>
<p>예를 들어 다음 쿼리가 자주 실행된다고 하자.</p>
<pre><code class="language-sql">SELECT *
FROM orders
WHERE customer_id = 100
  AND ordered_at &gt;= TIMESTAMP '2026-07-01'
ORDER BY ordered_at DESC;</code></pre>
<p>다음 인덱스를 검토할 수 있다.</p>
<pre><code class="language-sql">CREATE INDEX idx_orders_customer_date
ON orders(customer_id, ordered_at DESC);</code></pre>
<hr />
<h1 id="24-covering-index와-include">24. Covering Index와 INCLUDE</h1>
<p>쿼리에 필요한 모든 컬럼이 인덱스에 포함되어 있으면 테이블의 실제 데이터 페이지 접근을 줄일 수 있다.</p>
<pre><code class="language-sql">CREATE INDEX idx_employees_department_name
ON employees(department_id, name);</code></pre>
<p>다음 쿼리는 필요한 컬럼이 모두 인덱스에 들어 있다.</p>
<pre><code class="language-sql">SELECT department_id, name
FROM employees
WHERE department_id = 10;</code></pre>
<p>이처럼 특정 쿼리에 필요한 컬럼을 모두 포함하는 인덱스를 Covering Index라고 부를 수 있다.</p>
<hr />
<h2 id="241-postgresql의-include">24.1 PostgreSQL의 INCLUDE</h2>
<p>검색과 정렬에 사용하지는 않지만 결과 반환을 위해 필요한 컬럼은 <code>INCLUDE</code>에 추가할 수 있다.</p>
<pre><code class="language-sql">CREATE INDEX idx_employees_department_cover
ON employees(department_id)
INCLUDE (name, email);</code></pre>
<p>각 컬럼의 역할은 다음과 같다.</p>
<pre><code class="language-text">department_id
→ Key Column
→ 검색과 정렬에 사용 가능

name, email
→ Included Column
→ 리프 엔트리에 포함
→ 검색 범위를 좁히는 키로는 사용하지 않음</code></pre>
<p>모든 컬럼을 복합 인덱스의 Key Column으로 구성하는 것과 <code>INCLUDE</code>를 사용하는 것은 목적이 다르다.</p>
<hr />
<h2 id="242-index-only-scan">24.2 Index Only Scan</h2>
<p>필요한 데이터가 인덱스에 모두 들어 있다면 PostgreSQL은 <code>Index Only Scan</code>을 선택할 수 있다.</p>
<pre><code class="language-text">Index Only Scan using idx_employees_department_cover</code></pre>
<p>하지만 이름이 <code>Index Only Scan</code>이라고 해서 항상 Heap에 전혀 접근하지 않는 것은 아니다.</p>
<p>PostgreSQL은 MVCC를 사용하므로 해당 행 버전이 현재 트랜잭션에서 보이는지 확인해야 한다.</p>
<hr />
<h2 id="243-visibility-map">24.3 Visibility Map</h2>
<p>PostgreSQL은 각 Heap 페이지의 모든 행이 모든 트랜잭션에서 볼 수 있는 상태인지를 Visibility Map에 기록한다.</p>
<p>페이지가 <code>all-visible</code> 상태라면 인덱스만 확인하고 결과를 반환할 수 있다.</p>
<pre><code class="language-text">필요한 컬럼이 인덱스에 모두 존재
+
Heap 페이지가 all-visible
→ Heap 접근 없이 결과 반환 가능</code></pre>
<p>반대로 <code>all-visible</code> 상태가 아니라면 Heap을 확인해야 한다.</p>
<p>실행계획에서는 다음 항목을 확인한다.</p>
<pre><code class="language-text">Heap Fetches: 0</code></pre>
<p><code>Heap Fetches</code>가 0에 가까울수록 실제로 인덱스만으로 처리된 것이다.</p>
<p>VACUUM이 적절히 수행되면 Visibility Map이 관리되어 Index Only Scan의 효율이 높아질 수 있다.</p>
<hr />
<h1 id="25-부분-인덱스">25. 부분 인덱스</h1>
<p>부분 인덱스는 테이블의 모든 행을 인덱싱하지 않고 특정 조건을 만족하는 일부 행만 인덱싱한다.</p>
<pre><code class="language-sql">CREATE INDEX idx_orders_pending_created_at
ON orders(created_at)
WHERE status = 'PENDING';</code></pre>
<p>전체 주문 중 <code>PENDING</code> 상태만 인덱스에 포함된다.</p>
<pre><code class="language-text">전체 orders 테이블
├── PENDING   → 인덱스에 포함
├── PAID      → 제외
├── CANCELLED → 제외
└── COMPLETED → 제외</code></pre>
<hr />
<h2 id="251-장점">25.1 장점</h2>
<pre><code class="language-text">인덱스 크기 감소
인덱스 생성 비용 감소
쓰기 유지 비용 감소
자주 조회하는 일부 데이터에 집중 가능</code></pre>
<hr />
<h2 id="252-활용-조건">25.2 활용 조건</h2>
<p>다음과 같이 부분 인덱스 조건을 만족하는 쿼리에서 사용할 수 있다.</p>
<pre><code class="language-sql">SELECT *
FROM orders
WHERE status = 'PENDING'
  AND created_at &lt; NOW() - INTERVAL '1 hour';</code></pre>
<p>부분 인덱스를 사용하려면 쿼리 조건이 인덱스의 <code>WHERE</code> 조건을 논리적으로 만족해야 한다.</p>
<p>예를 들어 다음 인덱스는 완료된 교육 이력을 탐색하는 데 사용할 수 있다.</p>
<pre><code class="language-sql">CREATE INDEX idx_training_completed_employee
ON employee_training(employee_id)
WHERE completion_status = 'COMPLETED'
  AND employee_id IS NOT NULL;</code></pre>
<hr />
<h1 id="26-표현식-인덱스">26. 표현식 인덱스</h1>
<p>컬럼에 함수를 적용한 값을 자주 검색한다면 표현식 인덱스를 만들 수 있다.</p>
<p>다음 쿼리를 자주 실행한다고 하자.</p>
<pre><code class="language-sql">SELECT *
FROM users
WHERE LOWER(email) = 'kim@example.com';</code></pre>
<p>일반적인 <code>email</code> 인덱스는 원본 문자열을 저장한다.</p>
<pre><code class="language-sql">CREATE INDEX idx_users_email
ON users(email);</code></pre>
<p>하지만 쿼리는 <code>LOWER(email)</code>이라는 표현식을 사용한다.</p>
<p>따라서 다음과 같이 표현식 인덱스를 구성할 수 있다.</p>
<pre><code class="language-sql">CREATE INDEX idx_users_lower_email
ON users(LOWER(email));</code></pre>
<p>이후 다음 조건에서 인덱스 활용을 기대할 수 있다.</p>
<pre><code class="language-sql">WHERE LOWER(email) = 'kim@example.com'</code></pre>
<p>표현식 인덱스도 데이터 변경 시 표현식 값을 계산하고 인덱스를 유지해야 하므로 쓰기 비용이 발생한다.</p>
<hr />
<h1 id="27-sargability">27. SARGability</h1>
<p>SARGable은 Search Argument Able의 의미로, 인덱스가 검색 시작점과 종료점을 만들 수 있는 조건을 뜻한다.</p>
<hr />
<h2 id="271-비-sargable-조건">27.1 비-SARGable 조건</h2>
<pre><code class="language-sql">WHERE EXTRACT(YEAR FROM hire_date) = 2025;</code></pre>
<p>모든 <code>hire_date</code> 값에 함수를 적용한 뒤 결과를 검사해야 할 수 있다.</p>
<p>일반적인 <code>hire_date</code> B-Tree 인덱스의 정렬 순서를 직접 활용하기 어렵다.</p>
<hr />
<h2 id="272-sargable-조건">27.2 SARGable 조건</h2>
<pre><code class="language-sql">WHERE hire_date &gt;= DATE '2025-01-01'
  AND hire_date &lt;  DATE '2026-01-01';</code></pre>
<p>검색할 날짜 범위의 시작점과 종료점을 만들 수 있다.</p>
<pre><code class="language-text">2025-01-01부터 탐색 시작
→ 2026-01-01 이전까지 순서대로 검색</code></pre>
<p>표현식 인덱스를 만드는 방법도 있지만, 단순한 범위 조건으로 바꿀 수 있다면 원본 컬럼 인덱스를 더 다양한 쿼리에 활용할 수 있다.</p>
<hr />
<h1 id="28-인덱스가-사용되기-어려운-경우">28. 인덱스가 사용되기 어려운 경우</h1>
<p>인덱스가 존재해도 PostgreSQL이 이를 사용하지 않을 수 있다.</p>
<hr />
<h2 id="281-조회-대상이-너무-많은-경우">28.1 조회 대상이 너무 많은 경우</h2>
<pre><code class="language-sql">WHERE active = true</code></pre>
<p>전체 데이터의 대부분이 <code>true</code>라면 인덱스를 따라 수많은 Heap 페이지를 방문하는 것보다 테이블 전체를 순차적으로 읽는 것이 빠를 수 있다.</p>
<hr />
<h2 id="282-인덱스-컬럼에-함수-적용">28.2 인덱스 컬럼에 함수 적용</h2>
<pre><code class="language-sql">WHERE LOWER(name) = 'kim'</code></pre>
<p>일반적인 <code>name</code> 인덱스만으로는 활용하기 어려울 수 있다.</p>
<p>표현식 인덱스를 검토할 수 있다.</p>
<pre><code class="language-sql">CREATE INDEX idx_users_lower_name
ON users(LOWER(name));</code></pre>
<hr />
<h2 id="283-앞쪽-와일드카드">28.3 앞쪽 와일드카드</h2>
<pre><code class="language-sql">WHERE name LIKE '%Kim%'</code></pre>
<p>문자열의 시작 부분을 알 수 없으므로 일반적인 B-Tree에서 탐색 시작점을 만들기 어렵다.</p>
<p>전문검색이나 <code>pg_trgm</code> 기반 GIN·GiST 인덱스 등 다른 방법을 검토할 수 있다.</p>
<hr />
<h2 id="284-자료형-불일치와-형변환">28.4 자료형 불일치와 형변환</h2>
<p>컬럼과 비교 값의 자료형이 맞지 않으면 형변환이 발생할 수 있다.</p>
<p>특히 컬럼 쪽에 형변환이 적용되는 형태가 되면 인덱스 활용에 영향을 줄 수 있다.</p>
<pre><code class="language-sql">WHERE text_id::integer = 100</code></pre>
<p>가능하면 컬럼 자료형과 비교 값의 자료형을 일치시키는 것이 좋다.</p>
<hr />
<h2 id="285-복합-인덱스의-선두-컬럼-미사용">28.5 복합 인덱스의 선두 컬럼 미사용</h2>
<pre><code class="language-text">인덱스: (customer_id, status)

조건:
status = 'PAID'</code></pre>
<p>두 번째 컬럼만으로는 탐색 범위를 앞에서부터 좁히기 어렵다.</p>
<hr />
<h2 id="286-통계정보가-부정확한-경우">28.6 통계정보가 부정확한 경우</h2>
<p>PostgreSQL은 통계정보를 바탕으로 결과 행 수와 비용을 추정한다.</p>
<p>통계가 오래되었거나 데이터 분포를 충분히 표현하지 못하면 인덱스가 더 좋은 상황에서도 다른 계획을 선택할 수 있다.</p>
<pre><code class="language-sql">ANALYZE employees;</code></pre>
<p>인덱스를 만든 뒤에도 실행계획으로 실제 사용 여부를 확인해야 한다.</p>
<hr />
<h1 id="29-인덱스-선택-가이드">29. 인덱스 선택 가이드</h1>
<h2 id="일반적인-조건·범위·정렬-검색">일반적인 조건·범위·정렬 검색</h2>
<pre><code class="language-sql">WHERE id = ?
WHERE salary BETWEEN ? AND ?
ORDER BY created_at</code></pre>
<pre><code class="language-text">→ B-Tree</code></pre>
<hr />
<h2 id="정확한-동등-비교만-수행">정확한 동등 비교만 수행</h2>
<pre><code class="language-sql">WHERE session_token = ?</code></pre>
<pre><code class="language-text">→ 우선 B-Tree 검토
→ 실제 측정에서 이점이 있다면 Hash 검토</code></pre>
<hr />
<h2 id="배열과-jsonb-포함-검색">배열과 JSONB 포함 검색</h2>
<pre><code class="language-sql">WHERE tags @&gt; ARRAY['DB']</code></pre>
<pre><code class="language-sql">WHERE attributes @&gt; '{&quot;color&quot;:&quot;black&quot;}'</code></pre>
<pre><code class="language-text">→ GIN</code></pre>
<hr />
<h2 id="공간·범위·거리·겹침-검색">공간·범위·거리·겹침 검색</h2>
<pre><code class="language-text">예약 기간이 겹치는가?
특정 영역 안에 있는가?
현재 위치에서 가장 가까운 지점은 어디인가?</code></pre>
<pre><code class="language-text">→ GiST</code></pre>
<hr />
<h2 id="공간-분할·접두사-구조">공간 분할·접두사 구조</h2>
<pre><code class="language-text">IP 주소
Trie 형태의 접두사
분할 가능한 점 데이터</code></pre>
<pre><code class="language-text">→ SP-GiST</code></pre>
<hr />
<h2 id="시간순-초대형-데이터">시간순 초대형 데이터</h2>
<pre><code class="language-sql">WHERE created_at BETWEEN ? AND ?</code></pre>
<pre><code class="language-text">→ BRIN</code></pre>
<p>단, 컬럼 값과 데이터의 물리적 저장 순서가 비슷해야 한다.</p>
<hr />
<h2 id="일부-상태의-데이터만-반복-조회">일부 상태의 데이터만 반복 조회</h2>
<pre><code class="language-sql">WHERE status = 'PENDING'</code></pre>
<pre><code class="language-text">→ 부분 인덱스</code></pre>
<hr />
<h2 id="함수-적용-결과를-반복-검색">함수 적용 결과를 반복 검색</h2>
<pre><code class="language-sql">WHERE LOWER(email) = ?</code></pre>
<pre><code class="language-text">→ 표현식 인덱스</code></pre>
<hr />
<h2 id="결과-반환-컬럼까지-인덱스에서-처리">결과 반환 컬럼까지 인덱스에서 처리</h2>
<pre><code class="language-sql">SELECT name, email
FROM employees
WHERE department_id = ?;</code></pre>
<pre><code class="language-text">→ INCLUDE를 이용한 Covering Index 검토</code></pre>

<h1 id="30-인덱스-설계-순서">30. 인덱스 설계 순서</h1>

<h2 id="301-자주-실행되는-쿼리-확인">30.1 자주 실행되는 쿼리 확인</h2>

<h2 id="302-선택성과-데이터-분포-확인">30.2 선택성과 데이터 분포 확인</h2>

<pre><code class="language-text">실행시간이 줄었는가?

쓰기 비용은 감당 가능한가?

<h1 id="31-전체-핵심-요약">31. 전체 핵심 요약</h1>
<h2 id="인덱스의-목적">인덱스의 목적</h2>
<pre><code class="language-text">전체 테이블을 순차 탐색하지 않고
&lt;Search Key, Pointer&gt;를 이용해
원하는 데이터 위치를 빠르게 찾는 것</code></pre>
<hr />
<h2 id="인덱스의-트레이드오프">인덱스의 트레이드오프</h2>
<pre><code class="language-text">인덱스 추가
→ SELECT 성능 향상 가능
→ INSERT·UPDATE·DELETE 비용 증가
→ 저장 공간 증가
→ VACUUM과 유지보수 비용 증가
→ 캐시 공간 사용 증가</code></pre>
<hr />
<h2 id="전통적인-분류">전통적인 분류</h2>
<pre><code class="language-text">Ordered / Hash
→ 탐색 키의 순서를 유지하는가?

Primary / Clustering / Secondary
→ 데이터의 물리적 저장 순서와 어떤 관계인가?

Dense / Sparse
→ 인덱스 엔트리를 얼마나 촘촘하게 저장하는가?</code></pre>
<hr />
<h2 id="btree의-핵심">B+Tree의 핵심</h2>
<pre><code class="language-text">하나의 노드에 많은 자식
→ 높은 Fan-out
→ 낮은 트리 높이
→ 적은 인덱스 페이지 접근

리프 노드가 정렬되고 서로 연결됨
→ 범위 검색에 유리</code></pre>
<hr />
<h2 id="postgresql에서-기억할-점">PostgreSQL에서 기억할 점</h2>
<pre><code class="language-text">1. 일반적인 인덱스는 인덱스 키와 TID를 이용해 Heap 행을 찾는다.

2. PostgreSQL은 MVCC를 사용하므로 UPDATE와 DELETE 시
   기존 행과 인덱스 엔트리가 즉시 물리적으로 제거되지 않는다.

3. 인덱스 컬럼이 변경되지 않는 일부 UPDATE는
   HOT Update로 인덱스 갱신을 피할 수 있다.

4. PostgreSQL에는 영구적인 CREATE BITMAP INDEX가 없다.

5. Bitmap Index Scan은 기존 인덱스 결과로
   실행 중 Bitmap을 만드는 방식이다.

6. PostgreSQL의 CLUSTER는 테이블을 한 번 재배치하지만
   이후의 물리적 순서를 자동으로 유지하지 않는다.

7. Index Only Scan도 Visibility Map 상태에 따라
   Heap Fetch가 발생할 수 있다.

8. 인덱스가 존재해도 조회 결과가 많다면
   Sequential Scan이 더 효율적일 수 있다.</code></pre>

<h1 id="결론">결론</h1>
<p>인덱스는 많을수록 좋은 것이 아니다.</p>
<p>좋은 인덱스는 다음 질문에 대한 답을 바탕으로 만들어진다.</p>
<pre><code class="language-text">어떤 WHERE 조건이 자주 사용되는가?
정확한 일치 검색인가, 범위 검색인가?
정렬이 필요한가?
전체 데이터 중 몇 개의 행을 조회하는가?
데이터 변경은 얼마나 자주 발생하는가?
컬럼 값과 물리적 저장 순서가 비슷한가?
일부 상태의 행만 자주 조회하는가?
함수 적용 결과를 검색하는가?
필요한 컬럼을 인덱스만으로 반환할 수 있는가?</code></pre>
<p>가장 기본적인 선택은 B-Tree다.</p>
<p>Hash, GIN, GiST, SP-GiST, BRIN은 B-Tree로 효율적으로 처리하기 어려운 데이터 구조와 검색 방식을 지원하는 특수한 선택지다.</p>
<p>그리고 최종적인 판단은 인덱스의 존재 여부가 아니라 실제 실행계획과 측정 결과를 통해 내려야 한다.</p>
<pre><code class="language-text">정확한 쿼리 작성
→ 데이터 분포 확인
→ 인덱스 설계
→ EXPLAIN ANALYZE로 검증
→ 읽기 성능과 쓰기 비용을 함께 평가</code></pre>
<p>이 흐름을 이해하면 인덱스를 단순한 조회 가속 기능이 아니라, 데이터의 물리적 접근 방식과 읽기·쓰기 비용을 함께 설계하는 도구로 바라볼 수 있다.</p>
