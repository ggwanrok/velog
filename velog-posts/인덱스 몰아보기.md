<h1 id="데이터베이스-인덱스-이론-정리">데이터베이스 인덱스 이론 정리</h1>
<p>데이터베이스에서 인덱스는 흔히 다음과 같이 설명된다.</p>
<blockquote>
<p>인덱스는 데이터 조회 속도를 높이기 위한 자료구조다.</p>
</blockquote>
<p>틀린 설명은 아니지만, 이것만으로는 인덱스를 충분히 이해하기 어렵다.</p>
<p>인덱스는 데이터를 빠르게 찾게 해주는 대신 추가 저장 공간을 사용한다. 또한 데이터가 삽입·수정·삭제될 때 인덱스도 함께 관리되어야 하므로 쓰기 비용을 증가시킨다.</p>
<p>따라서 인덱스는 단순한 조회 가속 기능이 아니라 다음 요소를 함께 고려하는 설계 도구다.</p>
<pre><code class="language-text">어떤 값을 기준으로 데이터를 찾을 것인가?
어떤 자료구조로 탐색할 것인가?
인덱스와 실제 데이터는 어떤 관계를 가지는가?
얼마나 많은 인덱스 정보를 저장할 것인가?
조회 성능과 변경 비용 사이에서 어떤 균형을 선택할 것인가?</code></pre>
<p>인덱스 이론은 다음 흐름으로 이해하는 것이 좋다.</p>
<pre><code class="language-text">인덱스의 기본 개념
→ 인덱스 엔트리와 페이지
→ 인덱스의 구현 방식
→ 다단계 인덱스와 B+Tree
→ 인덱스 분류
→ 선택성과 효율
→ 복합 인덱스 설계
→ 인덱스의 비용과 주의점</code></pre>
<hr />
<h1 id="인덱스란">인덱스란?</h1>
<p>인덱스는 테이블 전체를 처음부터 끝까지 읽지 않고, 원하는 데이터가 저장된 위치를 빠르게 찾기 위한 보조 자료구조다.</p>
<p>책에서 특정 단원를 찾을 때 모든 페이지를 순서대로 넘기지 않고, 책 뒤의 색인에서 단어와 페이지 번호를 확인하는 것과 비슷하다.</p>
<p>예를 들어 다음과 같은 데이터가 있다고 하자.</p>
<pre><code class="language-text">사원 번호    이름
1001        김철수
1002        이영희
1003        박민수
1004        최지수</code></pre>
<p>사원 번호를 기준으로 인덱스를 구성하면 개념적으로 다음과 같은 정보를 저장할 수 있다.</p>
<pre><code class="language-text">1001 → 데이터 위치 A
1002 → 데이터 위치 B
1003 → 데이터 위치 C
1004 → 데이터 위치 D</code></pre>
<p>사원 번호가 <code>1003</code>인 데이터를 찾을 때 테이블의 모든 행을 확인하지 않고, 인덱스에서 <code>1003</code>을 탐색한 뒤 해당 데이터 위치로 이동할 수 있다.</p>
<hr />
<h1 id="인덱스-엔트리">인덱스 엔트리</h1>
<p>인덱스는 일반적으로 다음과 같은 엔트리로 구성된다.</p>
<pre><code class="language-text">&lt;Search Key, Pointer&gt;</code></pre>
<h2 id="search-key">Search Key</h2>
<p><code>Search Key</code>는 데이터를 찾는 기준이 되는 값이다.</p>
<p>탐색 키는 하나의 컬럼일 수도 있고, 여러 컬럼의 조합일 수도 있다.</p>
<pre><code class="language-text">사원 번호
이메일
부서 번호
급여
생성 일시
상태
이름과 생년월일의 조합</code></pre>
<p>탐색 키는 반드시 기본키일 필요는 없다.</p>
<p>예를 들어 고객 번호와 주문 상태를 함께 탐색 기준으로 사용한다면 다음과 같은 복합 탐색 키를 구성할 수 있다.</p>
<pre><code class="language-text">(고객 번호, 주문 상태)</code></pre>
<h2 id="pointer">Pointer</h2>
<p><code>Pointer</code>는 탐색 키에 대응하는 데이터의 위치를 가리킨다.</p>
<p>구현 방식에 따라 포인터는 다음과 같은 대상을 가리킬 수 있다.</p>
<pre><code class="language-text">실제 데이터 레코드
데이터가 저장된 페이지
동일한 키를 가진 데이터 위치 목록
하위 단계의 인덱스 페이지
다른 탐색 키</code></pre>
<p>인덱스의 핵심은 탐색 키를 이용해 원하는 데이터가 있는 위치를 빠르게 좁혀 가는 것이다.</p>
<hr />
<h1 id="인덱스와-페이지">인덱스와 페이지</h1>
<p>디스크 기반 데이터베이스는 일반적으로 데이터를 레코드 하나씩 읽지 않는다.</p>
<p>여러 개의 레코드가 들어 있는 페이지 또는 블록 단위로 데이터를 읽는다.</p>
<pre><code class="language-text">데이터 파일
├── Page 1
├── Page 2
├── Page 3
├── Page 4
└── ...</code></pre>
<p>인덱스도 페이지 단위로 저장된다.</p>
<pre><code class="language-text">인덱스 페이지
├── 탐색 키
├── 탐색 키
├── 탐색 키
└── 포인터</code></pre>
<p>인덱스를 이용한 검색은 개념적으로 다음과 같이 진행된다.</p>
<pre><code class="language-text">인덱스 페이지 탐색
        ↓
조건에 맞는 키 확인
        ↓
데이터 위치 확인
        ↓
데이터 페이지 접근
        ↓
실제 레코드 반환</code></pre>
<p>따라서 인덱스의 성능은 단순한 비교 연산 횟수만으로 결정되지 않는다.</p>
<p>다음 요소가 함께 중요하다.</p>
<pre><code class="language-text">몇 개의 인덱스 페이지를 읽는가?
몇 개의 데이터 페이지를 읽는가?
페이지를 순차적으로 읽는가?
여러 위치를 무작위로 읽는가?
필요한 페이지가 메모리에 존재하는가?</code></pre>
<p>인덱스의 목적은 전체 데이터 페이지를 읽는 대신, 필요한 데이터가 들어 있는 일부 페이지만 읽도록 만드는 것이다.</p>
<hr />
<h1 id="인덱스가-지원하는-작업">인덱스가 지원하는 작업</h1>
<p>인덱스는 단순한 단건 조회 외에도 여러 작업을 지원할 수 있다.</p>
<h2 id="정확한-일치-검색">정확한 일치 검색</h2>
<p>특정 값과 정확히 일치하는 데이터를 찾는다.</p>
<pre><code class="language-sql">WHERE employee_id = 100</code></pre>
<p>이를 동등 검색 또는 정확한 일치 검색이라고 한다.</p>
<h2 id="범위-검색">범위 검색</h2>
<p>특정 값의 범위에 포함되는 데이터를 찾는다.</p>
<pre><code class="language-sql">WHERE salary BETWEEN 5000 AND 10000</code></pre>
<pre><code class="language-sql">WHERE created_at &gt;= '2026-01-01'</code></pre>
<p>값의 순서가 유지되는 인덱스 구조는 범위 검색을 효율적으로 처리할 수 있다.</p>
<h2 id="정렬">정렬</h2>
<p>인덱스가 원하는 순서로 정렬되어 있다면 별도의 정렬 작업을 줄일 수 있다.</p>
<pre><code class="language-sql">ORDER BY created_at</code></pre>
<h2 id="조인">조인</h2>
<p>두 데이터 집합을 연결할 때 조인 대상 값을 빠르게 찾는 데 사용할 수 있다.</p>
<pre><code class="language-sql">employees.department_id = departments.department_id</code></pre>
<h2 id="최솟값과-최댓값">최솟값과 최댓값</h2>
<p>정렬된 인덱스에서는 첫 번째 또는 마지막 엔트리를 이용해 최솟값과 최댓값을 찾을 수 있다.</p>
<h2 id="고유성-검사">고유성 검사</h2>
<p>고유 인덱스는 동일한 탐색 키가 이미 존재하는지를 빠르게 확인할 수 있다.</p>
<p>인덱스는 조회뿐 아니라 데이터 무결성 검사에도 사용될 수 있다.</p>
<hr />
<h1 id="ordered-index와-hash-index">Ordered Index와 Hash Index</h1>
<p>인덱스는 탐색 키의 순서를 유지하는지에 따라 크게 정렬 인덱스와 해시 인덱스로 구분할 수 있다.</p>
<h2 id="ordered-index">Ordered Index</h2>
<p>Ordered Index는 탐색 키를 정렬된 순서로 저장한다.</p>
<pre><code class="language-text">10 → 위치 A
20 → 위치 B
30 → 위치 C
40 → 위치 D</code></pre>
<p>값의 순서가 유지되므로 다음과 같은 검색에 적합하다.</p>
<pre><code class="language-text">정확한 값 검색
범위 검색
대소 비교
정렬
최솟값과 최댓값 검색</code></pre>
<p>예를 들면 다음과 같다.</p>
<pre><code class="language-sql">WHERE id = 20</code></pre>
<pre><code class="language-sql">WHERE id &gt; 20</code></pre>
<pre><code class="language-sql">WHERE id BETWEEN 10 AND 30</code></pre>
<pre><code class="language-sql">ORDER BY id</code></pre>
<p>대표적인 Ordered Index 구조가 B-Tree와 B+Tree다.</p>
<h2 id="hash-index">Hash Index</h2>
<p>Hash Index는 탐색 키를 해시 함수에 입력하여 해당 값이 저장될 버킷 위치를 계산한다.</p>
<pre><code class="language-text">탐색 키
   ↓
해시 함수
   ↓
해시값
   ↓
버킷 위치</code></pre>
<p>예를 들어 이메일 주소를 해시 함수에 입력하면 특정 버킷 번호가 계산된다.</p>
<pre><code class="language-text">kim@example.com
        ↓
      hash()
        ↓
    Bucket 17</code></pre>
<p>Hash Index는 정확한 동등 비교에 적합하다.</p>
<pre><code class="language-sql">WHERE email = 'kim@example.com'</code></pre>
<p>그러나 해시값은 원래 값의 순서를 보존하지 않는다.</p>
<pre><code class="language-text">원래 값: 10, 20, 30
해시값:  81, 13, 55</code></pre>
<p>따라서 다음과 같은 연산에는 적합하지 않다.</p>
<pre><code class="language-text">범위 검색
대소 비교
정렬
최솟값과 최댓값 검색</code></pre>
<pre><code class="language-sql">WHERE salary &gt; 5000</code></pre>
<pre><code class="language-sql">WHERE age BETWEEN 20 AND 30</code></pre>
<pre><code class="language-sql">ORDER BY salary</code></pre>

<h1 id="데이터의-물리적-저장-순서에-따른-분류">데이터의 물리적 저장 순서에 따른 분류</h1>
<p>인덱스는 탐색 키의 순서와 실제 데이터의 저장 순서가 어떤 관계를 가지는지에 따라 분류할 수도 있다.</p>
<p>대표적으로 다음 세 가지 개념이 있다.</p>
<pre><code class="language-text">Primary Index
Clustering Index
Secondary Index</code></pre>
<p>이때 중요한 것은 이러한 분류가 기본키 제약조건의 유무가 아니라, 실제 데이터 저장 순서와 탐색 키의 관계를 기준으로 한다는 점이다.</p>
<p>또한 세부 용어는 교재나 데이터베이스 시스템마다 조금씩 다르게 사용될 수 있다.</p>
<hr />
<h2 id="primary-index">Primary Index</h2>
<p>전통적인 인덱스 이론에서 Primary Index는 실제 데이터 파일이 고유한 탐색 키 순서로 정렬되어 있고, 해당 정렬 기준에 대해 만들어진 인덱스를 의미한다.</p>
<p>예를 들어 데이터가 사원 번호 순서로 저장되어 있다고 하자.</p>
<pre><code class="language-text">1001 김철수
1002 이영희
1003 박민수
1004 최지수</code></pre>
<p>사원 번호를 기준으로 인덱스를 구성하면 탐색 키의 순서와 데이터 저장 순서가 일치한다.</p>
<pre><code class="language-text">탐색 키 순서
1001, 1002, 1003, 1004

데이터 저장 순서
1001, 1002, 1003, 1004</code></pre>
<p>Primary Index에서 중요한 것은 다음 두 조건이다.</p>
<pre><code class="language-text">탐색 키가 고유함
+
데이터가 탐색 키 순서로 저장됨</code></pre>
<p>기본키가 정렬 기준으로 사용되는 경우가 많지만, <code>Primary Index</code>와 <code>Primary Key</code>가 항상 같은 의미인 것은 아니다.</p>
<hr />
<h2 id="clustering-index">Clustering Index</h2>
<p>Clustering Index는 데이터가 특정 탐색 키 값을 기준으로 물리적으로 모여 있는 구조다.</p>
<p>Primary Index와 달리 탐색 키는 중복될 수 있다.</p>
<p>예를 들어 부서 번호 순서로 데이터가 저장되어 있다고 하자.</p>
<pre><code class="language-text">10 김철수
10 박민수
10 이지수
20 최영희
20 윤서연
30 정민호</code></pre>
<p>같은 부서에 속한 데이터가 가까운 페이지에 모여 있다.</p>
<p>인덱스는 각 그룹의 시작 위치를 가리킬 수 있다.</p>
<pre><code class="language-text">10 → 10번 부서 데이터의 시작 위치
20 → 20번 부서 데이터의 시작 위치
30 → 30번 부서 데이터의 시작 위치</code></pre>
<p>같은 키를 가진 여러 데이터를 조회할 때 관련 데이터가 가까운 페이지에 모여 있으므로 페이지 접근 효율을 높일 수 있다.</p>
<pre><code class="language-text">같은 값을 가진 데이터가 물리적으로 가까움
→ 연속된 페이지 접근 가능
→ 무작위 접근 감소</code></pre>
<p>한 데이터 파일을 여러 탐색 키 순서로 동시에 물리적으로 정렬할 수는 없다.</p>
<p>따라서 하나의 데이터 파일에서 물리적 정렬 기준은 일반적으로 하나만 선택할 수 있다.</p>
<hr />
<h2 id="secondary-index">Secondary Index</h2>
<p>Secondary Index는 탐색 키의 정렬 순서와 실제 데이터의 물리적 저장 순서가 일치하지 않는 인덱스다.</p>
<p>예를 들어 데이터는 사원 번호 순서로 저장되어 있지만 부서 이름을 기준으로 인덱스를 만들 수 있다.</p>
<pre><code class="language-text">실제 데이터 저장 순서

1001 김철수 개발팀
1002 이영희 인사팀
1003 박민수 개발팀
1004 최지수 재무팀</code></pre>
<p>부서 이름 인덱스는 다음과 같이 정렬될 수 있다.</p>
<pre><code class="language-text">개발팀 → 1001 위치, 1003 위치
인사팀 → 1002 위치
재무팀 → 1004 위치</code></pre>
<p>하지만 실제 데이터는 여러 페이지에 흩어져 있을 수 있다.</p>
<pre><code class="language-text">개발팀 사원 1 → Block 2
개발팀 사원 2 → Block 19
개발팀 사원 3 → Block 7</code></pre>
<p>조회 대상이 적으면 일부 페이지만 방문하면 되므로 효율적이다.</p>
<p>그러나 조회 대상이 많으면 수많은 데이터 페이지를 무작위로 방문해야 한다.</p>
<pre><code class="language-text">Block 2
→ Block 19
→ Block 7
→ Block 31
→ ...</code></pre>
<p>이 경우 인덱스를 사용하는 것보다 테이블 전체를 순차적으로 읽는 편이 더 효율적일 수 있다.</p>
<hr />
<h1 id="dense-index와-sparse-index">Dense Index와 Sparse Index</h1>
<p>Dense와 Sparse는 인덱스 엔트리를 얼마나 촘촘하게 저장하는지를 기준으로 한 분류다.</p>
<pre><code class="language-text">Primary / Clustering / Secondary
→ 데이터 저장 순서와의 관계

Dense / Sparse
→ 인덱스 엔트리의 밀도</code></pre>
<p>두 분류는 서로 다른 기준이다.</p>
<hr />
<h2 id="dense-index">Dense Index</h2>
<p>Dense Index는 모든 탐색 키 값에 대한 접근 정보를 가지는 구조다.</p>
<pre><code class="language-text">데이터

1001 김철수
1002 이영희
1003 박민수
1004 최지수</code></pre>
<pre><code class="language-text">Dense Index

1001 → 데이터 위치
1002 → 데이터 위치
1003 → 데이터 위치
1004 → 데이터 위치</code></pre>
<p>중복된 탐색 키가 있는 경우 하나의 키가 여러 데이터 위치를 가리킬 수도 있다.</p>
<pre><code class="language-text">개발팀
├── 김철수 위치
├── 박민수 위치
└── 윤서연 위치</code></pre>
<h3 id="장점">장점</h3>
<pre><code class="language-text">원하는 키의 위치를 직접 확인할 수 있음
검색 과정이 비교적 빠름
데이터가 탐색 키 순서로 정렬되지 않아도 사용 가능</code></pre>
<h3 id="단점">단점</h3>
<pre><code class="language-text">인덱스 엔트리 수가 많음
추가 저장 공간 사용
삽입·수정·삭제 비용 증가</code></pre>
<p>Secondary Index는 일반적으로 Dense한 구조가 필요하다.</p>
<p>실제 데이터가 탐색 키 순서로 저장되어 있지 않으므로 각 키의 위치를 개별적으로 기록해야 하기 때문이다.</p>
<hr />
<h2 id="sparse-index">Sparse Index</h2>
<p>Sparse Index는 모든 탐색 키를 저장하지 않고 일부 대표 키에 대해서만 인덱스 엔트리를 저장한다.</p>
<p>예를 들어 데이터가 다음과 같이 블록 단위로 정렬되어 있다고 하자.</p>
<pre><code class="language-text">Block 1: 1001, 1002
Block 2: 1003, 1004
Block 3: 1005, 1006</code></pre>
<p>Sparse Index는 각 블록의 첫 번째 값만 저장할 수 있다.</p>
<pre><code class="language-text">1001 → Block 1
1003 → Block 2
1005 → Block 3</code></pre>
<p><code>1004</code>를 찾는 과정은 다음과 같다.</p>
<pre><code class="language-text">1. 인덱스에서 1004 이하의 가장 큰 대표 키를 찾는다.
2. 대표 키 1003을 찾는다.
3. 1003이 가리키는 Block 2로 이동한다.
4. Block 2 내부에서 1004를 찾는다.</code></pre>
<h3 id="장점-1">장점</h3>
<pre><code class="language-text">인덱스 엔트리 수가 적음
저장 공간을 적게 사용함
인덱스 자체를 읽는 비용이 작음</code></pre>
<h3 id="단점-1">단점</h3>
<pre><code class="language-text">데이터 블록 내부를 다시 탐색해야 함
대표 키가 변경되면 인덱스 수정이 필요함
데이터가 탐색 키 순서로 정렬되어 있어야 함</code></pre>
<p>Sparse Index가 동작하려면 실제 데이터가 탐색 키 순서로 정렬되어 있어야 한다.</p>
<p>데이터가 정렬되어 있어야 특정 값이 어느 대표 키 사이에 존재하는지 추론할 수 있기 때문이다.</p>
<hr />
<h1 id="인덱스-분류의-관계">인덱스 분류의 관계</h1>
<p>각 분류는 서로 독립적인 기준을 사용한다.</p>
<pre><code class="language-text">Ordered / Hash
→ 탐색 키의 순서를 유지하는가?

Primary / Clustering / Secondary
→ 데이터의 물리적 저장 순서와 어떤 관계인가?

Dense / Sparse
→ 인덱스 엔트리를 얼마나 촘촘하게 저장하는가?</code></pre>
<p>따라서 하나의 인덱스는 여러 분류에 동시에 속할 수 있다.</p>
<p>예를 들어 다음과 같이 생각할 수 있다.</p>
<pre><code class="language-text">정렬된 탐색 키를 사용하고
실제 데이터 순서와 일치하며
블록별 대표 키만 저장하는 인덱스</code></pre>
<p>이 인덱스는 다음 특성을 동시에 가질 수 있다.</p>
<pre><code class="language-text">Ordered Index
Primary 또는 Clustering Index
Sparse Index</code></pre>
<p>반면 실제 데이터 저장 순서와 관계없이 각 탐색 키의 위치를 저장한다면 다음과 같은 특성을 가질 수 있다.</p>
<pre><code class="language-text">Ordered Index
Secondary Index
Dense Index</code></pre>
<hr />
<h1 id="multilevel-index">Multilevel Index</h1>
<p>데이터가 많아지면 인덱스 자체도 커진다.</p>
<p>인덱스 전체가 하나의 페이지나 메모리에 들어가지 않는다면 원하는 인덱스 엔트리를 찾기 위해 인덱스 페이지도 여러 개 읽어야 한다.</p>
<p>이를 해결하기 위해 인덱스 위에 다시 인덱스를 구성할 수 있다.</p>
<pre><code class="language-text">상위 인덱스
      ↓
하위 인덱스
      ↓
데이터 파일</code></pre>
<p>예를 들어 하위 인덱스 페이지가 다음과 같다고 하자.</p>
<pre><code class="language-text">Index Block 1: 10, 20, 30
Index Block 2: 40, 50, 60
Index Block 3: 70, 80, 90</code></pre>
<p>상위 인덱스에는 각 하위 페이지의 대표 키만 저장할 수 있다.</p>
<pre><code class="language-text">10 → Index Block 1
40 → Index Block 2
70 → Index Block 3</code></pre>
<p><code>50</code>을 찾는 과정은 다음과 같다.</p>
<pre><code class="language-text">1. 상위 인덱스에서 50 이하의 가장 큰 대표 키를 찾는다.
2. 대표 키 40을 찾는다.
3. Index Block 2로 이동한다.
4. 하위 인덱스에서 50을 찾는다.
5. 실제 데이터 위치로 이동한다.</code></pre>
<p>인덱스 위에 인덱스를 구성하면 탐색 범위를 단계적으로 줄일 수 있다.</p>
<pre><code class="language-text">전체 인덱스
→ 관련 인덱스 페이지
→ 관련 데이터 페이지
→ 실제 데이터</code></pre>
<p>이러한 다단계 인덱스를 균형 있게 관리하는 대표적인 자료구조가 B-Tree와 B+Tree다.</p>
<hr />
<h1 id="b-tree-계열이-필요한-이유">B-Tree 계열이 필요한 이유</h1>
<p>일반적인 이진 탐색 트리는 한 노드가 최대 두 개의 자식을 가진다.</p>
<pre><code class="language-text">Binary Search Tree
→ 한 노드당 자식 최대 2개</code></pre>
<p>데이터가 많아지면 트리의 높이가 커질 수 있다.</p>
<p>디스크 기반 환경에서는 트리의 각 노드가 별도의 페이지에 저장될 수 있으므로 트리 높이가 커질수록 페이지 접근 횟수도 증가한다.</p>
<p>B-Tree 계열은 하나의 노드에 여러 개의 키와 포인터를 저장한다.</p>
<pre><code class="language-text">                [ 30 |   60   |  90 ]
              /      |        |       \
           0~29    30~59   60~89    90 이상</code></pre>
<p>한 노드가 많은 자식을 가질 수 있는 특성을 높은 <code>Fan-out</code>이라고 한다.</p>
<pre><code class="language-text">높은 Fan-out
→ 한 노드에 많은 자식 저장
→ 트리 높이 감소
→ 페이지 접근 횟수 감소</code></pre>
<p>따라서 매우 많은 데이터가 존재해도 비교적 적은 수의 페이지 접근으로 원하는 데이터에 도달할 수 있다.</p>
<hr />
<h2 id="btree의-구조">B+Tree의 구조</h2>
<p>데이터베이스 인덱스에서는 일반적으로 B+Tree 계열의 구조가 널리 사용된다.</p>
<p>B+Tree는 크게 내부 노드와 리프 노드로 구성된다.</p>
<pre><code class="language-text">Root Node
    ↓
Internal Node
    ↓
Leaf Node</code></pre>
<h3 id="내부-노드">내부 노드</h3>
<p>내부 노드는 실제 검색 결과를 직접 제공하기보다 어느 하위 페이지로 이동해야 하는지를 알려주는 역할을 한다.</p>
<pre><code class="language-text">              [40 | 70]
             /    |    \
         10~39  40~69  70 이상</code></pre>
<p>내부 노드는 하위 페이지의 범위를 구분하기 위한 대표 키와 포인터를 저장한다.</p>
<pre><code class="language-text">대표 키 → 하위 페이지</code></pre>
<p>모든 탐색 키를 저장하지 않고 하위 페이지의 대표 키를 저장하므로 Sparse Index와 비슷한 역할을 한다.</p>
<h3 id="리프-노드">리프 노드</h3>
<p>실제 검색에 사용되는 인덱스 엔트리는 리프 노드에 저장된다.</p>
<pre><code class="language-text">[10, 20, 30] ↔ [40, 50, 60] ↔ [70, 80, 90]</code></pre>
<p>리프 노드는 탐색 키 순서로 정렬되어 있다.</p>
<p>또한 인접한 리프 노드끼리 연결되어 있어 범위 검색에 유리하다.</p>
<hr />
<h2 id="btree의-검색">B+Tree의 검색</h2>
<p>특정 값 <code>50</code>을 찾는다고 하자.</p>
<pre><code class="language-text">1. 루트 노드에서 50이 속한 범위를 찾는다.
2. 해당 내부 노드로 이동한다.
3. 내부 노드에서 다시 범위를 좁힌다.
4. 50이 들어 있는 리프 노드에 도달한다.
5. 리프 노드에서 50을 찾는다.
6. 실제 데이터 위치로 이동한다.</code></pre>
<p>B+Tree는 균형 트리이기 때문에 모든 리프 노드가 일반적으로 비슷한 깊이에 존재한다.</p>
<p>따라서 특정 데이터만 유난히 오래 걸리는 문제를 줄일 수 있다.</p>
<p>일반적으로 탐색 비용은 다음과 같이 표현할 수 있다.</p>
<pre><code class="language-text">O(log N)</code></pre>
<p>다만 데이터베이스에서 중요한 것은 단순한 연산 횟수뿐 아니라 실제로 몇 개의 페이지를 읽었는가이다.</p>
<hr />
<h2 id="btree의-범위-검색">B+Tree의 범위 검색</h2>
<p>B+Tree의 가장 중요한 장점 중 하나는 범위 검색이다.</p>
<p>예를 들어 다음 범위를 찾는다고 하자.</p>
<pre><code class="language-text">30 이상 80 이하</code></pre>
<p>처리 과정은 다음과 같다.</p>
<pre><code class="language-text">1. 트리를 따라 30이 위치한 리프 노드까지 이동한다.
2. 리프 노드에서 30 이상의 첫 번째 키를 찾는다.
3. 연결된 다음 리프 노드를 순서대로 읽는다.
4. 80을 초과하면 탐색을 종료한다.</code></pre>
<p>리프 노드들이 연결되어 있으므로 범위 안의 모든 값을 루트부터 각각 다시 검색할 필요가 없다.</p>
<pre><code class="language-text">시작 위치 탐색
→ 연결된 리프 노드 순차 탐색
→ 종료 범위에서 중단</code></pre>
<p>이 때문에 B+Tree는 다음 작업에 적합하다.</p>
<pre><code class="language-text">범위 검색
정렬된 결과 조회
최솟값과 최댓값 조회
접두사 기반 탐색</code></pre>
<hr />
<h2 id="btree의-삽입">B+Tree의 삽입</h2>
<p>리프 노드에 새로운 키를 추가할 공간이 있다면 정렬 순서에 맞게 삽입한다.</p>
<pre><code class="language-text">기존 리프 노드
[10, 20, 40]

30 삽입

[10, 20, 30, 40]</code></pre>
<p>리프 노드에 공간이 없다면 노드 분할이 발생할 수 있다.</p>
<pre><code class="language-text">노드가 가득 참
→ 두 개의 노드로 분할
→ 부모 노드에 새로운 경계 키 추가</code></pre>
<p>예를 들어 다음 노드가 가득 찼다고 하자.</p>
<pre><code class="language-text">[10, 20, 30, 40]</code></pre>
<p>새로운 값 <code>50</code>이 들어오면 다음처럼 분할될 수 있다.</p>
<pre><code class="language-text">[10, 20] ↔ [30, 40, 50]</code></pre>
<p>부모 노드에는 새로운 경계 키가 추가된다.</p>
<pre><code class="language-text">부모 노드
[30]</code></pre>
<p>부모 노드도 가득 찬 상태라면 분할이 상위 노드까지 이어질 수 있다.</p>
<pre><code class="language-text">리프 노드 분할
→ 부모 노드 수정
→ 부모 노드 분할
→ 필요하면 새로운 루트 생성</code></pre>
<p>따라서 데이터 삽입은 실제 데이터만 추가하는 작업이 아니라 인덱스 구조를 유지하는 작업까지 포함할 수 있다.</p>
<hr />
<h2 id="btree의-삭제">B+Tree의 삭제</h2>
<p>키가 삭제되면 해당 엔트리를 제거한다.</p>
<p>삭제로 인해 노드의 사용량이 지나치게 낮아지면 다음 작업이 발생할 수 있다.</p>
<pre><code class="language-text">인접 노드에서 키 재분배
또는
인접 노드와 병합</code></pre>
<h3 id="키-재분배">키 재분배</h3>
<p>인접 노드에 충분한 키가 있다면 일부 키를 옮겨 노드 사용량을 맞춘다.</p>
<pre><code class="language-text">삭제 전

[10]   [20, 30, 40]

재분배 후

[10, 20]   [30, 40]</code></pre>
<h3 id="노드-병합">노드 병합</h3>
<p>인접 노드에도 여유가 없다면 두 노드를 하나로 합칠 수 있다.</p>
<pre><code class="language-text">[10] + [20]
    ↓
[10, 20]</code></pre>
<p>노드 병합이 발생하면 부모 노드의 경계 키도 수정해야 한다.</p>
<p>B+Tree는 삽입과 삭제가 반복되어도 트리의 균형을 유지하도록 설계되어 있다.</p>
<hr />
<h1 id="선택성과-인덱스-효율">선택성과 인덱스 효율</h1>
<p>인덱스가 효율적인지는 조건이 전체 데이터 중 얼마나 적은 데이터를 선택하는지에 크게 영향을 받는다.</p>
<p>조건 만족 비율은 다음과 같이 표현할 수 있다.</p>
<pre><code class="language-text">조건 만족 비율
= 조건을 만족하는 데이터 수 / 전체 데이터 수</code></pre>
<p>예를 들어 전체 100만 건 중 한 건을 찾는다고 하자.</p>
<pre><code class="language-text">1 / 1,000,000</code></pre>
<p>결과 데이터가 매우 적기 때문에 인덱스로 필요한 위치만 찾는 것이 유리할 가능성이 높다.</p>
<p>반면 전체 데이터의 절반을 찾는다면 다음과 같다.</p>
<pre><code class="language-text">500,000 / 1,000,000</code></pre>
<p>결과가 많기 때문에 인덱스를 통해 데이터 위치를 하나씩 찾아가는 비용이 커질 수 있다.</p>
<h2 id="선택성이-높은-조건">선택성이 높은 조건</h2>
<pre><code class="language-text">조건을 만족하는 데이터가 적음
→ 필요한 데이터 페이지만 접근
→ 인덱스 사용이 유리할 가능성이 높음</code></pre>
<p>예를 들면 다음과 같다.</p>
<pre><code class="language-text">고유한 사원 번호
고유한 이메일
주문 번호
상품 식별자</code></pre>
<h2 id="선택성이-낮은-조건">선택성이 낮은 조건</h2>
<pre><code class="language-text">조건을 만족하는 데이터가 많음
→ 많은 데이터 페이지 접근
→ 전체 데이터를 순차 탐색하는 것이 유리할 수 있음</code></pre>
<p>예를 들면 다음과 같다.</p>
<pre><code class="language-text">성별
활성 여부
처리 완료 여부
두세 종류만 존재하는 상태 값</code></pre>
<p>그러나 값의 종류가 적다고 해서 항상 인덱스가 비효율적인 것은 아니다.</p>
<p>예를 들어 상태 값이 두 종류뿐이어도 특정 상태가 전체의 0.1%만 차지한다면 해당 조건은 충분히 선택적일 수 있다.</p>
<p>따라서 중요한 것은 단순한 값의 종류가 아니라 실제 데이터 분포다.</p>
<hr />
<h1 id="카디널리티와-선택성">카디널리티와 선택성</h1>
<p>카디널리티는 컬럼에 존재하는 서로 다른 값의 개수를 의미한다.</p>
<p>예를 들어 전체 데이터가 100만 건일 때 다음과 같이 생각할 수 있다.</p>
<pre><code class="language-text">사원 번호
→ 서로 다른 값 약 100만 개
→ 높은 카디널리티

부서 번호
→ 서로 다른 값 20개
→ 상대적으로 낮은 카디널리티

성별
→ 서로 다른 값 2개
→ 낮은 카디널리티</code></pre>
<p>카디널리티가 높으면 특정 값을 조회했을 때 결과 행이 적을 가능성이 높다.</p>
<p>하지만 카디널리티와 선택성은 완전히 같은 개념은 아니다.</p>
<pre><code class="language-text">카디널리티
→ 컬럼에 서로 다른 값이 몇 개 존재하는가?

선택성
→ 특정 조건이 전체 데이터 중 얼마나 적은 데이터를 선택하는가?</code></pre>
<p>예를 들어 상태 값이 다음과 같이 분포할 수 있다.</p>
<pre><code class="language-text">COMPLETED: 990,000건
PENDING:    10,000건</code></pre>
<p>상태 컬럼의 카디널리티는 낮지만 <code>PENDING</code> 조건은 상대적으로 선택성이 높다.</p>
<p>따라서 인덱스 설계에서는 값의 개수뿐 아니라 값별 데이터 분포도 확인해야 한다.</p>
<hr />
<h1 id="복합-인덱스">복합 인덱스</h1>
<p>복합 인덱스는 두 개 이상의 탐색 키로 구성된 인덱스다.</p>
<pre><code class="language-text">(customer_id, status)</code></pre>
<p>복합 인덱스는 첫 번째 컬럼부터 순서대로 정렬된다.</p>
<pre><code class="language-text">customer_id 우선 정렬
→ customer_id가 같으면 status 정렬</code></pre>
<p>예를 들어 다음과 같은 구조가 만들어진다.</p>
<pre><code class="language-text">customer_id | status
------------+-----------
100         | CANCELLED
100         | PAID
100         | READY
200         | CANCELLED
200         | PAID
200         | READY</code></pre>
<p><code>customer_id = 100</code>인 데이터는 하나의 연속된 범위에 모여 있다.</p>
<pre><code class="language-text">100 | CANCELLED
100 | PAID
100 | READY</code></pre>
<p>따라서 다음 조건은 효율적으로 검색 범위를 좁힐 수 있다.</p>
<pre><code class="language-text">customer_id = 100</code></pre>
<p>다음 조건도 활용하기 좋다.</p>
<pre><code class="language-text">customer_id = 100
AND status = PAID</code></pre>
<hr />
<h2 id="leftmost-prefix">Leftmost Prefix</h2>
<p>복합 인덱스는 일반적으로 왼쪽에 위치한 컬럼부터 탐색 범위를 좁힐 수 있다.</p>
<p>이를 Leftmost Prefix 특성이라고 한다.</p>
<pre><code class="language-text">INDEX(a, b, c)</code></pre>
<p>다음 조건은 인덱스의 왼쪽부터 연속적으로 사용한다.</p>
<pre><code class="language-text">a
a, b
a, b, c</code></pre>
<p>반면 다음 조건은 첫 번째 컬럼이 없다.</p>
<pre><code class="language-text">b
c
b, c</code></pre>
<p>예를 들어 인덱스가 다음과 같다고 하자.</p>
<pre><code class="language-text">(customer_id, status)</code></pre>
<p><code>status = PAID</code>만으로 검색하면 인덱스 내부에 <code>PAID</code> 값이 여러 고객 번호 구간에 나누어져 존재한다.</p>
<pre><code class="language-text">customer_id = 100 구간의 PAID
customer_id = 200 구간의 PAID
customer_id = 300 구간의 PAID</code></pre>
<p>따라서 하나의 연속된 검색 범위를 쉽게 만들기 어렵다.</p>
<p>복합 인덱스의 컬럼 순서는 인덱스의 활용 가능성을 결정하는 중요한 요소다.</p>
<hr />
<h2 id="복합-인덱스의-컬럼-순서">복합 인덱스의 컬럼 순서</h2>
<p>복합 인덱스의 컬럼 순서를 단순히 카디널리티가 높은 컬럼부터 배치하는 방식으로 결정하면 안 된다.</p>
<p>다음 요소를 함께 고려해야 한다.</p>
<pre><code class="language-text">실제로 사용되는 검색 조건
동등 비교 조건
범위 비교 조건
정렬 기준
조인 조건
컬럼이 단독으로 사용되는지
여러 컬럼이 함께 사용되는지
예상 결과 데이터 수</code></pre>
<p>일반적인 출발점은 다음과 같다.</p>
<pre><code class="language-text">동등 비교 컬럼
→ 범위 비교 컬럼
→ 정렬 또는 추가 필터 컬럼</code></pre>
<p>예를 들어 다음 조건을 자주 사용한다고 하자.</p>
<pre><code class="language-text">customer_id = 특정 고객
ordered_at &gt;= 특정 날짜
ordered_at 내림차순 정렬</code></pre>
<p>다음과 같은 인덱스 순서를 고려할 수 있다.</p>
<pre><code class="language-text">(customer_id, ordered_at)</code></pre>
<p>먼저 고객 번호로 범위를 좁힌 뒤 해당 고객의 주문을 날짜 순서로 탐색할 수 있기 때문이다.</p>
<p>다만 이것은 절대적인 공식이 아니다.</p>
<p>실제 쿼리 조합과 데이터 분포에 따라 적절한 컬럼 순서는 달라질 수 있다.</p>
<hr />
<h1 id="인덱스와-정렬">인덱스와 정렬</h1>
<p>정렬된 인덱스는 정렬 작업을 줄이는 데 사용할 수 있다.</p>
<p>예를 들어 인덱스가 다음 순서로 구성되어 있다고 하자.</p>
<pre><code class="language-text">(customer_id, ordered_at)</code></pre>
<p>인덱스 내부는 다음과 같이 정렬된다.</p>
<pre><code class="language-text">customer_id 우선
→ 같은 customer_id 안에서 ordered_at 순서</code></pre>
<p>따라서 특정 고객의 주문을 날짜 순서로 조회할 때 인덱스의 저장 순서를 활용할 수 있다.</p>
<p>하지만 첫 번째 컬럼 조건 없이 전체 데이터를 날짜 순서로 조회한다면 원하는 정렬 순서와 인덱스 전체의 정렬 순서가 일치하지 않을 수 있다.</p>
<pre><code class="language-text">인덱스 전체 정렬
customer_id → ordered_at

원하는 정렬
ordered_at</code></pre>
<p>복합 인덱스가 정렬에 사용될 수 있는지도 컬럼 순서와 검색 조건을 함께 고려해야 한다.</p>
<hr />
<h1 id="인덱스의-장점">인덱스의 장점</h1>
<p>인덱스의 대표적인 장점은 다음과 같다.</p>
<pre><code class="language-text">전체 데이터를 읽지 않고 원하는 위치를 찾을 수 있음
정확한 값 검색 성능 개선 가능
범위 검색 성능 개선 가능
정렬 작업 감소 가능
조인 대상 탐색 성능 개선 가능
최솟값과 최댓값 검색 지원
고유성 검사 지원</code></pre>
<p>특히 전체 데이터 중 일부만 조회하는 선택적인 조건에서 큰 효과를 낼 가능성이 높다.</p>
<hr />
<h1 id="인덱스의-비용">인덱스의 비용</h1>
<p>인덱스는 조회 성능을 높일 수 있지만 공짜로 제공되는 기능은 아니다.</p>
<h2 id="저장-공간">저장 공간</h2>
<p>인덱스는 원본 데이터와 별도의 자료구조다.</p>
<p>따라서 인덱스를 추가할수록 추가 저장 공간이 필요하다.</p>
<pre><code class="language-text">원본 데이터
+
인덱스 1
+
인덱스 2
+
인덱스 3</code></pre>
<h2 id="삽입-비용">삽입 비용</h2>
<p>새로운 데이터가 추가되면 관련 인덱스에도 새로운 엔트리를 추가해야 한다.</p>
<pre><code class="language-text">데이터 삽입
→ 인덱스에 탐색 키 추가
→ 정렬 순서 유지
→ 필요한 경우 노드 분할</code></pre>
<h2 id="수정-비용">수정 비용</h2>
<p>인덱스 탐색 키로 사용되는 값이 변경되면 기존 인덱스 엔트리를 수정하거나 제거하고 새로운 엔트리를 추가해야 할 수 있다.</p>
<pre><code class="language-text">기존 키 제거
→ 새로운 키 삽입
→ 인덱스 구조 재조정</code></pre>
<h2 id="삭제-비용">삭제 비용</h2>
<p>데이터가 삭제되면 관련 인덱스 엔트리도 정리되어야 한다.</p>
<p>구현 방식에 따라 즉시 제거될 수도 있고 이후 정리 과정에서 제거될 수도 있다.</p>
<h2 id="메모리와-캐시-사용">메모리와 캐시 사용</h2>
<p>인덱스 페이지도 메모리 캐시를 사용한다.</p>
<p>불필요한 인덱스가 많으면 자주 사용하는 데이터와 인덱스가 캐시에서 밀려날 수 있다.</p>
<h2 id="유지보수-비용">유지보수 비용</h2>
<p>데이터 변경이 반복되면 인덱스 페이지가 분할되거나 공간 활용도가 낮아질 수 있다.</p>
<p>인덱스 통계 수집, 재구성, 불필요한 엔트리 정리와 같은 유지보수 작업이 필요할 수 있다.</p>
<hr />
<h1 id="인덱스가-항상-사용되는-것은-아니다">인덱스가 항상 사용되는 것은 아니다</h1>
<p>인덱스가 존재한다고 해서 데이터베이스가 반드시 해당 인덱스를 사용해야 하는 것은 아니다.</p>
<p>데이터베이스는 일반적으로 여러 접근 방법의 예상 비용을 비교한다.</p>
<pre><code class="language-text">인덱스를 탐색하는 비용
인덱스 페이지를 읽는 비용
데이터 페이지로 이동하는 비용
예상 결과 데이터 수
무작위 페이지 접근 비용
전체 데이터를 순차적으로 읽는 비용</code></pre>
<p>조회 대상이 매우 적다면 인덱스를 이용하는 것이 유리할 수 있다.</p>
<pre><code class="language-text">100만 건 중 10건 조회
→ 일부 위치만 탐색</code></pre>
<p>반면 조회 대상이 매우 많다면 전체 데이터를 순차적으로 읽는 것이 더 효율적일 수 있다.</p>
<pre><code class="language-text">100만 건 중 80만 건 조회
→ 인덱스를 통해 대부분의 데이터 페이지 방문
→ 전체 순차 탐색이 더 단순할 수 있음</code></pre>
<p>따라서 다음 두 문장은 서로 다른 의미다.</p>
<pre><code class="language-text">인덱스가 존재한다.
인덱스를 사용하는 것이 효율적이다.</code></pre>
<blockquote>
<p>물론 요런 판단은 DBMS가 할거다 ~</p>
</blockquote>
<hr />
<h1 id="인덱스-설계-원칙">인덱스 설계 원칙</h1>
<p>인덱스는 컬럼 자체가 아니라 실제 데이터 접근 패턴을 기준으로 설계해야 한다.</p>
<h2 id="실제-검색-조건을-기준으로-설계한다">실제 검색 조건을 기준으로 설계한다</h2>
<p>다음 질문을 먼저 확인해야 한다.</p>
<pre><code class="language-text">어떤 조건으로 데이터를 찾는가?
정확한 값 검색인가?
범위 검색인가?
어떤 컬럼을 함께 사용하는가?
어떤 순서로 정렬하는가?
몇 개의 데이터를 반환하는가?</code></pre>
<h2 id="데이터-분포를-확인한다">데이터 분포를 확인한다</h2>
<pre><code class="language-text">전체 데이터 수는 얼마인가?
조건을 만족하는 데이터는 몇 개인가?
값이 균등하게 분포하는가?
특정 값에 데이터가 집중되어 있는가?</code></pre>
<p>같은 컬럼이라도 값별 분포에 따라 인덱스 효과가 달라질 수 있다.</p>
<h2 id="검색-방식에-맞는-구조를-선택한다">검색 방식에 맞는 구조를 선택한다</h2>
<pre><code class="language-text">동등 검색만 필요한가?
범위와 정렬이 필요한가?
탐색 키의 순서가 중요한가?
데이터의 물리적 저장 순서와 연관되는가?</code></pre>
<p>정확한 동등 검색만 필요하다면 Hash 구조를 검토할 수 있다.</p>
<p>범위 검색과 정렬이 필요하다면 Ordered Index가 적합하다.</p>
<h2 id="복합-인덱스는-컬럼-순서가-중요하다">복합 인덱스는 컬럼 순서가 중요하다</h2>
<pre><code class="language-text">어떤 컬럼이 항상 조건에 포함되는가?
어떤 컬럼이 동등 비교에 사용되는가?
어떤 컬럼이 범위 비교에 사용되는가?
정렬 조건과 일치하는가?</code></pre>
<h2 id="읽기와-쓰기-비용을-함께-평가한다">읽기와 쓰기 비용을 함께 평가한다</h2>
<p>조회가 빨라지는 것만 보면 안 된다.</p>
<pre><code class="language-text">조회 빈도
데이터 삽입 빈도
데이터 수정 빈도
데이터 삭제 빈도
추가 저장 공간
유지보수 비용</code></pre>
<p>읽기가 드물고 쓰기가 매우 많은 테이블이라면 인덱스를 과도하게 추가하는 것이 오히려 전체 성능을 떨어뜨릴 수 있다.</p>
<hr />
<h2 id="인덱스-설계-시-주의점">인덱스 설계 시 주의점</h2>
<h3 id="인덱스는-많을수록-좋은-것이-아니다">인덱스는 많을수록 좋은 것이 아니다</h3>
<p>인덱스가 추가될 때마다 데이터 변경 시 관리해야 할 자료구조가 증가한다.</p>
<pre><code class="language-text">인덱스 1개
→ 데이터 변경 시 인덱스 1개 관리

인덱스 10개
→ 데이터 변경 시 최대 10개의 인덱스 관리</code></pre>
<p>사용하지 않는 인덱스는 저장 공간과 쓰기 비용만 증가시킬 수 있다.</p>
<h3 id="선택성이-낮은-조건을-무조건-인덱싱하지-않는다">선택성이 낮은 조건을 무조건 인덱싱하지 않는다</h3>
<p>값의 종류가 적고 대부분의 데이터가 같은 값을 가진다면 인덱스 효과가 제한적일 수 있다.</p>
<p>하지만 값의 종류가 적더라도 특정 값이 매우 적게 존재한다면 효과가 있을 수 있으므로 실제 분포를 확인해야 한다.</p>
<h3 id="복합-인덱스의-선두-컬럼을-고려한다">복합 인덱스의 선두 컬럼을 고려한다</h3>
<p>자주 사용하는 조건이 인덱스의 뒤쪽 컬럼에만 존재한다면 인덱스를 효율적으로 활용하기 어려울 수 있다.</p>
<pre><code class="language-text">인덱스: (a, b)
실제 조건: b</code></pre>
<p>실제 쿼리에서 어떤 컬럼이 먼저 조건으로 사용되는지를 확인해야 한다.</p>
<h3 id="지나치게-넓은-탐색-키를-피한다">지나치게 넓은 탐색 키를 피한다</h3>
<p>탐색 키가 커지면 하나의 인덱스 페이지에 저장할 수 있는 엔트리 수가 줄어든다.</p>
<pre><code class="language-text">큰 탐색 키
→ 페이지당 엔트리 수 감소
→ 트리 높이 증가 가능
→ 페이지 접근 증가</code></pre>
<p>또한 저장 공간과 갱신 비용도 증가한다.</p>
<h3 id="역할이-겹치는-인덱스를-줄인다">역할이 겹치는 인덱스를 줄인다</h3>
<p>다음과 같이 비슷한 역할의 인덱스가 여러 개 존재할 수 있다.</p>
<pre><code class="language-text">(a)
(a, b)
(a, b, c)</code></pre>
<p>상위 복합 인덱스가 단일 컬럼 조건까지 지원할 수 있다면 일부 인덱스는 역할이 중복될 수 있다.</p>
<p>다만 인덱스 크기, 정렬 요구사항, 사용 빈도에 따라 단일 인덱스가 별도로 필요할 수도 있다.</p>
<h3 id="작은-데이터에서는-효과가-제한적일-수-있다">작은 데이터에서는 효과가 제한적일 수 있다</h3>
<p>테이블 전체가 몇 개의 페이지에 불과하다면 인덱스를 탐색하는 비용과 전체 데이터를 읽는 비용의 차이가 크지 않을 수 있다.</p>
<p>인덱스는 데이터가 많을수록 그 필요성이 커지는 경향이 있다.</p>

<h1 id="인덱스-설계-순서">인덱스 설계 순서</h1>
<p>인덱스를 설계할 때는 다음 순서로 접근하는 것이 좋다.</p>
<h2 id="1단계-실제-데이터-접근-패턴-확인">1단계. 실제 데이터 접근 패턴 확인</h2>
<pre><code class="language-text">어떤 조건을 사용하는가?
어떤 컬럼을 함께 사용하는가?
정렬이 필요한가?
몇 건을 반환하는가?
얼마나 자주 실행되는가?</code></pre>
<h2 id="2단계-데이터-분포-확인">2단계. 데이터 분포 확인</h2>
<pre><code class="language-text">전체 데이터 수
서로 다른 값의 수
조건별 예상 데이터 수
특정 값으로의 집중 여부</code></pre>
<h2 id="3단계-인덱스-구조-선택">3단계. 인덱스 구조 선택</h2>
<pre><code class="language-text">동등 검색 중심
→ Hash 구조 검토

동등·범위·정렬
→ Ordered Index 검토

데이터 저장 순서와의 연관
→ Primary 또는 Clustering 구조 검토</code></pre>
<h2 id="4단계-인덱스-밀도-결정">4단계. 인덱스 밀도 결정</h2>
<pre><code class="language-text">모든 탐색 키의 위치가 필요한가?
블록별 대표 키만으로 탐색할 수 있는가?
데이터가 탐색 키 순서로 정렬되어 있는가?</code></pre>
<h2 id="5단계-복합-인덱스-순서-결정">5단계. 복합 인덱스 순서 결정</h2>
<pre><code class="language-text">동등 비교 컬럼
범위 비교 컬럼
정렬 컬럼
선두 컬럼의 단독 사용 여부</code></pre>
<h2 id="6단계-비용-비교">6단계. 비용 비교</h2>
<pre><code class="language-text">조회 성능은 얼마나 개선되는가?
쓰기 비용은 얼마나 증가하는가?
저장 공간은 얼마나 필요한가?
유지보수 비용을 감당할 수 있는가?</code></pre>

<h1 id="마무리">마무리</h1>
<p>인덱스는 단순히 조회 속도를 높이는 기능이 아니다.</p>
<p>인덱스는 데이터의 탐색 방식과 물리적 접근 비용을 설계하는 자료구조다.</p>
<p>인덱스를 제대로 이해하려면 다음 질문에 답할 수 있어야 한다.</p>
<pre><code class="language-text">인덱스에는 무엇이 저장되는가?
탐색 키와 포인터는 어떤 역할을 하는가?
정렬 인덱스와 해시 인덱스의 차이는 무엇인가?
데이터의 물리적 순서가 인덱스 성능에 어떤 영향을 주는가?
Dense Index와 Sparse Index는 무엇이 다른가?
다단계 인덱스가 필요한 이유는 무엇인가?
B+Tree는 왜 디스크 기반 데이터베이스에 적합한가?
선택성이 인덱스 효율에 어떤 영향을 주는가?
복합 인덱스의 컬럼 순서는 왜 중요한가?
조회 성능을 위해 어떤 쓰기 비용을 감당해야 하는가?</code></pre>
<p>좋은 인덱스는 단순히 특정 컬럼에 생성한 인덱스가 아니다.</p>
<pre><code class="language-text">실제 검색 패턴
+
데이터 분포
+
탐색 방식
+
데이터의 물리적 배치
+
읽기와 쓰기 비용</code></pre>
<p>을 함께 고려하여 설계한 인덱스가 좋은 인덱스다.</p>
<p>결국 인덱스 설계의 핵심은 다음과 같다.</p>
<pre><code class="language-text">어떤 데이터를
어떤 기준으로
얼마나 자주 찾는지를 분석하고,

조회 성능과 데이터 변경 비용 사이에서
적절한 균형을 선택하는 것</code></pre>
